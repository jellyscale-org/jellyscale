# Transcoding

Add `transcodeStore` to the config, the same for every role. With none anywhere, nothing transcodes and every source plays as it is. Every process records its roles and `transcodeStore` in the database with a heartbeat, and a replica compares them: when they differ, or one process has none (a worker-only process with none is left out, since it only extracts subtitles), an `api` replica refuses the transcode at PlaybackInfo and its log names both. A spec that already has a live job is offered anyway, by any replica, and its viewer joins it; the log warns and names both stores, and if the replica that serves the segments has no `transcodeStore`, it answers 503 and jellyfin-web asks PlaybackInfo again, which offers the live job again, so before playback the viewer retries without a dialog until the job ends, and after playback has begun the picture freezes; if it has a store it can't read the segments in, the request times out. A store URI that carries credentials (a user or password, or a parameter named like a key, secret, access, token, pass, sig or credential) is refused at startup; credentials come from the environment. A process with only the `worker` role and no store starts and extracts subtitles, but runs no transcodes. Set it, to the same value, on all of them:

| Key | Meaning | Default |
|---|---|---|
| `transcodeStore` | Store URI for segments: `file:///var/lib/jellyscale/segments`, or `s3://bucket/segments?endpoint=...` with credentials from the environment | none |
| `transcodeScratch` | Where a worker's ffmpeg writes before uploading. Workers on one host may share it; each sweep removes job directories untouched for two minutes, which a crash leaves behind | `$TMPDIR/jellyscale-transcode` |
| `transcodeSlots` | Concurrent transcode jobs per worker, paused ones included (below), apart from up to four subtitle extractions; a negative number is refused at startup | 2 |
| `transcodeIdle` | How long without a request before a spec's ffmpeg stops. Closing a tab sends no stop | 60s |
| `transcodeLead` | How much film, from the furthest segment any viewer of a spec has asked for, a transcode job may make before its ffmpeg pauses (below). It is independent of `transcodeIdle`, which still ends a job nobody requests | 60s |
| `transcodeRetention` | How long a spec's segments stay after its last request | 24h |

`stream` replicas and workers share the segments only through that store and Postgres, so the store must be reachable from both: a shared volume, or S3. The worker needs `ffmpeg` and `ffprobe` on its path, as the image has; `api` and `stream` need neither. Segments of a re-encode are 4 seconds, and a restart after a seek splices with the segments before it.

A viewer whose transcode can't start (no worker running, every slot busy, or the same one just failed) gets a "cannot be played at this time" dialog from jellyfin-web instead of waiting, answered within seconds; the server log says which. A segment that fails before playback has begun ends in that dialog too, because jellyfin-web asks PlaybackInfo again and is refused. There are two exceptions: a spec with a live job, which is offered again, and a copy whose keyframe index was found wrong, which is dropped so that the next PlaybackInfo re-encodes the film with no dialog. After playback has begun, a failed segment makes jellyfin-web drop the stream: the picture freezes, with no dialog. A worker that stops gracefully and is replaced within six seconds is not noticed, because a request for a segment waits that long for a worker (`test/roles.sh` does this with real processes). A worker that is killed mid-film is replaced without the viewer losing the picture (below). A viewer on a film whose default track plays as it is, who picks another audio track while no slot is free, keeps playing the default track. In a re-encode, interlaced H.264 is deinterlaced, and the output is H.264 at no more than 1080 lines, in software with `veryfast`; a copy does neither (see Video copy). A worker that falls behind makes the player stall, and there is no lower-quality fallback yet. A job whose ffmpeg makes no segment for 30 seconds is failed, so a hung encode ends in a dialog and not a spinner when it hangs before playback begins; after playback has begun the failed segment freezes the picture as above. A source scanned before the scanner recorded level, field order and range plays directly where its conditions allow it, and is probed again at the next scan, which it does without the file changing.

Storage: segments are kept for `transcodeRetention` (24 hours) after a spec's last request, one set per spec, so a film watched in full at a quality cap of *B* bits per second takes up to *B* × 3600 / 8 bytes per hour of film: about 0.45 GB per hour for each megabit of the cap. The encoder also caps video at 6 × width × height bits per second, and the width follows the source's shape: at 1080 lines a 16:9 spec stays under about 12.63 Mbps (about 5.7 GB per hour) and a 2.39:1 one, 2578 wide, under about 16.9 Mbps (about 7.6 GB per hour); at 720 lines 16:9 stays under about 5.72 Mbps (about 2.6 GB per hour). These are ceilings for a re-encode, with the 192 kbps audio included; none of them applies to a copied stream (see Video copy); how far real film at crf 23 falls below them has not been measured. Each distinct audio track or quality is its own spec. Workers also hold a job's unuploaded segments in `transcodeScratch`, a few at a time.

## Worker failover

What an operator has to do:

- Run at least two workers, with a slot to spare between them, so one can take over the other's jobs.
- Give workers a direct, session-mode Postgres URL, not one behind a transaction-mode pooler (Connections, below).
- Optionally set Postgres's `tcp_keepalives_*`, so that a worker whose host vanishes is noticed in seconds rather than at its 10 second lease (The bounds, below).

A worker killed in the middle of a film is replaced: another worker continues the job at the first missing segment, and jellyfin-web keeps playing, with no dialog. Killed 1.6 seconds into playback (the least buffer there is), the picture of a re-encode stood still for 2.5 to 2.8 seconds in jellyfin-web, and a copy's for 0.3 (`test/e2e`, four runs); a copy's replacement started about 5 seconds after the kill, when the player next asked, because a copy had read ahead and its player had enough to show meanwhile; it goes on by itself, because hls.js abandons a request after 10 seconds, and later in a film, with a full buffer, the viewer sees nothing. This needs a second worker with a free slot (or the same one restarted within 6 seconds, as before). With one worker, or none free, the job waits in the queue, and after 6 seconds the segment request fails and the picture freezes with no dialog; only the viewer's next PlaybackInfo, after a seek or a new film, gets the "cannot be played" dialog. Replacement segments splice with the earlier ones (a restart after a seek does the same).

What an operator sees: each worker holds a Postgres session advisory lock for as long as it lives. Every live worker looks for workers whose lock is gone four times a second, and so does every PlaybackInfo, at most once a second per replica. Whoever finds one forgets it (its slots stop counting, so the next PlaybackInfo with no worker left is refused) and gives its jobs a second to end, after which a viewer's next request queues the job again for a live worker. Measured with real processes and ffmpeg at twice the film's speed, a SIGKILLed worker's replacement had the first missing segment 4.0 to 4.3 seconds after the kill (2 seconds before the new job starts, then the time ffmpeg takes to make a segment, which a re-encode slower than real time makes longer). Without this it was 13 seconds, past the 10 seconds after which hls.js abandons a request. The logs of one failover: whoever found the dead worker says `workers whose liveness lock is gone were forgotten`, naming the workers and the jobs it cut short; the new job is a `transcode started` for the same spec, at the first missing segment. A worker that lost its lock while it lives says `the worker lost its liveness lock`, after a line with the cause (`the worker's liveness connection ended` with its error, `the liveness connection is open but Postgres does not show its lock`, or `another replica took this worker for dead`), and its jobs end as `transcode interrupted` with `the worker's liveness lock was lost`, or `the worker was taken for dead`; `the worker holds its liveness lock again` says it is back.

The bounds: the lock is dropped by Postgres when the connection closes, which the kernel does however the worker's process dies, so a killed process, an out-of-memory kill, a crash and a stop of the container are all noticed within about a second. A host that loses power, a kernel panic, a network partition, and a pooler or proxy that keeps the server's end of the connection open when the worker's goes away close nothing, and then the job is taken over when its lease runs out, up to 10 seconds after the worker's last renewal, as before, and the dead worker counts as a worker for 10 seconds. Setting Postgres's `tcp_keepalives_idle`, `tcp_keepalives_interval` and `tcp_keepalives_count` makes the server drop such a connection, and the lock, sooner; the job is then taken over a second after, and a worker that is alive but cut off from Postgres may run its ffmpeg until its own lease check (10 seconds after its last renewal). It cannot store a segment meanwhile: before every store a worker asks Postgres whether the job is still its own, with an unexpired lease, and a database that does not answer counts as no. The same holds for a worker stopped (SIGSTOP, a frozen VM) for longer than its lease: its job is taken over, and when it goes on it stores nothing. A worker stopped for less than the lease, or a job waiting at its read-ahead limit, keeps its connection and is not taken from. A worker that loses its lock while it lives (Postgres restarted, a backend terminated, a proxy dropped an idle connection) stops every ffmpeg at once, claims nothing, connects again, and registers again only when it holds the lock, so a job is never stored by two workers. A lock that is gone while the worker's connection stands (the server's end was recycled by a pooler) is found by the worker four times a second, within the second's grace its jobs are given: its own reap finds its lock gone, or its row already deleted by whoever reaped first, and that is a loss too, logged with a hint to check for a pooler. A Postgres restart or failover ends every worker's lock connection at once, so every transcode in the cluster stops and is restarted at its first missing segment once the workers have locked again, which they try every second; viewers see a stall, and the segments splice (the audio bytes of a restart can differ). Two node ids that hash alike share a lock (about one chance in four billion for a pair): a dead one looks alive until its lease runs out, and the second of two live ones claims nothing until the first lets go, logging `the liveness lock is held by another node whose id has the same hash` every second; a restart gives it a new id.

Connections: each worker process opens one more Postgres connection, for the lock. It must be a direct, session-mode connection: behind a transaction-mode pooler such as pgbouncer the lock would belong to whichever server connection the pooler chose. (The listener for hints needs the same, but falls back to polling with a warning; the liveness lock cannot, and a worker that finds its lock missing says so in its log and names the pooler.) Behind a transaction-mode pooler a worker takes its lock, finds it gone at its first look, and tries again every second, logging an error each time; it claims next to nothing until the URL is fixed. A database slower than half a second a round trip is slow, not gone: the worker registers (it gives that 3 seconds) and keeps working, but each of its looks at the dead times out, so it reaps nobody and finds its own lost lock only through its 10 second lease; and if it stays that slow for 10 seconds, the worker's `seen_at` refresh (also bounded at half a second) does not land and PlaybackInfo stops counting the worker until it does (`TestAWorkerRegistersOverASlowDatabase` uses 300 ms). Postgres's `idle_session_timeout` must be off for the workers' role, since the lock's connection is idle by design: with it on, every timeout ends the lock and restarts the worker's transcodes. A fleet of N workers uses N more connections; `api` and `stream` processes use none for this. Subtitle extractions and chapter pictures keep their 10 second lease, whoever dies.

Not built: an `api` replica killed mid-film, which `PRODUCT.md` keeps as the other half of the Phase 4 gate, and an autoscaler.

## Video copy

When the video can play in the client as it is and only the audio or the container can't (H.264, HEVC or AV1 with AC3 in MKV, or in MP4), the worker copies the video and re-encodes the audio to AAC. A stream then costs almost no CPU and keeps the source's picture exactly. Nothing to configure. It happens when:

- the video is H.264, HEVC or AV1, and passes the client's `CodecProfiles` for it (profile, level, range, interlacing, resolution), and the client's HLS transcoding profile lists the codec;
- the picture is SDR (H.264 too), and for HEVC and AV1 the profile is one the master playlist can name: HEVC Main or Main 10, AV1 profile 0 at 8 or 10 bits. HDR films and other profiles are re-encoded to H.264, and HDR is tone mapped (below);
- no bitrate cap is below the file's bitrate, and no subtitle is to be burnt in;
- the file has a keyframe index, which the scan reads from the file's own index (Matroska Cues, or the MP4 sample tables) and keeps in the database. A Matroska file written without Cues, a fragmented MP4 and any other container are re-encoded, as before;
- no gap between keyframes is longer than 12 seconds, counting the stretch from the last keyframe to the end of the film. x264 and x265 default to a keyframe every 250 frames, which is under 12 seconds at 21 fps and up. A file with longer gaps is re-encoded.

The playlist is cut on the file's keyframes: a segment ends at the first keyframe at least 4 seconds after it began, or earlier if waiting would make it longer than 12 seconds, so no segment is over 12 seconds, and the playlist says their exact lengths.

A copy is not capped, and at Auto it carries the file's whole bitrate and size, 4K included, exactly as direct play of the same file does and as Jellyfin's copy does. A viewer on a slow link picks a cap in the quality menu, which re-encodes. A copy stores and sends the picture at the file's own bitrate: a 40 Mbps remux takes about 18 GB per hour (computed) of film for each spec, kept for 24 hours, against the 5.7 GB per hour at most of a 1080p re-encode. None of the storage ceilings above applies to it.

Reading the source: a copy opens the file twice, once for the video and once for the audio, and reads each at 5 times the film's speed (`-readrate 5`), so while the job runs it reads ten times the film's bitrate, and a run to the end reads twice the film's bytes. A job also stops when it is far enough ahead of its viewers (below), so what it reads is bounded by what is watched, not by the film. Every request for a copied stream's playlists and segments reads the film's keyframe array (about 14 KB computed for a 2 hour film with a keyframe every 4 seconds, 8 bytes each) from Postgres; the request rate has not been measured. For a 2 hour film at 40 Mbps (36 GB), a viewer who watches it to the end still costs a run to the end: 72 GB read from the source (72 GB of S3 egress), 36 GB of segments stored for 24 hours, over the length of the film. A viewer who leaves after a minute no longer costs the 120 seconds of a job running free (about 600 s of film made, 6 GB read, 3 GB stored, computed from the rates). The job has made at most the furthest segment the player asked for, plus the 60 seconds of `transcodeLead`, plus the rest of its last segment (up to 12 seconds): with a player that asked for 30 seconds beyond what it showed (an assumption; the buffer was not measured), 60 + 30 + 60 + 12 = 162 seconds of film, 1.6 GB read, 0.8 GB stored, and then the job waits `transcodeIdle` paused, reading nothing. The byte figures here are computed from the bitrate and the length, not measured. They assume the store takes uploads at 5 times the film's speed (200 Mbps for a 40 Mbps film), and ffmpeg is not paced by uploads: unuploaded segments sit in `transcodeScratch` a few at a time if the store keeps up. A store slower than that lets ffmpeg make segments in scratch until the uploaded ones reach the lead, which is more than the lead by the ratio of the speeds (5 times the lead for a store that takes the film at 1 times its speed); they are not uploaded past the lead. A seek waits for the whole segment it lands in, up to 12 seconds of film (60 MB at 40 Mbps), read at 5 times the film's speed and downloaded at the file's bitrate.

**Read-ahead.** A job makes at most `transcodeLead` (default 60 seconds of film, 15 segments of 4 seconds in a re-encode, fewer in a copy whose segments are longer) beyond the furthest segment a viewer of its spec has asked for. Then the worker stops its ffmpeg (SIGSTOP) and starts it again (SIGCONT) when requests come within the lead. The stream replica that serves a segment writes the segment number into the viewer's row, `transcode_viewers.segment`, in the write it already makes for every request (`last_seen_at`), so a segment request costs no more writes than before. A worker whose job has made everything up to its limit looks at the viewers' segments every 500 ms; a job that is not at its limit does not look. The viewers counted are those not stopped and seen within `transcodeIdle`, whose last segment is one this job has made or is about to (the window in which `ensure` lets a request join a job): a viewer far ahead has a job of its own and does not carry this one on. A viewer that has fetched only a playlist, or one served by a replica from before this, has no segment and frees the job until it asks for one or is gone. A paused job keeps its lease, its slot and its scratch directory, which the worker touches so that another worker's sweep leaves it; the stall check does not run while it is paused; and `transcodeIdle` ends it as it ends any job, 60 seconds after the last request. A seek past the lead starts a job there, as before. Segments beyond the limit that ffmpeg made before it was paused stay in scratch until the limit reaches them. SIGSTOP was chosen over ffmpeg's own controls because it is the same on ffmpeg 6.1, 8.1 and 9, needs no pipe to ffmpeg, and leaves its input open at its place. A system without it (not Linux) runs jobs without the bound and says so in the log.

Default lead: the bound is the furthest segment asked for plus the lead, not the playback position, so what the player asks for is always inside it, whatever its buffer. The lead only has to cover what a resume takes: the worker's 500 ms look, ffmpeg making the next segment (a re-encode slower than real time makes a 4 second one in more than 4 seconds), and the delay between the player asking and the segment landing. In jellyfin-web in Chromium with `transcodeLead` 20s (5 segments), a copied film's job had stored 7 segments when the player had asked for up to 2, and a re-encoded one's 10 when it had asked for up to 5, of 45, with ffmpeg stopped (`test/e2e`). With 10 second copied segments from S3 at 5 times the film's speed, a request after a 20 second pause was answered in 2.2 to 2.4 seconds, and each one after it in 1.9 (`TestAPausedCopyFromS3ResumesAndMakesTheSameSegments`).

Jellyfin 12.4 (a `jellyfin/jellyfin:12.4` container's `encoding.xml`) has `EnableThrottling` false and `ThrottleDelaySeconds` 180 by default, so its transcodes run to the end of the film unless the operator turns throttling on. How it pauses when on was not observed; jellyscale bounds by default.

**Paused jobs hold slots.** A paused job keeps its slot, so `transcodeSlots` bounds the transcoded streams a worker serves at once, not only the encodes running: a copy of a 2 hour film holds its slot for the 2 hours, where before it held it for the 24 minutes its read took. A slot is one job, that is one spec being watched: viewers of the same spec share it, direct play takes none, and capacity is the workers times `transcodeSlots`. A re-encode pauses only where it runs faster than the film, so over a watch it costs what keeps up with the film. From the measurements under Tone mapping (x264 veryfast, at most 1080 lines out): about 0.8 of a core for a 1080p SDR source, 1.6 for 4K SDR, 2.0 for 1080p HDR10 and 3.2 for 4K HDR10; a copy costs almost none. Size `transcodeSlots` as the worker's cores divided by the cost of the films it re-encodes, plus a quarter for headroom (so about 4 cores a slot for 4K HDR, as below), because a new job and each seek run flat out until they are the lead ahead; on a worker that mostly copies it can be well above its cores. Too few slots shows as `all N transcode slots are busy` in the log and a "cannot be played at this time" dialog; with the default 2 and one worker, a third transcoded stream at once is refused. A paused job whose viewers have all seeked away from it is cancelled within a second and gives its slot back; jellyfin-web stops the old stream when it switches audio track or quality (`Sessions/Playing/Stopped`), which ends its job; one whose viewers have gone (a closed tab sends nothing) is ended `transcodeIdle` after their last request, as any job is.

**Paused jobs and ffmpeg 6.1.** ffmpeg 6.1 budgets `-readrate` against the wall clock without `-readrate_catchup`, so after a pause it reads unthrottled until it has caught up (measured: `-readrate 5 -c copy` stopped for 8 seconds at 20.4 seconds of film was at 61 seconds 0.2 seconds after SIGCONT; 8.1.3 and 9.0.2 went on at 5 times the film). The worker pauses it again within its 100 ms poll, so on 6.1 a resume reads past the limit what ffmpeg reads at full speed in up to 100 ms, bounded by the disk or the network rather than the film. Nothing past the limit is stored. The image's ffmpeg is not 6.1; a worker run on Ubuntu 24.04's is. **S3 inputs.** A stopped ffmpeg stops reading its two connections to the loopback server, which stop reading their S3 GETs. The test pauses a copy from SeaweedFS and Garage for 20 seconds and resumes it with the same segments, byte for byte, as a run from the start; a body the store cuts meanwhile is reopened at its offset by the reader (`store.Reader`, invariant 42). A connection a proxy drops with a reset meanwhile is reopened at its offset the same way (`TestReaderResumesAfterAReset`, with a store that resets the body; no real proxy was run), so a job paused for up to `transcodeIdle` with its GETs held does not fail on that. **Upgrading.** The migration adds `transcode_viewers.segment`. Replicas and workers may roll in any order: a worker keeps a job unbounded while a viewer of its spec has recorded no segment, as an old `api` or `stream` replica never does.

The audio becomes stereo AAC (192 kbps by default), so only the picture is unchanged.

The scan builds the index, and a few things have to be known about it. A film scanned before this version has no index until the next scan reads it (a scan does so for every H.264, HEVC or AV1 file in MKV or MP4 that has none), so it is re-encoded until then. For a Matroska file the index is the Cues (the test bounds the read to 2% of a small test file); for an MP4 it is the moov, which has an entry for every frame and audio packet, so a large MP4's is megabytes. The scan also reads where the video ends, from the packets of the last stretch from the last keyframe to the end of the file, when that stretch is within 12 seconds of the file's duration (a film with a longer gap can't be copied and is not read): up to 12 seconds of film, read up to twice (120 MB at 40 Mbps), plus what ffmpeg reads to open the file, a few MB that vary with its version. If the index turns out not to match the file (a segment doesn't start or end on a keyframe), the job fails, the file's index is dropped and an error logged with the item and source, and the next PlaybackInfo re-encodes the film (jellyfin-web asks PlaybackInfo again when a segment fails before playback has begun; after it has begun the picture freezes until the viewer restarts). A dropped index stays empty until the file changes; to have the scan read it again, set `keyframes` to NULL on that `media_sources` row. An input cut short (a file truncated in the store) fails the job but keeps the index, unless the cut is within 1.5 seconds of the end of the film, inside the last segment: that job succeeds and its last segment is that much short. The scan logs an unusable index at Info with the reason, and a read that failed at Warn, to be tried again at the next scan; the other reasons a film is re-encoded are in the `TranscodeReasons` of the PlaybackInfo reply. A film whose audio outlasts its video enough to fail the 12 second check against the file's duration is re-encoded.

Upgrading from a version without video copy, roll in this order: workers, then `stream` replicas, then `api` replicas. The API is what offers a copy, so it goes last. A worker from before this release that claimed a copy job would not know it is a copy, and would re-encode the picture and store it under the copy's hash; once every worker is new, none can.

After the HEVC and AV1 slice, HEVC and AV1 films scanned before it have no index and no stored bit depth until the next scan reads them (it does so without the file changing), and are re-encoded until then. Chrome plays AV1 in software, so an AV1 film with AC3 audio now arrives as a copy of the file's own picture; it plays HEVC only with a hardware decoder, which jellyfin-web's profile reports, so on other machines an HEVC film is re-encoded as before. What a copy costs in Postgres, network and storage is the H.264 copy's or less (HEVC and AV1 files are smaller than H.264 of the same quality): the keyframe array per request, the Cues or moov read once per scan, no new role. Observed against Jellyfin 12.4 in [`compat/captures/hevc-av1-12.4.md`](../compat/captures/hevc-av1-12.4.md).

After this release, existing H.264 films whose audio the client can't play (AC3 in MKV, say) become full-bitrate copies once a scan has read their index, where they were re-encoded. A viewer on such a film gets the source's picture, and the storage and bandwidth change with it: a copy stores and sends the file's own bitrate (see Storage above and the figures under Video copy), where a re-encode is at most 1080p.

**Audio copy.** When the video is re-encoded (a codec the client lacks, interlaced, a level or profile over its limit, a bitrate cap, a burnt subtitle) the audio is copied, not encoded to AAC, if the client's fMP4 HLS transcoding profile lists its codec (of AAC, MP3, AC3, E-AC3, Opus and FLAC), the track has no more channels than that profile's `MaxAudioChannels` and the CodecProfile limits on audio, and it takes no more than a quarter of the bitrate cap (the copy's own bitrate comes out of the cap and the picture gets the rest). Jellyfin's Chrome profile lists AAC, Opus and FLAC with two channels, so there stereo tracks of those codecs copy and AC3 and 5.1 are still encoded to stereo AAC; a client that lists AC3 and six channels gets them as they are, when the track is within a quarter of the cap. A track whose file doesn't state its bitrate (a Matroska file without a `BPS` tag, which the scan now reads) counts as 6 Mbps, so it copies at Auto and under caps of 24 Mbps and up; a film scanned before this version has the bitrates the earlier scan stored, with no rescan forced. The video-copy path still encodes its audio. Observed against Jellyfin 12.4 in [`compat/captures/audio-copy-12.4.md`](../compat/captures/audio-copy-12.4.md). After a restart on another worker, a copy from an MP4 has the same audio bytes in each segment; a copy from a Matroska file has the same packets, with times that can move by under 1 ms, because Matroska stores whole milliseconds. That is inaudible, and accepted.

What it costs: a worker spends no CPU on the audio (no decode, downmix or AAC encode) and a restart reads the film the same two times as before. The network, S3 reads and stored segments grow with the track: a 640 kbps AC3 5.1 track in place of 192 kbps AAC is 0.45 Mbps more to each viewer, so 100 streams add about 45 Mbps through `stream` and from the store, and about 0.2 GB of storage per hour of film for each spec (viewers of the same film, track and cap share its segments) (FLAC at 1 to 4 Mbps adds up to ten times that), kept for the 24 hours of any segment. Postgres holds no more than before: a stream's `BitRate` was already in `media_sources.streams`, and the spec hash text is a few characters longer. A copied track is the file's own packets, so a restart on another worker puts the same packets in the same segments (`TestCopiedAudioSplicesTheSamePackets`), where encoded audio differs inaudibly; an MP4 source's audio in each segment is byte for byte the same, and a Matroska source's packets are identical with times that can differ by under 1 ms after a restart, because Matroska stores whole milliseconds (accepted). The risk that is not measured: a client that lists FLAC or AC3 whose decoder stutters on a high bitrate; its CodecProfile limits are honoured, nothing else is.

## Tone mapping

A film in PQ (HDR10) or HLG that is re-encoded to H.264 is tone mapped to SDR BT.709 on the worker, so a viewer on an SDR screen doesn't see washed-out colour. Nothing to configure. It happens when:

- the video is re-encoded, which an HDR film is for a client that wasn't told it plays HDR (an HDR film is never copied to one, in H.264 as in HEVC and AV1);
- the file declares PQ or HLG as its transfer function. Dolby Vision is mapped by its base layer: 8.1 as HDR10 and 8.4 as HLG; profile 5, which has no HDR10 base, is left alone (it still looks wrong, as before). Films scanned before this release have no transfer function stored and are not mapped until the next scan reads them again.

It is done in software with ffmpeg's `zscale` and `tonemap` filters, which every ffmpeg the project is tested with has (6.1.1 on Ubuntu 24.04, 8.1 on Alpine, 9.0). `libplacebo` would need a GPU on the worker and is not used. Tone mapping is the expensive part of an HDR transcode: on this 16 core machine, x264 veryfast to 1080p cost 40.5 CPU seconds for 20 s of 1080p HDR10 against 15.2 without the mapping (2.7 times), and 63.7 CPU seconds for 20 s of 4K HEVC against 32.2 (2.0 times), about 3.2 cores to keep one 4K HDR stream in real time. A worker's slots count every job alike, so size `transcodeSlots` for 4K HDR films by cores (about 4 per slot), not for SDR ones. The output is bigger than an unmapped re-encode of the same film, by 11% to 16% for the 1080p clip and 16% to 38% for the 4K one in two measurements (11.9 MB against 10.7 MB, and 6.4 MB against 5.5 MB), under the same bitrate cap, 8-bit, at most 1080 lines.

Upgrading from a version without tone mapping, roll in this order: workers, then `stream` replicas, then `api` replicas. Both `stream` and `api` replicas queue tone-mapped jobs (a master playlist request starts one). A worker from before this release that claimed one would not know the spec's `ToneMap`, would re-encode the picture without mapping it and store the washed-out segments under the tone-mapped hash, where viewers get them for the 24 hours of retention with nothing in any log. The same holds when rolling back: roll back the `api` and `stream` replicas first, so no tone-mapped job is queued when the first old worker starts. Once every worker is new, none can claim one wrongly. This is a known departure (ARCHITECTURE, Known departures), the same exposure as copied audio, so workers roll first and roll back last. A `stream` replica of this release still serves an older `api` replica's copy of an H.264 HDR film as a copy, so a playback begun during the upgrade keeps going.
