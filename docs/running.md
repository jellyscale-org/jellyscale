# Running jellyscale

## Roles

One binary, chosen with `--roles`:

| Role | Serves |
|---|---|
| `api` | REST API, WebSocket |
| `stream` | Images, direct-play media, file downloads, HLS playlists and segments, subtitles, the encoding configuration |
| `worker` | Library scans, transcodes, subtitle extraction |

`--roles=all` runs everything in one process. Paths under `/Videos/`, `/Items/*/Images/` and `/Items/*/Download`, and `/Playback/BitrateTest` and `/System/Configuration/encoding` (case-insensitive), belong on `stream`, and everything else on `api`. [`deploy/compose/Caddyfile`](../deploy/compose/Caddyfile) and `test/e2e/router.mjs` do this. An ingress written before `/System/Configuration/encoding` moved to `stream` (so that it is answered while Postgres is away) must add it: an `api` replica answers it 404, and jellyfin-web then draws no ASS subtitles.

## Run

```sh
docker create --name jf jellyfin/jellyfin:12.4
docker cp jf:/jellyfin/jellyfin-web web-dist && docker rm -v jf

MEDIA_DIR=/path/to/media JELLYSCALE_ADMIN_PASSWORD=change-me \
  docker compose -f deploy/compose/compose.yaml up --build
```

`MEDIA_DIR` needs `movies/` and `shows/` folders. Segments are kept in the `transcode` volume. Open http://127.0.0.1:8096/web/ and sign in as `admin`. The stack's Caddy ingress sends media and images to `stream` and the rest to `api`. Libraries on S3 need `JELLYSCALE_S3_ACCESS_KEY` and `JELLYSCALE_S3_SECRET_KEY` exported on the host; compose passes them to every service. Add one to `deploy/compose/config.json` such as `{"name": "Cloud", "kind": "movies", "media": "s3://bucket/movies?endpoint=https://s3.example.com", "assets": "s3://bucket/assets?endpoint=https://s3.example.com"}`. For a single process, run `--roles=all`.

A client's tests that want a server with a small known library, started with one Compose file and no setup, use the published fixtures image: [Testing a client](client-testing.md).

## Rolling update

Replace the `stream` replicas first, then the `api` replicas. An `api` replica of this release offers a copy of HDR10, HDR10+ and HLG video, and a `stream` replica of the previous release refuses that copy, so a viewer who is sent to it fails to play. A new `stream` replica serves every copy the previous `api` offered, so it is safe to be first.

Every job records the output version of the replica that queued it, and a worker claims only jobs of the version it makes, so an upgrade must keep a running worker for every version a running replica queues. To upgrade, start the new workers first, then replace `stream`, then `api`, and stop the old workers last, so that at each step every version a running replica queues has a running worker that makes it. To roll back, start the old workers first, then put the old `api` back, then the old `stream`, and stop the new workers last, again with a worker for each version at every step: the old `stream` must never run while no worker of the old version does. When a release does not change the output version, the order matters only for the HDR10 rule above, and for a job kind the old workers don't know: JS-089 adds the subtitle job kind `images` (a film's image tracks, stored in the asset store) without changing the output version, so for that release roll the workers first, as DOMAINS 51 says. A worker of the release before claims an `images` job as a subtitle track, fails it (`subtitle extraction failed`, `the source file has changed or is gone`, logged at Error) and the next play after 30 seconds queues it again, so while old workers run, the film's track is stored by a new worker or not at all, and viewers meanwhile have a burnt cue drawn as JS-071 did, with no wait. JS-088 raises it from 4 to 5 because a worker from before it cannot make the copy-fallback `Recode` layout. That changes every spec hash: segments and running jobs of version 4 are not reused by version 5, so playback is encoded again as it is asked for; old workers must stay until their version 4 jobs end, and the old objects remain in the store until the ordinary 24 hour retention sweep.

Rolling back across the liveness changes of JS-030: a worker of the release before stops at start on `--liveness-database-url` (`flag provided but not defined`) and takes its lock and renews its leases through `JELLYSCALE_DATABASE_URL`. Remove the flag from the worker, and make `JELLYSCALE_DATABASE_URL` a direct, session-mode URL again if a pooler was put in front of it because the flag sent the lock around it, before such a worker starts. Workers and replicas roll in any order for this change (none is needed: a replica ignores the flag, and the output-version order above is the only one); for a roll forward, start the new workers with the flag once the pooled URL is in place. A fleet of both releases meanwhile works: the workers of the release before each still look for the dead, beside the one reaper of the new, so a dead worker of either release is forgotten on the same conditions and no live worker of either release is forgotten. A subtitle row of a worker that an old worker forgot waits out its full lease as before (only the new reaper cuts it), and a worker from before the liveness lock (a row that took no lock) is never forgotten and is taken over at its lease.

When that order is not kept, a viewer whose job no running worker of its version takes waits `queueTimeout` (6 seconds) and no less, then gets a 503 with `Retry-After`, and the server log says that only workers of another output version run. Segments made by another version are never served under a spec of this one. A worker built before this release makes no such check, since it claims any queued job, so every such worker must be stopped before a replica of a later output version starts.

## Replicas, readiness and the ingress

Run two or more replicas of `api` and of `stream` behind the ingress. Two routes tell it about each one, and neither needs a token:

- `GET /healthz` is liveness: it answers 2xx from the process alone, through a drain and through any Postgres outage, so a liveness probe never restarts every pod together.
- `GET /readyz` is readiness: 200 while the replica takes requests, 503 from the moment it is told to stop, and 503 when it has been cut off from Postgres for 30 seconds without a break. Outages that are shorter, or that add up to more than 30 seconds, never fail it, so a switchover does not take every replica out of service.

What any ingress must do, and the shipped [Caddyfile](../deploy/compose/Caddyfile) does with two replicas of each role listed one by one:

- Poll `/readyz` of every replica at an interval of 2 seconds or less. A polling interval is the time a router needs to notice, and lead below is longer than it.
- Stop sending to a replica that answers 503, and to one that does not answer: a refused connection means the process is gone.
- Retry a GET or HEAD that failed before its response header (a connection refused or reset) on another replica, so that a replica killed between two polls costs a viewer no segment. A film that has begun freezes on one failed segment.
- Keep one upstream per replica. A name that resolves to several replicas is one upstream to Caddy's health check, and one draining replica would take the whole role out.
- When no replica of a role is ready, which happens when Postgres has been away from every one of them for more than 30 seconds, send to all of them anyway if the ingress can: requests wait for Postgres on every replica (a segment up to 90 seconds) and are answered when it is back, where a 503 from the ingress stops the film. Caddy's active health check has no such fallback and answers 503 itself, so the shipped Caddyfile adds one in `handle_errors`: when a block finds no ready replica it sends the request to every replica of the role, ignoring `/readyz` (and a viewer then waits about a second longer for the 503 to be given up on). A Kubernetes Service with `publishNotReadyAddresses: true` sends to every pod but then ignores readiness in a drain too, so only an ingress that fails open when none is ready gives both.

`shutdownGrace` is how long a replica that gets SIGTERM takes to stop, as a Go duration, counted from the signal; left out it is `30s`, and a value that is not a duration or is negative stops the start, naming the key. On SIGTERM `/readyz` answers 503 at once and the replica goes on taking and answering new requests for a lead of 5 seconds, so that a router that polls every second or two has stopped sending before any request is refused (a `shutdownGrace` below 5 seconds shortens it). It then closes its WebSockets, with a close frame and their rows removed, so clients reconnect to another replica, and stops accepting connections. A response in flight, such as a segment waiting on its job or a direct-play range, is sent whole if it ends within the grace, and the process then exits by itself; one that outlasts the grace is cut at its end and the process exits within seconds of it, so a slow or hung client never holds a replica. Set the pod's termination grace period (`terminationGracePeriodSeconds`) above `shutdownGrace`, 40 seconds for the default, or the pod is killed in the middle of the drain. A viewer on a replica that is killed rather than stopped reconnects the WebSocket to another replica, and the killed replica's claim on a device is gone within seconds, without the device having to reconnect.

## Memory of the stream role

A `stream` replica sends a segment while it reads it from the store, 32 KiB at a time, so its memory is a fixed base plus a figure per viewer: a base of 64 MiB (the Go runtime, the snapshot of sessions and the connection pools) and 1 MiB per concurrent viewer of Go heap, the most the memory test allows. The figure does not grow with the film's bitrate or the segment's length: a 4K copy segment of tens of MB costs a viewer the same as a 2 MB one. The heap is not all a viewer costs: a viewer who stops reading leaves the bytes already written in the kernel's send buffer of its connection, bounded by `tcp_wmem` (about 4 MiB), and on an S3 store the store connection's receive queue (`tcp_rmem`) holds some more, which comes on top of the heap and counts toward a pod's limit, not its heap. For requests and limits, take the base, plus the heap figure and the send buffer for each viewer the replica is to carry.

## Configuration

A process started without `--config` runs with every key at the default, the same as a config of `{}`: `name` is `jellyscale`, `adminUser` is empty (no account is created), `webDir` is empty (no web client is served), and `scanInterval`, how often a worker scans its libraries, is `15m`; a value that is not a positive duration stops the start naming the key, whatever the role, before anything is written to Postgres. The other keys are at the defaults named below and in docs/transcoding.md, and the drain is as in "Rolling update". `--roles` takes `api`, `stream`, `worker`, a comma-separated list of them, or `all`; an empty, unknown or repeated role, or `all` in a list, stops the start naming it.

A key the server does not know, at the top of the config or in a library, is refused at startup with its name, so a misspelt `chapterImages` can't silently leave the option off; so is anything after the config. Upgrading: a config that loaded before because the server ignored a stray key now stops the start, naming the key to remove.

A library whose POSIX media folder is missing fails its scan with an error naming the folder, and so does one whose media store lists no video at all while the library has films (an empty mount point, a volume unmounted under a folder that is still there, or an empty bucket): the films and their watch state are kept, the log says why, and the next scan after the volume is back carries on as before. The cost is that a library emptied on purpose keeps its last films listed until a video is in it again.

A film or episode whose file a scan no longer lists is hidden, not deleted: viewers see what they would if it were gone, but its item, media source and every viewer's position, played flag and favourite stay in the database. A file that is listed again inside the grace, at its old key or moved or copied to another (matched by its size and ETag, or by its size and what the probe finds in it), is shown again as the same item. `missingGrace`, a Go duration such as `72h`, is how long that grace is; left out it is `168h` (seven days), and a value that is not a duration or is negative stops the start, naming the key. The grace is counted by Postgres's clock from the first scan that missed the file and kept in the database, so it holds across scans, workers and restarts. The first scan after it has passed removes the item with its watch state, and then any season or series left with no episode; a file that returns after that is a new item.

`maxLostShare`, a number from 0 to 1 (left out, `0.2`), is the most of a library's stored files a scan may find missing. A scan that would lose more fails, like the empty-mount case above, with an error that names the library, how many files are lost and how many are stored; it hides and removes nothing (not even an item whose grace has passed), `jellyscale_scan_last_success` is 0 for the library, and every later scan fails the same way until the files are back, when the first one succeeds with every item and watch state as before. A file moved to another key and matched to its item is not lost, and the files already hidden count, so several small losses can't add up unseen. After removing that many files on purpose (more than the share of a library), set `maxLostShare` to `1` for one scan, or higher than the share you are removing, and set it back.

A library is identified by its media store and kind, not only by its name: a config that changes only a library's `name` leaves one library with the same id, items and watch state, and the new name in the views. A library that is new to the database gets the hash of its name as its id, which is what every library has had, so an upgrade keeps all ids. A library left out of config is hidden with its items (it is gone from the views, and its items from every listing) and is removed, with its items and everyone's watch state, by the first worker tick after `missingGrace` has passed since the first worker start without it; putting it back in config before then shows it again with its id and everything in it. A worker removes libraries on every scan tick, so no restart is needed. Every worker must list the same libraries: a worker whose list leaves a library out hides it from every viewer and starts its grace, whatever the other workers list. The `libraries` of api and stream replicas are not read (a bad entry there stops only a worker), and a worker listing none hides and removes nothing, so emptying the list does not remove the last library. A library's grace runs from the first worker start without it, no longer from any start.

`transcodeHelpers` set to `false` stops this worker's slow transcodes from asking other workers to help (parallel transcoding): a slow job is then one ffmpeg and inserts no helper rows. Left out or `true`, helpers are on. Set it on every worker: a worker with it on still asks for help, and every worker still runs helper jobs other workers asked for; a play that two workers hold together (below) is admitted only where the worker that runs its job asks for helpers. The server no longer holds room back for a viewer who has not asked: a helper takes the cores of any worker that has them, so keep cores to spare (room for one more film, the cores of the dearest film) by sizing the workers and the autoscaler. Helpers never keep a viewer waiting, and a watched film is never taken under real time for a newcomer. A new viewer stops a helper only of a film whose own worker holds it at 1.2 times real time alone (the helper's cores are then spare); a helper of a film that its worker does not hold alone is that film's own, and a new viewer whose job would fit only by stopping it is refused within seconds with `CoresHeldByWatchedFilm`, and starts nothing. The first viewer's own seek is never refused for its own helpers, and a viewer who joins a re-encode that already runs starts no job and is never refused by this rule. The helpers a newcomer may stop give their cores back at once (those that are queued first, else the ones furthest ahead); what the helper made is kept, and the rest of its chunk is made when a viewer reaches it, which costs that viewer about what a seek does. A stopped helper's job records `a new viewer needed its slot` as its error, and a running one logs it as the reason its ffmpeg stopped. The film that is held keeps the cores of its next helper between two chunks too (a partner worker with its share free), for as long as a viewer is watching it, paused or not.

A worker counts what it can hold, in the reference machine's cores the price table is in (docs/transcoding.md), and learns it from the jobs it runs; you declare nothing. It starts from the CPUs its process may use (the CPUs `taskset` or a container limit leave it; a container limit counts as written, fractional too: a limit of 3.5 starts at 3.5, not 4), each at the reference speed, and never from a benchmark: it starts no ffmpeg of its own, at its start or later to raise or lower its figure, it registers at once, and a replacement in a rolling restart claims the job a viewer is waiting on in time. `transcodeCores` is an optional ceiling: the start is the lesser of the CPUs and `transcodeCores`, a ceiling above the CPUs is not counted as written, and what the worker learns never goes above its start (a worker with `transcodeCores` still learns below it). `transcodeSlots`, when `transcodeCores` is not set, is that many cores as before. Capacity is the price a worker keeps at 1.2 times real time, E = the sum of price x speed / 1.2 over its jobs: the i5-6500, which makes the 3.2 core job at 0.81 to 0.87 times real time, holds about 2.2 to 2.3 (computed), so that is what `transcodeCores` would be if you capped it, in the new unit. At each heartbeat while a job runs the worker takes a sample of its jobs' own speed and of the CPU its ffmpeg processes wanted (time on a CPU plus time on a run queue, from the kernel's scheduler accounting). Seven samples in a row of a worker whose CPUs its ffmpeg wanted (0.9 of them or more) and whose jobs run under 1.2x lower the figure to their mean, about 45 seconds after the first heavy job is claimed, and no running job ends for it (the viewer of that job keeps the film at the speed the worker makes it unless a second worker with room helps; see Sizing workers); three that show more raise it (any job that runs at 1.2x or more with the figure lowered raises it within three samples, a shared play's own job included, with no wait); a dead band of 10% either way moves nothing, and a figure never falls below a quarter of its start. A slow read from the media store, a slow upload, time paused at the lead, a job under 15 seconds old, an HEVC or AV1 fallback and a kernel that cannot be read count for nothing. A lowered figure that no job has tested rises to its start after 5 minutes (30 leases), and each time a job shows such a rise wrong the wait doubles, up to 7 days, and starts at 5 minutes again when a rise holds. The row, the log (`transcode capacity` at the start, with `source` assumed, ceiling or learned; `transcode capacity moved`, with the figure before and after, for a move of more than a fifth; `transcode capacity timed rise failed`, which from the second failed rise names `transcodeCores` as the ceiling that ends the retries) and `/metrics` (`jellyscale_transcode_cores`, `jellyscale_transcode_capacity_source{source}`) all give the figure that admission counts. A worker that cannot read the kernel's scheduler figures says so once at its start (`transcode capacity cannot be learned`, `jellyscale_transcode_capacity_unreadable` 1) and keeps its start figure. A capacity below the dearest row (4.2) is said once per start, in the log and on `/metrics`, and a worker refuses a play it cannot hold. A worker takes a subtitle or image-track extraction at the lowest priority, so that it takes only the cores its jobs leave; those cores are in no ledger, and a neighbour's extraction in another pod competes by the node's own weights. A re-encode's capacity counts as it is priced: two workers that each have 0.65 of a chunked re-encode's price free hold it together (one runs it, the other its helpers; 0.65 of the price is 0.78 of real time, what each of the slowest measured pair made the job at alone, D-066), where one worker with the whole price free holds it alone; the answer is the same on every replica. In a rolling update a replica of the release before counts a new worker by its slots, which are its cores rounded up, and by its cores when they are above zero, so it counts the figure a new worker learned; a new replica takes a worker of the release before as asking for helpers, as it does, so a play it shares with one that declared fewer cores than the job costs may find its helper unclaimed, which is a stall until the worker is replaced.

`trustedProxies`, a list of IP addresses or CIDR prefixes (`["10.0.0.5"]`, `["10.0.0.0/8"]`), is how the server learns which address a sign-in came from behind an ingress, for the bound per address (docs/access.md, Failed sign-ins). Declare every proxy in front of the api role. The address that counts is the peer's, unless the peer is a declared proxy: then it is the entry of `X-Forwarded-For` nearest the server (read from the right) that is not itself a declared proxy, so an entry the client sent ahead of it changes nothing, and a forwarded header from any other peer is ignored. The ingress must set or append the header (Caddy 2 replaces what a client sent with the address it was connected from, observed). A request from a declared proxy with no usable entry (no header, every entry a declared proxy, or the nearest one not an address) has no address to count: the bound per address is not applied to it, the proxy's own address is never counted, the bounds per name and per known device apply, and the first such sign-in of a process is logged as a WARN naming `trustedProxies`; each one is counted in `jellyscale_signin_unattributed_total` (no label), so alert on it rising behind an ingress. `[]` declares no proxy: the peer counts, and a forwarded header from a private or loopback peer is logged once per process as `forwarded header from an undeclared proxy`, a likely ingress that is not declared. Anything in the list that is no address or prefix stops the start naming the key, whatever the role.

Before declaring `trustedProxies`, confirm that the address counted is each client's own: a single failed sign-in writes no log line, only a refusal does, so with two devices, make 11 wrong sign-ins in a row for a name that is no account from one (the first 10 answer 401, the 11th is refused by the bound per address, and that address is refused for 15 minutes), read the `sign-in refused` line, which names the address that counts, and do it again from a second of the two devices. With the key set, the lines of the two devices must show two different addresses. If it shows one, the ingress sees every client at one address, and the bound per address would count that one address for everyone behind it: one guesser, or one viewer who mistypes ten times, would refuse everyone behind that address for 15 minutes. Leave the key out then.

In the shipped compose stack the bound per address is off, because `config.json` leaves `trustedProxies` out: the stack publishes its ingress on `127.0.0.1` only, so Docker hands every client on the host to it from the bridge gateway's address, and declaring the ingress would count that one address for all of them. The bounds per name and per known device hold there. With the key left out in any deployment the bound per address is off, every api process logs a warning naming `trustedProxies` at each start and `jellyscale_signin_address_bound` is 0. `compose.yaml` carries the key commented out, with when to declare it.

What a `sign-in refused` line holds depends on whether an address was counted for the request. When one was (the peer's, or the client's behind a declared proxy), the line has `address`, and `user` only for a name that is an account (never an unknown name's text, which viewers may have typed a password into). When none was (`trustedProxies` absent, or a declared proxy with no usable forwarded entry), the line has `peer`, the connection's address, and no `address`, and `forwarded_unverified`, the `X-Forwarded-For` header as received, escaped and cut to 256 bytes, absent when none came. That header is the peer's word: it never counts toward a bound, refuses anyone or labels a metric.

In the shipped compose stack the `sign-in refused` line identifies the account and the bound but not the client: `peer` is the ingress container's address and the forwarded value is the Docker bridge gateway's (observed in the stack test), the same for every viewer, so neither is the client. The peer's address is every viewer's and must never be blocked, banned or firewalled on the strength of that line; the client's address is known only to whatever stands in front of the stack (a reverse proxy or router with its own log), so correlate the time and account there.

A declared ingress must keep an address across its container being recreated: give it a fixed address in its network (compose `ipv4_address`), or declare the network's prefix (`["172.28.0.0/16"]`) instead of one address; `compose.yaml` points here. A server with no ingress declares `"trustedProxies": []`, so that the peer counts as the client and the start-up warning stops: a server with no ingress and the key absent logs the warning at every start. Viewers behind one household NAT share one counted address, so ten wrong passwords among them refuse that address for 15 minutes. An `X-Forwarded-For` entry must be a bare address: one written with a port or in brackets is unusable, and the per-address bound is not applied to that request.

`databaseMaxConns` sets the most Postgres connections the process opens for its queries, shared by every role in it. Left out or `0`, it is 16; a negative value, 1 (the hint listener keeps one connection, so 1 leaves none for queries) or more than 10000 is refused at start. The default holds about 800 viewers' traffic in one process; a pool of 4 (pgx's own default on a host with 4 CPUs or fewer, as the dogfood's: pgx uses the larger of 4 and the CPU count) queued every call at 400 (ARCHITECTURE.md, Control-plane ceiling), and 64 held 1600. Each worker also holds two more connections outside the pool, one for its liveness lock and one for its lease keeper (held while it has a job), and each running scan, segment sweep or asset sweep pass one more for its advisory lock (a sweep pass holds one for all it deletes), so Postgres's `max_connections` must cover every process's pool plus two for each worker and one for each of those running: a stock server's 100 is reached at about 45 busy workers, or 90 idle ones.

`--liveness-database-url`, a flag of the worker and not a config key (it carries a credential, so give it as you give the main URL: it is in the process's arguments), gives a worker's liveness lock and its lease keeper a Postgres URL of their own. Every other statement of the worker (claims, looks at the dead, registration, job rows, hints, scans, sweeps, migrations) uses `JELLYSCALE_DATABASE_URL`. Without the flag the lock and the keeper use that URL as before, and an `api` or `stream` process given it starts and opens no connection to it. A value that is not a `postgres://` or `postgresql://` URL stops the start with an error naming the flag, before anything is written to Postgres; a URL that parses and refuses connections stops nothing: the worker logs `taking the worker's liveness lock failed` with the reason, claims no job, tries again every second and takes jobs once it connects. The liveness URL must be a direct, session-mode connection to Postgres: a session advisory lock belongs to the server connection that took it. Behind a pooler in transaction mode the worker logs that Postgres does not show its lock, naming `--liveness-database-url`, or, where the pooler keeps the lock on a server connection after the worker is gone (pgbouncer 1.26.1 does), a worker killed behind a transaction-mode liveness URL is not noticed and its jobs wait their lease (10 seconds) as when a host loses power. The main URL may then sit behind a pooler in session mode (every role works with it, observed with pgbouncer) or be direct; a pooler in transaction or statement mode breaks it, because the hint listener's LISTEN and the advisory locks of the migrations, scans and sweeps, taken in one statement and released in another, belong to whichever server connection the pooler chose, so hints are lost and a lock can be held for good or by two replicas at once. N workers cost Postgres 2N direct connections (the lock's and the keeper's, the keeper's held while the worker has a job), which a pooler does not carry: `max_connections` must cover them and the pooler's own server connections. A running scan, segment sweep or asset sweep pass holds one more connection for its advisory locks, which goes to the main URL and so through a session-mode pooler like the pool's.

A Postgres switchover or restart, which takes seconds, is survived without interrupting playback; a transcode goes on through any outage shorter than 6 seconds, and through one of up to 9 seconds that begins just after its lease was renewed (every 3 seconds), and after a longer one the viewer's next request for a segment not yet stored starts the job again where it stopped; a longer outage keeps direct play and stored segments going, while a transcode stops once its stored segments run out and subtitles not yet fetched wait. Every replica logs `Postgres is away` and later `Postgres is back`, requests that need the database wait for it (up to 90 seconds for a segment) rather than answer an error, except that some requests are still answered 500 during a switchover and a subtitle that was refused after a read that hit the outage stays refused for 30 seconds (a gap that JS-146 closes, `docs/status.md`), and that direct play and segments already in the transcode store go on: every stream replica keeps a snapshot, refreshed every 5 seconds, of the tokens of sessions seen within a window of 10 minutes (a film paused in a background tab is still served), and serves those tokens from it while Postgres is away, whichever replica the viewer used before: byte ranges of the film, stored segments, and the subtitle tracks and fonts the asset store holds (a token signed out after the last refresh stays usable until Postgres is back, and a tab closed without a Stopped stays served for the window; a new job, a login and everything else wait). At 1000 sessions in the window a refresh reads about 250 KB and a replica holds about 300 KB. A film just started is in the snapshot within milliseconds, because the api replica notifies the stream replicas of a start, so the gap that remains for a film started less than 1 second before the outage is under 1 second, and closing it costs, per start, one notification and one small query of the session and its film on each stream replica, workers keep their transcodes and store the segments they made once it answers, and `GET /healthz` answers from the process alone, so a liveness probe on it does not restart every pod together. `GET /readyz` stays 200 for the first 30 seconds of one unbroken outage and then answers 503 on the replicas that cannot reach Postgres, and is 200 again within seconds of it answering, with no restart; requests already waiting go on waiting. Run the database with synchronous replication (CNPG `synchronous` settings): a switchover to a replica that lacks the last committed rows can lose a worker's `next_segment` or its `transcode_nodes` row, which the worker answers by stopping its jobs and starting over, so playback stalls for a few seconds.

## A viewer's track preferences

A viewer's track preferences (`/jellyscale/v1/track-preferences`, docs/api.md) are one jsonb document in `users.track_preferences`, apart from the 16 settings of `users.configuration`. A viewer who has never changed them has NULL and is answered the defaults; their first change stores the whole document. To read one viewer's (names match without regard to case, as a login does):

```sql
SELECT name, track_preferences FROM users WHERE lower(name) = lower('<viewer name>');
```

## Sizing workers

A worker learns what it holds (Configuration), so most of sizing is giving it CPUs it can count on.

- **Requests equal limits, in whole cores.** Give a worker pod a CPU request equal to its limit, a whole number of cores. A limit above the request lets the kernel throttle the pod when its neighbours are busy, which the worker meets as a slow CPU it cannot plan for, and a fractional limit is counted as written but throttles in periods a heavy job feels.
- **The CPUs measured so far.** The price rows are in cores of the reference machine (a Ryzen 7 7800X3D). A worker held to 2 CPUs by a limit made the 4K HDR job (3.2) at 0.88 times real time, so it holds about 2.35 of them; on the same worker the 1080p SDR row (0.8) ran at 3.3 times, 4K SDR (1.6) at 1.9, 1080p HDR (2.0) at 1.2 to 1.3 (docs/transcoding.md has the table). The i5-6500 holds about 2.2 to 2.3. A figure learned on the 3.2 row predicted the speeds of the other x264 rows within 10% on that worker; the HEVC fallback row ran 33% to 52% faster than its price says, which a learned figure refuses or shares on the safe side.
- **Refusals for short cores.** A play refused with `cores are short` in the log and the dialog "cannot be played at this time" means no worker has the job's price free: add workers, or CPUs to the ones you have. The log line and the decision line give the job's cost and the capacity of each worker as learned. A worker that learned a low figure from a neighbour's burst rises again by itself, in a few seconds once a job shows it holds more, and by time after 5 minutes at the longest.
- **Slow jobs that got no helper.** `jellyscale_transcode_unhelped_jobs_total{reason,capacity}` counts re-encodes that ran under 1.2 times real time and got no helper, once each: `lone_worker` and `no_room` mean no second worker had room, `helpers_off` is `transcodeHelpers: false`. A count that grows is a film that stalled or nearly did: add a worker with room, or CPUs.
- **A whole node for a 4K-capable worker.** The 4K HDR job costs 3.2 reference cores and the AV1 fallback of one 4.2: a worker that is to hold one alone needs about 4 to 5 CPUs of a current core, more of a slower one, and it holds its job best with the node's CPUs to itself. Two smaller workers share it (each needs 2.08 free), at the cost of a helper's restarts at each chunk. A CPU limit counts as written, so a worker limited to 2 CPUs counts 2.0, under the 2.08 it needs: give a worker that is to share a 4K film a limit of 3 or more (a faster CPU than the reference one is still counted at the reference speed, so its learned figure never rises above its start).
- **What learning cannot see.**
  - The worker's own extractions beside a transcode (a PGS copy, chapter pictures, a probe): a sample taken while one runs, and for 10 seconds after, never moves a figure the worker learned, because the job is slower for a reason that is not the CPU's capacity. On a synthetic 4K HDR film under a CPU limit of 2, the job ran 16% to 18% slower for as long as the extraction ran (0.88x to 0.73x for 24 to 28 s from a local disk), and in the dogfood's one sighting 0.85x fell to about 0.6x. A whole-film read from a network store runs minutes, up to the hour, once per file version, and a chapter backlog runs for hours: for all of that time a worker that has not yet learned may still be lowered beside the extraction, but one that has does not move. A second worker with room keeps such a play at real time (a job under 1.2x asks for a helper, and one under 1.0x beside an extraction is counted under `own_extraction`, once for each job, and logged); a lone worker has none, and the film can run under real time and freeze while the extraction lasts (docs/status.md, Known gaps; D-070; JS-141 plans to close it).
  - Contention the kernel does not show: a noisy neighbour on shared memory bandwidth, a hypervisor that steals time, a network mount that is slow for everyone. These slow a job without its ffmpeg waiting on a run queue, so the worker reads it as not the CPU and keeps its figure.
- **What the first heavy play, and a lone slow worker's timed rise, cost a viewer.** The figure is lowered about 45 seconds after the first heavy job is claimed, but that is when the figure falls, not when the film recovers: lowering ends no running job, so the viewer who was admitted above what the worker holds gets the film at the speed the worker makes it (0.85 times real time on the i5-class, a stall in the player) until they leave. The same is true of the first heavy play after each worker start (a restart relearns from its processors until JS-178 keeps the figure) and of the play admitted at a timed rise. A second worker with room changes this: the slow job asks for a helper (once the job has run 2 seconds under 1.2x, or, where the second worker has only 0.65 of the price free, once the figure has fallen and the next heartbeat has asked), and the play is real time again about 50 seconds after the claim (computed from the design, not measured on two workers); a lone worker has no helper, and no one else gets the 4K play meanwhile. A lone worker that was lowered refuses a play it cannot hold, within seconds, for 5 minutes; then the timed rise returns it to its start and one play is admitted above what it holds. The wait doubles each time a job shows such a rise wrong, so the first day admits at most 8 such plays (5, 10, 20 ... 640 minutes), and a week at most. Set `transcodeCores` to the figure the worker holds to end the retries: it is then the start, and a rise never takes the worker above it.
- **`transcodeCores` is an optional ceiling in the new unit** (the price kept at 1.2 times real time; for the i5-6500 about 2.2 to 2.3, not the 2.7 of the earlier unit): leave it out unless a worker shares its host with work you do not want it to count on. A legacy `transcodeSlots` is not that: it counts as that many cores even above the processors (the start log line says so), so the worker starts from a figure its CPUs cannot give and learns downward from it, with a floor of a quarter of it; declare `transcodeCores`, a ceiling that is never above the CPUs, instead of a large `transcodeSlots`.

## Sizing the transcode store

The segments of a spec stay in the transcode store (`transcodeStore`, a volume or a bucket) for `transcodeRetention` after its last request, 24 hours unless you set it, and the store grows as fast as viewers start films. `transcodeBudget` (docs/transcoding.md) caps it. Both are removed by a worker's sweep, which runs once a sweep period (a minute); with many workers one of them lists the store each period, so listing costs the same with one worker as with fifty.

**What a spec costs.** A re-encode is stored at the bitrate of its quality cap: 1 Mbps for an hour is 10^6 × 3600 / 8 = 450 MB, so each hour of film costs 0.45 GB per hour for each Mbps of the cap. A copy is stored at the file's own bitrate, whatever the client's cap, because its segments are the source's own bytes. Each distinct audio track or quality is its own spec. Worked example:

- A re-encode of a 2 hour film at a cap of 6 Mbps takes 6 Mbps × 0.45 GB per hour per Mbps = 2.7 GB per hour, 5.4 GB for the film.
- A copy of a 2 hour film whose file is 20 Mbps takes 20 Mbps × 0.45 GB per hour per Mbps = 9 GB per hour, 18 GB for the film, though the client asked for 6 Mbps. (At 40 Mbps, 18 GB per hour.)

A film is stored only as far as viewers got, plus `transcodeLead` (60 seconds) ahead of the furthest of them, so these are what a viewer who watches it all costs.

**Picking a budget.** Count the viewers you expect at once, and for each the film length in hours times the per-hour figure of the stream they get; that is what is being watched, and the budget must hold it with room, because the budget never removes a spec that is being watched. A spec is watched while it has a queued or running job (a helper's too), or a viewer who has not stopped has asked for it within the last 10 minutes, which is how long a paused film is still served. With 10 viewers each on a different 2 hour film at 6 Mbps, that is 10 × 5.4 GB = 54 GB; a budget of 100GB leaves the rest for the specs of viewers who have left, which stay, least recently requested going first, so that one who comes back to resume finds what they made. Beyond that, a bigger budget keeps resumes and second viewings cheap, and a smaller one costs encoding.

**What the budget does and does not promise.** Over its budget, a sweep removes whole specs (the init segment and every segment), least recently requested first, and only as many as bring the store to or under it. A spec with no viewer row counts as the least recently requested. A viewer who asks for a spec being removed is served by a job the request starts. The store can go over the budget by what is being watched plus one sweep period of writes: segments written between two sweeps are not seen until the next, and what is watched is never removed. When the watched specs alone are over the budget the store stays over it and the log says so ("the transcode store is over its budget"). Watch `jellyscale_transcode_store_bytes` against `transcodeBudget`; a store above it for more than a few sweep periods is under more load than the budget allows.

**What each sweep removes and keeps.**

- Segments, by age: a spec nobody has asked for in `transcodeRetention` goes, with its viewers' rows. By budget: as above. Neither removes a spec with a queued or running job.
- Assets, in each library's asset store, once every 10 sweep periods: the subtitle text, `.sup` copies, stored image tracks (`subtitles/{source}/{hash}/{index}.mkv`, JS-089), primary image, fonts manifest and chapter pictures of a file that was removed (its item deleted after `missingGrace`) and of the previous version of a changed file (a new ETag), and the old text of a subtitle file beside the film that was edited. It keeps every asset of each source's current version, and everything of a file hidden as missing inside `missingGrace`, so its artwork and tracks are there when the file returns. A font stays while the fonts manifest of any remaining version names it, so a font a removed film and a kept film share stays; a font no manifest names goes. Two libraries that share an asset store keep each other's assets.
- The asset sweep leaves alone what something is writing: the assets of a film with a queued or running subtitle, `.sup`, image track extraction, fonts or chapter-picture job, every font while a fonts job runs, and the images of a library while one of its scans runs (the scan puts an image before it commits the item's key). It removes only objects of the shapes above, so a file of your own in the asset store is never touched, but it lists the whole store, so give the assets a location of their own, not your media's. A sweep that cannot read Postgres, or whose listing of a store fails, removes nothing from that store and logs why; each sweep logs how many objects of each kind it removed.
- Image tracks (JS-089, decision D-003): the first play that burns a film's image track has a worker read the film once per file version, its whole size from the media store (egress on S3, also when the viewer stops early); watch it with `jellyscale_extraction_jobs_running{kind="image_tracks"}` and the `image track extraction started` and `ended` log lines. A track the film can't give is recorded, and the film is not read again for it until the file changes. A worker runs at most 2 such extractions at a time, on slots of their own that a viewer's subtitle never waits behind. The read has the extraction time limit of one hour, which is not configurable (decision D-002), so a film needs a read speed of its size over one hour (40 GB, about 11 MB/s). A film that takes longer is logged at Error as `image track extraction ran out of time`, with the item, the source, the reason (the time limit) and `retry_not_before`, the earliest time a play may try again, and is then not read again on every play: the failure is kept as the film's own until the daily sweep of finished jobs (24 hours) or until the file changes, so a plain slow film costs one hour-long read a day, started only by a play of it (never by a timer over the library), not one for each seek. Viewers of that film are not stopped and are not told: a seek into a cue shown a long time ago costs film reads, as JS-071 draws it (docs/subtitles.md). To store its track, give the worker a faster path to the film. Any other failure (a store that did not answer, a stopped worker) is tried again at the next play after 30 seconds.

## Metrics

Set `metricsListen` in the config (for example `":9090"`) and every role in the process serves Prometheus text exposition at `/metrics` on that address, on a listener of its own: the public port never has `/metrics`, so the ingress cannot reach it. Left out or empty, nothing listens. A worker-only process serves it too. There is no authentication, so bind it to an address only the operator's network reaches (`127.0.0.1:9090`, or a pod port no Service or Ingress exposes). Nothing in it carries a title or a file path.

To read it from a pod without a Prometheus server, forward the port of a pod and not of the Deployment:

```sh
kubectl -n media get pods -o wide
kubectl -n media port-forward pod/<pod> 9090:9090 &
curl -s localhost:9090/metrics | grep ^jellyscale_
```

Each pod serves only its own process. A transcode job, its speed, paused state, cores and its `jobs_running` exist only on the worker pod that runs it, and `deploy/...` forwards to one arbitrary pod, so with several workers it may show every core idle while the job you want runs on another. Find the pod with the job: `psql -c "select id, worker from transcode_jobs where state = 'running'"` gives the worker's ID, which is `<pid>-<start time in nanoseconds>` and not the pod's name. A worker logs `worker started worker=<id> host=<hostname>` when it starts (the hostname of a pod is its name), so `kubectl logs` of each worker pod, searched for that ID, finds the pod. Segment waits are on the stream pod that served the request, and scans on the worker that won the library's lock; queue depth is the same on every worker.

Every metric starts with `jellyscale_`, and the Go runtime and process metrics (`go_*`, `process_*`) come with it.

## Why a film plays as it does

Each api process writes one line at Info for each source a PlaybackInfo answer lists, with the message `playback decision`; an answer that lists two sources writes two lines, and one that names a source writes one. An answer that is refused (no source, `ErrorCode` `RateLimitExceeded`) writes one line, `method=refused`, for the source refused and for no other. A request that gets no answer (a bad body, a bad token, an unknown item, a database failure) writes none. The line says how the source plays, in the counters' words: `method=direct_play`, `copy` (the video as it is, whatever the audio and container need) or `reencode` (H.264 SDR). Its keys:

- `reasons`: every reason of the decision, comma separated, from the list below. A copy, a re-encode and a refusal always have some; a refusal has exactly one. A direct play has none, unless it gave up a transcode: then `asked` is `copy` or `reencode`, `asked_reasons` are the reasons of the transcode that was asked, and `reasons` is why none was given.
- `client`, `client_version`, `device`, `device_id`, `user` (the account's id, as the other api lines print it), `item` and `source` (a dashed lower case id whatever form the request used) and `play_session`, which is the answer's `PlaySessionId` and the same on every later line of that play.
- `out_codec`, `out_height`, `out_range` and `src_height` (copy and re-encode): what the viewer gets and the file's height. A copy is the file's own codec and height, in the range it sends (a Dolby Vision file as its base layer); a re-encode is `h264`, `SDR`, at most 1080 lines. `tone_mapped=yes` when the encode maps an HDR picture to SDR, and `ceiling_lowered=yes` when the 1080 line ceiling made the picture smaller than the same request would have got without it.
- `src_range` and `src_dv_profile`: the file's range and its Dolby Vision profile, where the row was read.
- `audio_asked` (the index the request gave, or `none`), `audio_index`, `audio_codec`, `audio_language` (the track that plays) and `audio_by`: `client` if the request named that track, `server` if it named none or named an index that is no audio track, so the file's default or the viewer's saved language chose it.
- `subtitle_asked` (as given, `-1` included, or `none`) and what plays: `subtitle_index`, `subtitle_codec`, `subtitle_language` and `subtitle_kind` (`text` or `image`), `none` for `-1`, for a track that is no subtitle track, or for a mode that chose none. A track the viewer's saved subtitle mode and language chose is named as it plays while `subtitle_asked` stays `none`, so the line tells the server's choice from the client's (JS-041).
- `admitted`, `cost` and `capacities` (a copy or re-encode that starts a new job): `admitted=one_worker` when one worker holds the job alone, `admitted=shared` when no worker holds it alone and two hold it together with helpers; `cost` is the job's price in reference cores, and `capacities` the capacity of the worker it was admitted on, or of both, comma separated (reference cores, docs/transcoding.md). A play that joins a job already running has none of these.
- `cost` and `most_capacity` (a refusal for cores): the job's price and the largest capacity any worker had, both in reference cores. A refusal decided before any worker was counted (no worker, a remembered failure) has neither.

A line never holds a title, a file name or a path. To find why one viewer's film was re-encoded, search the api logs for the play session id (the `PlaySessionId` of the answer, which the TranscodingUrl carries too): `grep 'playback decision' | grep play_session=<id>`. To find the decisions for a film, search for `item=<id>`. The ids are printed dashed and lower case. To get from an item id as the line prints it to the film, ask Postgres: `select name, type from items where id = '<item>'`.

The counters say how often. Re-encodes by reason over the last day, summed over the api replicas:

```
sum by (reason) (increase(jellyscale_playbackinfo_decision_reasons_total{method="reencode"}[1d]))
```

The reasons are Jellyfin's names where Jellyfin has one (the `TranscodeReasons` of its API) and jellyscale's own where it has none. A name is spelled the same in the line, in the counters' `reason` label and in a TranscodingUrl's `TranscodeReasons`, and every name in a source's `TranscodeReasons` (and in `GET /Sessions`) is in its line. A reason only the line and the counters hold, such as `KeyframeIndexUnusable` or the track pick, never reaches a client.

Why the client's profile or the request does not allow the file as it is:

- `ContainerNotSupported`: the client's profile does not list the file's container.
- `VideoCodecNotSupported`: the profile does not list the video codec, or the codec is one jellyscale never copies (anything but H.264, HEVC and AV1), so the video is re-encoded.
- `AudioCodecNotSupported`: the profile does not list the audio codec of the track that plays.
- `SubtitleCodecNotSupported`: a subtitle is drawn into the picture, which takes a re-encode; for an image track and for a text track.
- `SecondaryAudioNotSupported`: the track that plays is not the file's default, and the client's profile cannot pick it itself.
- `VideoProfileNotSupported`: the client refuses the video's profile, or its profile cannot be named for the playlist (for example HEVC other than Main and Main 10).
- `VideoLevelNotSupported`: the video's level is over what the client's profile allows.
- `VideoResolutionNotSupported`: the picture's width or height is over what the client's profile allows.
- `InterlacedVideoNotSupported`: the video is interlaced and the client's profile does not allow it.
- `AudioChannelsNotSupported`: the track has more channels than the client's profile allows.
- `ContainerBitrateExceedsLimit`: the file's bitrate is over the cap, whether the client profile's or the request's `MaxStreamingBitrate`.
- `VideoRangeTypeNotSupported`: the client's profile does not list the file's range (HDR10, HDR10+, HLG or Dolby Vision); `src_range` and `src_dv_profile` say which.

Why the video is not sent as it is, which only jellyscale names:

- `KeyframeIndexUnusable`: the video is in a codec that is copied (H.264, HEVC, AV1) but the file has no keyframe index, or its keyframes are too far apart to cut segments on.
- `BitrateUnknownUnderCap`: a cap applies and the file does not say its bitrate, so nothing shows that a copy fits it.
- `VideoRangeNotCopyable`: the range cannot be copied: H.264 in HDR, or Dolby Vision profile 5.
- `VideoRangeUnknown`: the file's range has not been scanned yet; a rescan fills it in.

Why a transcode was refused (a refused line carries exactly one of these), or, on a direct play line, why none was given:

- `NoWorkerRunning`: no transcode worker is running.
- `NoWorkerWithFreeCores`: workers run, but none has the cores free that the job costs.
- `CoresHeldByWatchedFilm`: a film another viewer is watching holds the cores this play needs: it runs on helpers of more than one worker, and the newcomer would fit only by stopping them, which would take that viewer under real time. Room for one more film, kept by sizing the workers or by the autoscaler, avoids it. It is counted apart from `NoWorkerWithFreeCores` because it is not a lack of cores in the cluster but cores that are held.
- `TranscodeStoreMismatch`: the running processes have different `transcodeStore` settings, so they cannot share segments.
- `RememberedFailure`: the same transcode failed a moment ago, and is not offered again until the failure is forgotten; the log's own lines, not the decision line, say what failed.
- `WorkersAtCopyBound`: every worker already holds as many copies as it takes.
- `NoWorkerOfThisOutputVersion`: a track other than the file's default was asked, and no worker of this release's output version runs transcodes (see the rolling update).
- `NoTranscodeStore`: a track pick or a transcode was asked and no `transcodeStore` is set, so transcoding is off.
- `NoProbedDuration`: the film has no probed duration, so it can be neither copied nor transcoded.
