# Running jellyscale

## Roles

One binary, chosen with `--roles`:

| Role | Serves |
|---|---|
| `api` | REST API, WebSocket |
| `stream` | Images, direct-play media, file downloads, HLS playlists and segments, subtitles, the encoding configuration |
| `worker` | Library scans, transcodes, subtitle extraction |

`--roles=all` runs everything in one process. Paths under `/Videos/`, `/Items/*/Images/` and `/Items/*/Download`, and `/Playback/BitrateTest` and `/System/Configuration/encoding` (case-insensitive), belong on `stream`, and everything else on `api`. [`deploy/compose/Caddyfile`](../deploy/compose/Caddyfile) and `test/e2e/router.mjs` do this. An ingress written before `/System/Configuration/encoding` moved to `stream` (so that it is answered while Postgres is away) must add it: an `api` replica answers it 404, and jellyfin-web then draws no ASS subtitles.

## Run

```sh
docker create --name jf jellyfin/jellyfin:12.4
docker cp jf:/jellyfin/jellyfin-web web-dist && docker rm -v jf

MEDIA_DIR=/path/to/media JELLYSCALE_ADMIN_PASSWORD=change-me \
  docker compose -f deploy/compose/compose.yaml up --build
```

`MEDIA_DIR` needs `movies/` and `shows/` folders. Segments are kept in the `transcode` volume. Open http://127.0.0.1:8096/web/ and sign in as `admin`. The stack's Caddy ingress sends media and images to `stream` and the rest to `api`. Libraries on S3 need `JELLYSCALE_S3_ACCESS_KEY` and `JELLYSCALE_S3_SECRET_KEY` exported on the host; compose passes them to every service. Add one to `deploy/compose/config.json` such as `{"name": "Cloud", "kind": "movies", "media": "s3://bucket/movies?endpoint=https://s3.example.com", "assets": "s3://bucket/assets?endpoint=https://s3.example.com"}`. For a single process, run `--roles=all`.

A client's tests that want a server with a small known library, started with one Compose file and no setup, use the published fixtures image: [Testing a client](client-testing.md).

## Rolling update

Replace the `stream` replicas first, then the `api` replicas. An `api` replica of this release offers a copy of HDR10, HDR10+ and HLG video, and a `stream` replica of the previous release refuses that copy, so a viewer who is sent to it fails to play. A new `stream` replica serves every copy the previous `api` offered, so it is safe to be first.

Every job records the output version of the replica that queued it, and a worker claims only jobs of the version it makes, so an upgrade must keep a running worker for every version a running replica queues. To upgrade, start the new workers first, then replace `stream`, then `api`, and stop the old workers last, so that at each step every version a running replica queues has a running worker that makes it. To roll back, start the old workers first, then put the old `api` back, then the old `stream`, and stop the new workers last, again with a worker for each version at every step: the old `stream` must never run while no worker of the old version does. When a release does not change the output version, the order matters only for the HDR10 rule above, and for a job kind the old workers don't know: JS-089 adds the subtitle job kind `images` (a film's image tracks, stored in the asset store) without changing the output version, so for that release roll the workers first, as DOMAINS 51 says. A worker of the release before claims an `images` job as a subtitle track, fails it (`subtitle extraction failed`, `the source file has changed or is gone`, logged at Error) and the next play after 30 seconds queues it again, so while old workers run, the film's track is stored by a new worker or not at all, and viewers meanwhile have a burnt cue drawn as JS-071 did, with no wait. JS-088 raises it from 4 to 5 because a worker from before it cannot make the copy-fallback `Recode` layout. That changes every spec hash: segments and running jobs of version 4 are not reused by version 5, so playback is encoded again as it is asked for; old workers must stay until their version 4 jobs end, and the old objects remain in the store until the ordinary 24 hour retention sweep.

Rolling back across the liveness changes of JS-030: a worker of the release before stops at start on `--liveness-database-url` (`flag provided but not defined`) and takes its lock and renews its leases through `JELLYSCALE_DATABASE_URL`. Remove the flag from the worker, and make `JELLYSCALE_DATABASE_URL` a direct, session-mode URL again if a pooler was put in front of it because the flag sent the lock around it, before such a worker starts. Workers and replicas roll in any order for this change (none is needed: a replica ignores the flag, and the output-version order above is the only one); for a roll forward, start the new workers with the flag once the pooled URL is in place. A fleet of both releases meanwhile works: the workers of the release before each still look for the dead, beside the one reaper of the new, so a dead worker of either release is forgotten on the same conditions and no live worker of either release is forgotten. A subtitle row of a worker that an old worker forgot waits out its full lease as before (only the new reaper cuts it), and a worker from before the liveness lock (a row that took no lock) is never forgotten and is taken over at its lease.

When that order is not kept, a viewer whose job no running worker of its version takes waits `queueTimeout` (6 seconds) and no less, then gets a 503 with `Retry-After`, and the server log says that only workers of another output version run. Segments made by another version are never served under a spec of this one. A worker built before this release makes no such check, since it claims any queued job, so every such worker must be stopped before a replica of a later output version starts.

## Replicas, readiness and the ingress

Run two or more replicas of `api` and of `stream` behind the ingress. Two routes tell it about each one, and neither needs a token:

- `GET /healthz` is liveness: it answers 2xx from the process alone, through a drain and through any Postgres outage, so a liveness probe never restarts every pod together.
- `GET /readyz` is readiness: 200 while the replica takes requests, 503 from the moment it is told to stop, and 503 when it has been cut off from Postgres for 30 seconds without a break. Outages that are shorter, or that add up to more than 30 seconds, never fail it, so a switchover does not take every replica out of service.

What any ingress must do, and the shipped [Caddyfile](../deploy/compose/Caddyfile) does with two replicas of each role listed one by one:

- Poll `/readyz` of every replica at an interval of 2 seconds or less. A polling interval is the time a router needs to notice, and lead below is longer than it.
- Stop sending to a replica that answers 503, and to one that does not answer: a refused connection means the process is gone.
- Retry a GET or HEAD that failed before its response header (a connection refused or reset) on another replica, so that a replica killed between two polls costs a viewer no segment. A film that has begun freezes on one failed segment.
- Keep one upstream per replica. A name that resolves to several replicas is one upstream to Caddy's health check, and one draining replica would take the whole role out.
- When no replica of a role is ready, which happens when Postgres has been away from every one of them for more than 30 seconds, send to all of them anyway if the ingress can: requests wait for Postgres on every replica (a segment up to 90 seconds) and are answered when it is back, where a 503 from the ingress stops the film. Caddy's active health check has no such fallback and answers 503 itself, so the shipped Caddyfile adds one in `handle_errors`: when a block finds no ready replica it sends the request to every replica of the role, ignoring `/readyz` (and a viewer then waits about a second longer for the 503 to be given up on). A Kubernetes Service with `publishNotReadyAddresses: true` sends to every pod but then ignores readiness in a drain too, so only an ingress that fails open when none is ready gives both.

`shutdownGrace` is how long a replica that gets SIGTERM takes to stop, as a Go duration, counted from the signal; left out it is `30s`, and a value that is not a duration or is negative stops the start, naming the key. On SIGTERM `/readyz` answers 503 at once and the replica goes on taking and answering new requests for a lead of 5 seconds, so that a router that polls every second or two has stopped sending before any request is refused (a `shutdownGrace` below 5 seconds shortens it). It then closes its WebSockets, with a close frame and their rows removed, so clients reconnect to another replica, and stops accepting connections. A response in flight, such as a segment waiting on its job or a direct-play range, is sent whole if it ends within the grace, and the process then exits by itself; one that outlasts the grace is cut at its end and the process exits within seconds of it, so a slow or hung client never holds a replica. Set the pod's termination grace period (`terminationGracePeriodSeconds`) above `shutdownGrace`, 40 seconds for the default, or the pod is killed in the middle of the drain. A viewer on a replica that is killed rather than stopped reconnects the WebSocket to another replica, and the killed replica's claim on a device is gone within seconds, without the device having to reconnect.

## Memory of the stream role

A `stream` replica sends a segment while it reads it from the store, 32 KiB at a time, so its memory is a fixed base plus a figure per viewer: a base of 64 MiB (the Go runtime, the snapshot of sessions and the connection pools) and 1 MiB per concurrent viewer of Go heap, the most the memory test allows. The figure does not grow with the film's bitrate or the segment's length: a 4K copy segment of tens of MB costs a viewer the same as a 2 MB one. The heap is not all a viewer costs: a viewer who stops reading leaves the bytes already written in the kernel's send buffer of its connection, bounded by `tcp_wmem` (about 4 MiB), and on an S3 store the store connection's receive queue (`tcp_rmem`) holds some more, which comes on top of the heap and counts toward a pod's limit, not its heap. For requests and limits, take the base, plus the heap figure and the send buffer for each viewer the replica is to carry.

## Configuration

A process started without `--config` runs with every key at the default, the same as a config of `{}`: `name` is `jellyscale`, `adminUser` is empty (no account is created), `webDir` is empty (no web client is served), and `scanInterval`, how often a worker scans its libraries, is `15m`; a value that is not a positive duration stops the start naming the key, whatever the role, before anything is written to Postgres. The other keys are at the defaults named below and in docs/transcoding.md, and the drain is as in "Rolling update". `--roles` takes `api`, `stream`, `worker`, a comma-separated list of them, or `all`; an empty, unknown or repeated role, or `all` in a list, stops the start naming it.

A key the server does not know, at the top of the config or in a library, is refused at startup with its name, so a misspelt `chapterImages` can't silently leave the option off; so is anything after the config. Upgrading: a config that loaded before because the server ignored a stray key now stops the start, naming the key to remove.

A library whose POSIX media folder is missing fails its scan with an error naming the folder, and so does one whose media store lists no video at all while the library has films (an empty mount point, a volume unmounted under a folder that is still there, or an empty bucket): the films and their watch state are kept, the log says why, and the next scan after the volume is back carries on as before. The cost is that a library emptied on purpose keeps its last films listed until a video is in it again.

A film or episode whose file a scan no longer lists is hidden, not deleted: viewers see what they would if it were gone, but its item, media source and every viewer's position, played flag and favourite stay in the database. A file that is listed again inside the grace, at its old key or moved or copied to another (matched by its size and ETag, or by its size and what the probe finds in it), is shown again as the same item. `missingGrace`, a Go duration such as `72h`, is how long that grace is; left out it is `168h` (seven days), and a value that is not a duration or is negative stops the start, naming the key. The grace is counted by Postgres's clock from the first scan that missed the file and kept in the database, so it holds across scans, workers and restarts. The first scan after it has passed removes the item with its watch state, and then any season or series left with no episode; a file that returns after that is a new item.

`maxLostShare`, a number from 0 to 1 (left out, `0.2`), is the most of a library's stored files a scan may find missing. A scan that would lose more fails, like the empty-mount case above, with an error that names the library, how many files are lost and how many are stored; it hides and removes nothing (not even an item whose grace has passed), `jellyscale_scan_last_success` is 0 for the library, and every later scan fails the same way until the files are back, when the first one succeeds with every item and watch state as before. A file moved to another key and matched to its item is not lost, and the files already hidden count, so several small losses can't add up unseen. After removing that many files on purpose (more than the share of a library), set `maxLostShare` to `1` for one scan, or higher than the share you are removing, and set it back.

A library is identified by its media store and kind, not only by its name: a config that changes only a library's `name` leaves one library with the same id, items and watch state, and the new name in the views. A library that is new to the database gets the hash of its name as its id, which is what every library has had, so an upgrade keeps all ids. A library left out of config is hidden with its items (it is gone from the views, and its items from every listing) and is removed, with its items and everyone's watch state, by the first worker tick after `missingGrace` has passed since the first worker start without it; putting it back in config before then shows it again with its id and everything in it. A worker removes libraries on every scan tick, so no restart is needed. Every worker must list the same libraries: a worker whose list leaves a library out hides it from every viewer and starts its grace, whatever the other workers list. The `libraries` of api and stream replicas are not read (a bad entry there stops only a worker), and a worker listing none hides and removes nothing, so emptying the list does not remove the last library. A library's grace runs from the first worker start without it, no longer from any start.

`transcodeHelpers` set to `false` stops this worker's slow transcodes from asking other workers to help (parallel transcoding): a slow job is then one ffmpeg and inserts no helper rows. Left out or `true`, helpers are on. Set it on every worker: a worker with it on still asks for help, and every worker still runs helper jobs other workers asked for. Helpers never keep a viewer waiting: a new viewer whose job fits no worker until helpers stop stops them (those that are queued first, else the ones furthest ahead) and they give their cores back at once. What the helper made is kept, and the rest of its chunk is made when a viewer reaches it, which costs that viewer about what a seek does. A stopped helper's job records `a new viewer needed its slot` as its error, and a running one logs it as the reason its ffmpeg stopped.

`databaseMaxConns` sets the most Postgres connections the process opens for its queries, shared by every role in it. Left out or `0`, it is 16; a negative value, 1 (the hint listener keeps one connection, so 1 leaves none for queries) or more than 10000 is refused at start. The default holds about 800 viewers' traffic in one process; a pool of 4 (pgx's own default on a host with 4 CPUs or fewer, as the dogfood's: pgx uses the larger of 4 and the CPU count) queued every call at 400 (ARCHITECTURE.md, Control-plane ceiling), and 64 held 1600. Each worker also holds two more connections outside the pool, one for its liveness lock and one for its lease keeper (held while it has a job), and each running scan, segment sweep or asset sweep pass one more for its advisory lock (a sweep pass holds one for all it deletes), so Postgres's `max_connections` must cover every process's pool plus two for each worker and one for each of those running: a stock server's 100 is reached at about 45 busy workers, or 90 idle ones.

`--liveness-database-url`, a flag of the worker and not a config key (it carries a credential, so give it as you give the main URL: it is in the process's arguments), gives a worker's liveness lock and its lease keeper a Postgres URL of their own. Every other statement of the worker (claims, looks at the dead, registration, job rows, hints, scans, sweeps, migrations) uses `JELLYSCALE_DATABASE_URL`. Without the flag the lock and the keeper use that URL as before, and an `api` or `stream` process given it starts and opens no connection to it. A value that is not a `postgres://` or `postgresql://` URL stops the start with an error naming the flag, before anything is written to Postgres; a URL that parses and refuses connections stops nothing: the worker logs `taking the worker's liveness lock failed` with the reason, claims no job, tries again every second and takes jobs once it connects. The liveness URL must be a direct, session-mode connection to Postgres: a session advisory lock belongs to the server connection that took it. Behind a pooler in transaction mode the worker logs that Postgres does not show its lock, naming `--liveness-database-url`, or, where the pooler keeps the lock on a server connection after the worker is gone (pgbouncer 1.26.1 does), a worker killed behind a transaction-mode liveness URL is not noticed and its jobs wait their lease (10 seconds) as when a host loses power. The main URL may then sit behind a pooler in session mode (every role works with it, observed with pgbouncer) or be direct; a pooler in transaction or statement mode breaks it, because the hint listener's LISTEN and the advisory locks of the migrations, scans and sweeps, taken in one statement and released in another, belong to whichever server connection the pooler chose, so hints are lost and a lock can be held for good or by two replicas at once. N workers cost Postgres 2N direct connections (the lock's and the keeper's, the keeper's held while the worker has a job), which a pooler does not carry: `max_connections` must cover them and the pooler's own server connections. A running scan, segment sweep or asset sweep pass holds one more connection for its advisory locks, which goes to the main URL and so through a session-mode pooler like the pool's.

A Postgres switchover or restart, which takes seconds, is survived without interrupting playback; a transcode goes on through any outage shorter than 6 seconds, and through one of up to 9 seconds that begins just after its lease was renewed (every 3 seconds), and after a longer one the viewer's next request for a segment not yet stored starts the job again where it stopped; a longer outage keeps direct play and stored segments going, while a transcode stops once its stored segments run out and subtitles not yet fetched wait. Every replica logs `Postgres is away` and later `Postgres is back`, requests that need the database wait for it (up to 90 seconds for a segment) rather than answer an error, except that direct play and segments already in the transcode store go on: every stream replica keeps a snapshot, refreshed every 5 seconds, of the tokens of sessions seen within a window of 10 minutes (a film paused in a background tab is still served), and serves those tokens from it while Postgres is away, whichever replica the viewer used before: byte ranges of the film, stored segments, and the subtitle tracks and fonts the asset store holds (a token signed out after the last refresh stays usable until Postgres is back, and a tab closed without a Stopped stays served for the window; a new job, a login and everything else wait). At 1000 sessions in the window a refresh reads about 250 KB and a replica holds about 300 KB. A film just started is in the snapshot within milliseconds, because the api replica notifies the stream replicas of a start, so the gap that remains for a film started less than 1 second before the outage is under 1 second, and closing it costs, per start, one notification and one small query of the session and its film on each stream replica, workers keep their transcodes and store the segments they made once it answers, and `GET /healthz` answers from the process alone, so a liveness probe on it does not restart every pod together. `GET /readyz` stays 200 for the first 30 seconds of one unbroken outage and then answers 503 on the replicas that cannot reach Postgres, and is 200 again within seconds of it answering, with no restart; requests already waiting go on waiting. Run the database with synchronous replication (CNPG `synchronous` settings): a switchover to a replica that lacks the last committed rows can lose a worker's `next_segment` or its `transcode_nodes` row, which the worker answers by stopping its jobs and starting over, so playback stalls for a few seconds.

## A viewer's track preferences

A viewer's track preferences (`/jellyscale/v1/track-preferences`, docs/api.md) are one jsonb document in `users.track_preferences`, apart from the 16 settings of `users.configuration`. A viewer who has never changed them has NULL and is answered the defaults; their first change stores the whole document. To read one viewer's (names match without regard to case, as a login does):

```sql
SELECT name, track_preferences FROM users WHERE lower(name) = lower('<viewer name>');
```

## Sizing the transcode store

The segments of a spec stay in the transcode store (`transcodeStore`, a volume or a bucket) for `transcodeRetention` after its last request, 24 hours unless you set it, and the store grows as fast as viewers start films. `transcodeBudget` (docs/transcoding.md) caps it. Both are removed by a worker's sweep, which runs once a sweep period (a minute); with many workers one of them lists the store each period, so listing costs the same with one worker as with fifty.

**What a spec costs.** A re-encode is stored at the bitrate of its quality cap: 1 Mbps for an hour is 10^6 × 3600 / 8 = 450 MB, so each hour of film costs 0.45 GB per hour for each Mbps of the cap. A copy is stored at the file's own bitrate, whatever the client's cap, because its segments are the source's own bytes. Each distinct audio track or quality is its own spec. Worked example:

- A re-encode of a 2 hour film at a cap of 6 Mbps takes 6 Mbps × 0.45 GB per hour per Mbps = 2.7 GB per hour, 5.4 GB for the film.
- A copy of a 2 hour film whose file is 20 Mbps takes 20 Mbps × 0.45 GB per hour per Mbps = 9 GB per hour, 18 GB for the film, though the client asked for 6 Mbps. (At 40 Mbps, 18 GB per hour.)

A film is stored only as far as viewers got, plus `transcodeLead` (60 seconds) ahead of the furthest of them, so these are what a viewer who watches it all costs.

**Picking a budget.** Count the viewers you expect at once, and for each the film length in hours times the per-hour figure of the stream they get; that is what is being watched, and the budget must hold it with room, because the budget never removes a spec that is being watched. A spec is watched while it has a queued or running job (a helper's too), or a viewer who has not stopped has asked for it within the last 10 minutes, which is how long a paused film is still served. With 10 viewers each on a different 2 hour film at 6 Mbps, that is 10 × 5.4 GB = 54 GB; a budget of 100GB leaves the rest for the specs of viewers who have left, which stay, least recently requested going first, so that one who comes back to resume finds what they made. Beyond that, a bigger budget keeps resumes and second viewings cheap, and a smaller one costs encoding.

**What the budget does and does not promise.** Over its budget, a sweep removes whole specs (the init segment and every segment), least recently requested first, and only as many as bring the store to or under it. A spec with no viewer row counts as the least recently requested. A viewer who asks for a spec being removed is served by a job the request starts. The store can go over the budget by what is being watched plus one sweep period of writes: segments written between two sweeps are not seen until the next, and what is watched is never removed. When the watched specs alone are over the budget the store stays over it and the log says so ("the transcode store is over its budget"). Watch `jellyscale_transcode_store_bytes` against `transcodeBudget`; a store above it for more than a few sweep periods is under more load than the budget allows.

**What each sweep removes and keeps.**

- Segments, by age: a spec nobody has asked for in `transcodeRetention` goes, with its viewers' rows. By budget: as above. Neither removes a spec with a queued or running job.
- Assets, in each library's asset store, once every 10 sweep periods: the subtitle text, `.sup` copies, stored image tracks (`subtitles/{source}/{hash}/{index}.mkv`, JS-089), primary image, fonts manifest and chapter pictures of a file that was removed (its item deleted after `missingGrace`) and of the previous version of a changed file (a new ETag), and the old text of a subtitle file beside the film that was edited. It keeps every asset of each source's current version, and everything of a file hidden as missing inside `missingGrace`, so its artwork and tracks are there when the file returns. A font stays while the fonts manifest of any remaining version names it, so a font a removed film and a kept film share stays; a font no manifest names goes. Two libraries that share an asset store keep each other's assets.
- The asset sweep leaves alone what something is writing: the assets of a film with a queued or running subtitle, `.sup`, image track extraction, fonts or chapter-picture job, every font while a fonts job runs, and the images of a library while one of its scans runs (the scan puts an image before it commits the item's key). It removes only objects of the shapes above, so a file of your own in the asset store is never touched, but it lists the whole store, so give the assets a location of their own, not your media's. A sweep that cannot read Postgres, or whose listing of a store fails, removes nothing from that store and logs why; each sweep logs how many objects of each kind it removed.
- Image tracks (JS-089): a worker reads a film once, with at most 2 such extractions at a time, on slots of their own that a viewer's subtitle never waits behind. The read has the extraction time limit of one hour, which is not configurable. A film that takes longer (a very large file on a slow store: 40 GB needs about 11 MB/s) fails with `image track extraction ended ... reading the file took longer than ...` followed by `subtitle extraction failed` in the worker's log, and is then not read again on every play: the failure is kept as the film's own until the daily sweep of finished jobs (24 hours) or until the file changes, so a plain slow film costs one hour-long read a day, not one for each seek. Viewers of that film are not stopped and are not told: a seek into a cue shown a long time ago costs film reads, as JS-071 draws it (docs/subtitles.md). To store its track, give the worker a faster path to the film. Any other failure (a store that did not answer, a stopped worker) is tried again at the next play after 30 seconds.

## Metrics

Set `metricsListen` in the config (for example `":9090"`) and every role in the process serves Prometheus text exposition at `/metrics` on that address, on a listener of its own: the public port never has `/metrics`, so the ingress cannot reach it. Left out or empty, nothing listens. A worker-only process serves it too. There is no authentication, so bind it to an address only the operator's network reaches (`127.0.0.1:9090`, or a pod port no Service or Ingress exposes). Nothing in it carries a title or a file path.

To read it from a pod without a Prometheus server, forward the port of a pod and not of the Deployment:

```sh
kubectl -n media get pods -o wide
kubectl -n media port-forward pod/<pod> 9090:9090 &
curl -s localhost:9090/metrics | grep ^jellyscale_
```

Each pod serves only its own process. A transcode job, its speed, paused state, cores and its `jobs_running` exist only on the worker pod that runs it, and `deploy/...` forwards to one arbitrary pod, so with several workers it may show every core idle while the job you want runs on another. Find the pod with the job: `psql -c "select id, worker from transcode_jobs where state = 'running'"` gives the worker's ID, which is `<pid>-<start time in nanoseconds>` and not the pod's name. A worker logs `worker started worker=<id> host=<hostname>` when it starts (the hostname of a pod is its name), so `kubectl logs` of each worker pod, searched for that ID, finds the pod. Segment waits are on the stream pod that served the request, and scans on the worker that won the library's lock; queue depth is the same on every worker.

Every metric starts with `jellyscale_`, and the Go runtime and process metrics (`go_*`, `process_*`) come with it.

| Metric | Role | Meaning |
| --- | --- | --- |
| `jellyscale_transcode_jobs_running{kind}` | worker | Jobs running, paused ones included, by `reencode` or `copy`. |
| `jellyscale_transcode_job_speed_ratio{job,kind}` | worker | Seconds of film a running job encodes per second of its own running time, over its last 10 seconds. It comes from ffmpeg's `-progress` output and leaves out the time ffmpeg is paused at its lead limit, so a healthy job that paused is not slow. Below 1.0 a viewer stutters. A copy reads its input at 5 times the film's speed, so it shows about 5 whatever the machine could do. Absent until the job has run a second, and gone when the job ends. `job` is the job's ID. |
| `jellyscale_transcode_job_paused{job}` | worker | 1 while that job's ffmpeg is paused at its lead limit. |
| `jellyscale_transcode_cores`, `jellyscale_transcode_cores_busy` | worker | Cores this worker declared (`transcodeCores`), and the cost in cores of the jobs it holds (paused jobs hold theirs; docs/transcoding.md has the costs). |
| `jellyscale_transcode_queue_cores` | worker | The cost in cores of the jobs queued for a worker and not yet past the queue timeout, for the whole cluster, read from Postgres when scraped, so every worker reports the same number: take one worker's, don't sum them. It is the signal to scale workers on: one queued 4K tone mapped job reads 3.2, one 1080p SDR job 0.8. |
| `jellyscale_transcode_queue_depth` | worker | The number of jobs queued for a worker and not yet past the queue timeout, beside `queue_cores`, so that copies held back by their own bound (a copy costs hardly any cores) are not read as no demand. It is the whole cluster's queue, read from Postgres when scraped, so every worker reports the same number: take one worker's, don't sum them. Workers report it, not api or stream, so a scraper sees one source per worker and no query runs for roles that don't need it. |
| `jellyscale_transcode_store_bytes` | worker | The bytes the transcode store held when a worker's sweep last listed it, for the whole cluster, read from Postgres when scraped, so every worker reports the same number: take one worker's, don't sum them. It is refreshed each sweep period (a minute) and, after a sweep, it is what the store holds. A sweep whose listing fails leaves the last number, and it is absent until the first listing; it is never 0 for a store that could not be read. Compare it with `transcodeBudget`. |
