# A path-secret playback link on Media3 (JS-219)

This spike answers whether one media link, with its secret in the path and
relative URLs inside its playlists, can be held by a player across a real
30-minute pause and then seek, and what the player reports when the link is
refused because its playback has ended. The result is handed to the product
owner before JS-217's Spec.

## Player and version

Media3 ExoPlayer **1.11.1** (the stable release listed at the Jetpack Media3
release notes), with `media3-exoplayer-hls` for HLS. The app is a minimal Java
activity in `spikes/pathsecret/android`; it holds one link, renders to a
`SurfaceView`, and takes pause/seek/resume/stop commands by adb broadcast so
that the pause is not simulated. The device is a headless Android TV emulator
running the installed `system-images;android-36;google-tv;x86_64` system image.

## Stand-in origin

`spikes/pathsecret/server.go` serves fMP4 HLS under `/media/<secret>/`. The
test film is generated by `spikes/pathsecret/make-media.sh` from `lavfi` sources
with ffmpeg; no real film is used. `master.m3u8` names `main.m3u8` relatively,
and that playlist names `init.mp4` and `segNNN.m4s` relatively. The origin
requires no header or query credential and logs every request with its UTC
time, path, query, any credentials present, status and byte count. A control
call switches the origin to refuse the link with `410 Gone` and a body naming
`playback-ended` and `start-again`, standing in for an ended playback.

## Result (observed)

Player: Media3 ExoPlayer 1.11.1, stable, with `media3-exoplayer-hls`, on a
headless Android TV emulator (API 36, x86_64, `google-tv` image).

- The link was `http://10.0.2.2:<port>/media/<secret>/master.m3u8`: the secret
  was in the path only; every logged media request had `query=""` and
  `credentials=none`. `master.m3u8` named `main.m3u8`, which named `init.mp4`
  and `segNNN.m4s`, all relative.
- Playback reached `STATE_READY`, reported `VIDEO 1280x720`, and the position
  advanced. There were no player errors.
- A real 30-minute pause (30 m 05 s of wall clock) followed. The player held
  its position at about 5.4 s; the origin logged **zero** requests during the
  pause. No error or state change was reported.
- A seek to 45,000 ms was then applied while paused: the app reported
  `DISCONTINUITY ... to=45000`, the origin served segments from the seek point
  onwards, and after resume the player was in `STATE_READY`, playing, at 45,018
  ms with no error. In an earlier run it kept playing from that point to 165,434
  ms over the following two minutes. So the same link survived the pause and
  the seek.
- For the refusal, the origin answered the link with `410 Gone` and a JSON body
  naming `playback-ended` and `start-again`. Media3 reported two
  `AnalyticsListener.onLoadError` events, each with
  `HttpDataSource$InvalidResponseCodeException: Response code: 410`. It did
  **not** call `Player.Listener.onPlayerError` within 90 seconds, and the player
  stayed in `STATE_BUFFERING` (`state=2`, `playWhenReady=true`) with no picture.
  An app therefore cannot rely on `onPlayerError` to notice that a playback has
  ended: it must watch load errors (or its own deadline) and start a new
  playback silently, showing nothing to the viewer. Only an explicit refusal
  of the new Play is shown, with its reason.

Evidence: the request log, app state snapshots and logcat are written by the
harness to its results directory, one sub-directory per run. The pause and seek
come from the long run (`seek_ok=1`, `requests_during_pause=0`). The refusal was
measured in a separate short run: in the long run, the TV launcher took focus
after the app was force-stopped for the refusal, so no refusal was requested
there; the short run with `SKIP_PAUSE=1` observed it.

## Exact commands

From the repository root, with `$ANDROID_HOME` pointing at the Android SDK,
`$JAVA17_HOME` at a JDK 17, `$RESULTS_DIR` empty, and `$ANDROID_AVD_HOME` at an
empty directory for this spike's own AVD:

```sh
export PORT=18080 CONSOLE_PORT=5580 AVD_NAME=js219_gms_tv SECRET=reel-secret-73
export RESULTS_DIR="$RESULTS_DIR" ANDROID_AVD_HOME="$ANDROID_AVD_HOME"
export ANDROID_HOME="$ANDROID_HOME" JAVA17_HOME="$JAVA17_HOME"
bash spikes/pathsecret/run.sh
```

`run.sh` generates the media, builds the app, creates and starts only its own
AVD on the chosen console port, starts the origin, installs the APK, starts
playback, issues a real 30-minute `sleep`, seeks to 45 s, resumes, then refuses
the link and records what the app sees. It shuts down only its own emulator and
origin on exit. Request logs, state snapshots, logcat and `summary.txt` are
written to `$RESULTS_DIR`.

For the short refusal-only run, use a fresh empty results directory and add:

```sh
export SKIP_PAUSE=1
bash spikes/pathsecret/run.sh
```
