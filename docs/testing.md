# Testing

```sh
go test ./...                               # Tests that need nothing outside Go
test/integration.sh                         # Every test, with disposable Postgres, SeaweedFS, Garage and real ffmpeg
INTEGRATION_SHARD=0/3 test/integration.sh   # One slice of it (0/3, 1/3, 2/3 of internal/transcode, or rest); CI runs them side by side
test/roles.sh <workdir>                     # Each role as its own process (makes its own films and config in <workdir>)
test/e2e/run.sh <workdir> <playwright_dir>  # Real jellyfin-web, two api replicas, S3, a router, a worker
E2E_GATES=transcode E2E_SHARD=1/3 test/e2e/run.sh <workdir> <playwright_dir>  # One slice of one gate
test/differential/run.sh <workdir>          # A real Jellyfin 12.4 and jellyscale asked the same requests; any unlisted difference fails
test/scripts_test.sh                        # The test scripts' own tests: shards, fixture cache, results
go run ./cmd/jellyscale --print-routes > compat/endpoints.yaml
```

There are two tiers of Go tests. `go test ./...` runs the tests that need nothing outside Go and passes on a machine with no ffmpeg, Postgres, S3 or fonts. Tests that need any of them live in files named `*_integration_test.go` with the build tag `//go:build integration`, and `test/integration.sh` runs them (`go test -tags integration`) with everything else. It needs Docker, curl, ffmpeg and ffprobe built with libx264, libx265, libsvtav1 and libass, and fontconfig with a font (`fonts-dejavu-core`, or `font-dejavu` on Alpine), and says which is missing when it stops. No test skips for a missing dependency: it fails, naming what it needs. A mistyped build tag would hide a test without any skip, so `TestBuildTags` requires a file's name and tag to agree. `cmd/testreport` fails a run with a skipped test, or with a different number of tests from what `go test -list` finds for the tier, which catches a run that stopped partway. Go tests run through [gotestsum](https://github.com/gotestyourself/gotestsum) (pinned in `go.mod`, run as `go tool gotestsum`), and in CI each job's summary lists passed, failed and skipped counts and each failure's reason, the last line a test located, with an annotation at that file and line. A panic or skip is named but has no line, and an e2e scenario is annotated at the quoted literal of its name, so a scenario keeps any part known only at run time after `: `; a name with no such literal is annotated at the top of the file. `test/roles.sh` and each `test/e2e` gate do the same in CI and print as before locally. A failed job uploads its logs as an artifact: for the Go tiers, `unit.json` or `tests.json` (every test's output, which holds the workers' log lines and the ffmpeg stderr in their errors) and `failures.log` (the full output of each failure, plus the server and worker log of a subtitle test that failed); for roles and e2e, the server, worker and ffmpeg logs; run locally, `JELLYSCALE_LOG_DIR` picks where the logs go. Roles and e2e default to `<workdir>/logs`; the Go tiers keep theirs only when it is set.

`test/e2e` needs `web-dist` (see [Running jellyscale](running.md#run)), and a directory with `playwright-core` installed. `run.sh` checks for `web-dist/index.html` first, before it starts anything, and prints the `docker cp` command when it is missing (a git worktree has none of its own: copy it in, or symlink the main checkout's). It drives the browser at `$CHROMIUM_PATH`, `/usr/bin/chromium` if unset. Use Google Chrome (`CHROMIUM_PATH=/usr/bin/google-chrome-stable`) where Chromium is built without H.264 and AAC, which every fixture needs. `E2E_GATES="transcode"` runs one gate, and `E2E_ONLY=regex` runs the scenarios of subtitles or transcode whose name matches (name the gate with it: a gate where nothing matches ran no scenario, and fails). `E2E_HEVC=1` says the browser plays HEVC (a machine with a hardware decoder); the transcode gate then expects HEVC to direct play and copy, where otherwise it expects the H.264 re-encode that CI's Chrome gets. The runner chooses; the test never asks the browser.

**Shards.** `E2E_SHARD=i/n` makes the subtitles and transcode gates run every n-th of their scenarios by call order, starting at the i-th (`test/e2e/shard.mjs`). A scenario that stops or kills the worker, or needs it gone, is marked `{ stopsWorker: true }` at its `scenario()` call and runs only on the last shard, after that shard's share, in call order. browse and play are one sequence of steps (the later ones need the login) and always run whole, so give them to one job. Every gate ends with `shard i/n: ran k of T`, T being every `scenario()` call before sharding and `E2E_ONLY` filtering; `run.sh` fails a gate with no such line (it stopped partway) or with k = 0 unless `E2E_ONLY` is set, and writes `gate i n k T` to `<logs>/shard-<gate>-<i>of<n>.txt`. `test/check-shards.sh e2e <dir> "<gates>"` reads those files and fails unless, for each gate named (CI passes `run.sh`'s default four and `differential`, so a gate that no job ran fails too), every shard is there, they agree on n and T, and their k add up to T: a scenario in no shard fails the build. A new scenario needs no list to be added to. Integration is split the same way, by `test/shard.sh`: `INTEGRATION_SHARD=i/n` runs the tests of `internal/transcode` whose rank, sorted by name, is i modulo n (as `-run '^(A|B)$'`), `INTEGRATION_SHARD=rest` every other package, both found by `go test -list`, so a new test or package lands in a shard on its own; `report.sh` expects the shard's own count (a shard that stopped partway fails) and `test/check-shards.sh integration` checks that the shards' counts add up to the tier's. In CI, `e2e shard` and `integration shard` are matrix jobs, and the jobs named `integration` and `e2e` (the required checks, with `lint-and-unit`) fail if any shard failed or was cancelled or the totals don't add up. The media tiers run once per change, in the merge queue, which tests the exact commit that lands on `main` (on top of `main` and every pull request queued ahead). On a pull request only `lint-and-unit` runs, and `integration` and `e2e` pass at once, saying the shards run in the queue; add the label `ci:full` to run everything on the pull request first, for early feedback on a risky change. A merge group, or a `ci:full` pull request, that changes only Markdown files in the root or under `docs/`, or `tasks/prd.json`, skips the media jobs and those two checks pass (`test/changes.sh`, which diffs without rename detection so code moved into `docs/` or to a `.md` name counts as code; `.claude/` and `compat/` count as code). A push to `main` was tested in its merge group: it runs `lint-and-unit`, and `fixture-cache` refills the e2e fixture cache when its key changed, because a cache saved in a merge group is seen only there. `lint-and-unit` runs on every event, and it is what runs the unit tests that read `PRODUCT.md` and `tasks/prd.json`.

**Differential tier.** `test/differential/run.sh <workdir>` starts `jellyfin/jellyfin:12.4` and Postgres in Docker on Docker-assigned ports and `jellyscale --roles=all` as a process, over hard links to the synthetic e2e films (the same cache; never a real library), completes Jellyfin's startup wizard through its API (`compat/captures/differential-12.4.md`), adds a movie, a show and an HDR library (the Dolby Vision and HDR10+ films of `test/fixtures/dovi`, under `media/hdr`) to both, waits for both scans, signs in to both as `admin`, and leaves a film half watched on both. Then `test/differential/run/main.go` sends each request of `test/differential/requests.yaml` to both and compares the answers. It needs Docker, ffmpeg, Go, curl and python3; the output ends with `shard 0/1: ran k of T`, and `<logs>/shard-differential-0of1.txt` holds `differential 0 1 k T` for `test/check-shards.sh`, so it runs in CI as one more entry of the `e2e shard` matrix and `e2e`, the required check, expects the `differential` gate. `DIFFERENTIAL_HOLD=600` keeps both servers up for ten minutes afterwards, to poke at them; the logs (`jellyfin.log`, `jellyscale.log`) go to `$JELLYSCALE_LOG_DIR`, default `<workdir>/logs`.

What makes two answers comparable is `test/differential/normalize.go`, tested in `normalize_test.go`: the ids of an item (32 hex digits, dashed or not, any case, also inside URLs) become `<id:Type/Name>`, the key being the item's type and, for a film or episode, its file name, because the two servers name a film differently; the map is built up front from a recursive listing of each server, so an id in another response (a series in an episode's `SeriesId`) maps too. Tokens, ETags, session ids and server ids are masked, and so are the timestamps under the keys that change from run to run, `MaskedTimeKeys` in `normalize.go`: `DateCreated`, `DateLastMediaAdded`, `LastPlayedDate`, `LastActivityDate` and `LastLoginDate`. The key stays so that a missing field still differs. Every other timestamp (`PremiereDate`, `EndDate`, one inside free text) is compared; add a key to the list only when its value changes between runs. Each request must answer 2xx on both servers unless it says `status: 404` (or another); `rows: true` also fails an empty list from either server (an `Items` list, a top-level array, a playlist), and goes on every request that returns items on the fixtures. Arrays are sorted unless the request says `ordered: true`; set it where the route promises an order (a sorted listing, seasons, a playlist, the streams of an item). A request is sent with the same admin on both, and a JSON path in the report looks like `Items[2].UserData.Played`.

**Adding a route.** Add an entry to `test/differential/requests.yaml`: `name`, `route` (the template as in `compat/endpoints.yaml`), `method`, `path` (the request line with the query jellyfin-web sends; `{{Movie/Alpha Film (2021)}}` is the id a server gave that item, keyed by type and file name, and `{{User/admin}}` the user), `body` for a POST, `ordered`, and `rows: true` if it returns items on the fixtures. Give the request a `name` no other request has: allowlist entries refer to it. Name only films of `test/fixtures/make.sh`; `files_test.go` checks the route is in `compat/endpoints.yaml` and that titles are synthetic. Run the tier: a new route usually shows differences.

A request can say `play: <name of a PlaybackInfo request>`: before it, the runner plays what that request is offered on both servers (master and main playlists, segment 0, `Sessions/Playing`), so `GET /Sessions` has a transcode to describe. `only: <Key>` keeps the differences under that key of each array element, for a document most of which other tasks own.

**Adding an allowlist entry.** Every difference is either fixed or listed in `compat/differences.yaml`, as `requests:` (a list of the `name`s in `requests.yaml` it applies to), `path` (or `paths`, a list sharing one reason), `kind` and `reason`. An entry applies only to the requests it names, never to the whole route: an entry another request needs cannot hide a difference in this one, which is how a dropped film or a wrong sort order once passed. A name that is no request fails the tier, and so does an entry with no `requests`. `kind` is `improvement` (better than Jellyfin on purpose), `non-goal` (PRODUCT.md leaves it out) or `gap` (to close; `task: JS-nnn` must be in `tasks/prd.json`). A path is the whole JSON path with `[]` for any index (`Items[].UserData.Key`), or one element (`[1]`); it never matches as a prefix. Besides the fields, the tier compares which items each array holds (by their `Id`, sorted unless the request is `ordered`, where the order counts) and reports a difference at `Items (ids)` (`(ids)` for a top-level array). Listing every field of a listing therefore cannot hide a dropped, extra or reordered item. A gap in that list needs an entry whose `path` ends in `(ids)` and whose `jellyscale:` lists the normalized Ids jellyscale answers today (`<id:Movie/Alpha Film (2021)>`); any other answer, such as a new wrong order, fails. An `(ids)` entry without `jellyscale:`, or `jellyscale:` on another path, is refused. A difference not listed fails the tier and the report names the request (`request: <name>`); an entry that no longer matches in one of its requests is printed as `note` so it can be removed, and the list shrinks as the gaps close. To check the tier can fail, put a bug back. `test/differential/acceptance.sh <workdir>` does it on copies of the tree, four times, and expects the tier to fail on the named request each time: `mediaTypeFilter` in `internal/api/items.go` ignoring its list (PR #32; `continue watching, Book` returns the half-watched film where Jellyfin returns none), `GET /Items/Latest` dropping a film (`latest films in the Movies library`), `GET /Items` sorted by the name instead of the sort name (`the films library, by name`), and a film with a `PremiereDate` Jellyfin does not give (`a film's details`).

**Fixtures.** The films the gates play are made by `test/fixtures/e2e.sh` (with `posix.sh` and `make.sh`) and cached under a key from `test/fixtures/key.sh`: a sha256 over the recipes (every `test/fixtures/*.sh`, so `cached.sh` and `key.sh` too, and the PGS generator with `internal/testenv`), the first line of `ffmpeg -version` and the serif font the font films attach. `run.sh` copies `<cache>/<key>/media` into the workdir; the cache is `$E2E_FIXTURE_CACHE`, default `~/.cache/jellyscale/e2e-fixtures`, and an entry is made in a temp dir and renamed, so a killed run leaves no half entry. CI caches the same directory with `actions/cache` under the same key. Hard links, the copy the failure scenario cuts short, assets, scratch and segments stay out of the cache, in the workdir. Editing any of those or changing ffmpeg or the font regenerates them; an entry for another key is removed after 14 days unused.

**Repeats.** `E2E_REPEAT=n` runs the chosen gates n times on one stack, to hunt a flake, and prints `passed p of n` for each scenario. Between iterations it clears the segments directory, the scratch directory and the S3 segments, truncates the transcode jobs and restarts the worker. It does not rebuild the stack, so the scan, the subtitles and fonts already extracted, and the users stay: these are warm reruns, and a scenario that depends on a film's first play can fail from the second iteration on without being flaky. `E2E_FLAKY_DEMO=1` adds a browse step that fails on odd iterations, to see the report (a repeat of 2 shows `passed 1 of 2`); CI never sets it.

**Temp files and results.** The scripts export `TMPDIR` before `go test`, ffmpeg and the browser start, and remove it on exit. Without a workdir it is a directory under `/tmp/jellyscale-test`. With one, the files live in `<workdir>/t`, so a SIGKILLed run's temp files stay with it and not in RAM-backed `/tmp`; `TMPDIR` is then a short link to it under `/tmp/jellyscale-test`, because unix sockets have a 108-byte path limit. Entries there are named `<script>.<pid>.XXXXXX`, and every script starts by removing those whose script has exited, with the `<workdir>/t` a link points to, and stale half-made entries in the fixture cache. Fixture films are made under TMPDIR and copied into the cache only when whole. `test/unit.sh`, `test/integration.sh`, `test/roles.sh` and `test/e2e/run.sh` record the outcome of a whole run (no `-run` arguments, no `E2E_ONLY`; a whole shard counts as itself) in `.results/<tree>/<name>` (gitignored; the tree is `tools/snapshot.sh`'s), as `key=value` lines with `status`, `summary` and the `log` directory, and write nothing if the tree changed during the run. `build`'s QA step reads them: it reuses a pass for an identical tree and runs the rest (`.claude/agents/qa.md`). Records older than two weeks are swept.
