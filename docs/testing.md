# Testing

```sh
go test ./...                               # Tests that need nothing outside Go
test/integration.sh                         # Every test, with disposable Postgres, SeaweedFS, Garage and real ffmpeg
INTEGRATION_SHARD=0/4 test/integration.sh   # One slice of it (0/4 to 3/4 of internal/transcode and internal/api, dealt by time, or rest); CI runs the five side by side
INTEGRATION_SHARD=0/4 INTEGRATION_PROCS=2 INTEGRATION_PROC=1 test/integration.sh   # Exactly process 1's share of a slice that CI runs as 2 processes
test/roles.sh <workdir>                     # Each role as its own process (makes its own films and config in <workdir>)
test/e2e/run.sh <workdir> <playwright_dir>  # Real jellyfin-web, two api replicas, S3, a router, a worker
E2E_GATES=transcode E2E_SHARD=1/3 test/e2e/run.sh <workdir> <playwright_dir>  # One slice of one gate
test/differential/run.sh <workdir>          # A real Jellyfin 12.4 and jellyscale asked the same requests; any unlisted difference fails
test/ffmpeg61.sh go test -tags integration ./internal/transcode -run X  # Under Ubuntu 24.04's ffmpeg 6.1, as CI
go run ./cmd/jellyscale --print-routes > compat/endpoints.yaml
```

Test the application's behaviour only: the tests show what the server does for a viewer or an operator. Do not test documentation, Markdown, static content, CI or workflow YAML, source shape, fixture inventories, or the test tools themselves; a test tool proves itself by running. Record a failure that taught something in [Historical test failures](#historical-test-failures).

There are two tiers of Go tests. `go test ./...` runs the tests that need nothing outside Go and passes on a machine with no ffmpeg, Postgres, S3 or fonts. Tests that need any of them live in files named `*_integration_test.go` with the build tag `//go:build integration`, and `test/integration.sh` runs them (`go test -tags integration`) with everything else. It needs Docker, curl, ffmpeg and ffprobe built with libx264, libx265, libsvtav1 and libass, and fontconfig with a font (`fonts-dejavu-core`, or `font-dejavu` on Alpine), and says which is missing when it stops. No test skips for a missing dependency: it fails, naming what it needs. A test file's name and build tag must agree, since a mistyped tag hides a test without a skip. `cmd/testreport` fails a run with a skipped test, or with a different number of tests from what `go test -list` finds for the tier, which catches a run that stopped partway. Go tests run through [gotestsum](https://github.com/gotestyourself/gotestsum) (pinned in `go.mod`, run as `go tool gotestsum`), and in CI each job's summary lists passed, failed and skipped counts and each failure's reason, the last line a test located, with an annotation at that file and line. A panic or skip is named but has no line, and an e2e scenario is annotated at the quoted literal of its name, so a scenario keeps any part known only at run time after `: `; a name with no such literal is annotated at the top of the file. `test/roles.sh` and each `test/e2e` gate do the same in CI and print as before locally. A failed job uploads its logs as an artifact: for the Go tiers, `unit.json` or `tests.json` (every test's output, which holds the workers' log lines and the ffmpeg stderr in their errors) and `failures.log` (the full output of each failure, plus the server and worker log of a subtitle test that failed); for roles and e2e, the server, worker and ffmpeg logs; run locally, `JELLYSCALE_LOG_DIR` picks where the logs go. Roles and e2e default to `<workdir>/logs`; the Go tiers keep theirs only when it is set.

`test/e2e` needs `web-dist` (see [Running jellyscale](running.md#run)), and a directory with `playwright-core` installed. `run.sh` checks for `web-dist/index.html` first, before it starts anything, and prints the `docker cp` command when it is missing (a git worktree has none of its own: copy it in, or symlink the main checkout's). It drives the browser at `$CHROMIUM_PATH`, `/usr/bin/chromium` if unset. Use Google Chrome (`CHROMIUM_PATH=/usr/bin/google-chrome-stable`) where Chromium is built without H.264 and AAC, which every fixture needs. `E2E_GATES="transcode"` runs one gate, and `E2E_ONLY=regex` runs the scenarios of subtitles or transcode whose name matches (name the gate with it: a gate where nothing matches ran no scenario, and fails). `E2E_HEVC=1` says the browser plays HEVC (a machine with a hardware decoder); the transcode gate then expects HEVC to direct play and copy, where otherwise it expects the H.264 re-encode that CI's Chrome gets. The runner chooses; the test never asks the browser.

**Mechanisms, not speeds.** A test checks what the code does, never how fast the machine did it: no test passes, fails or branches on a measured duration or speed. A bar of that kind (a duration with an upper bound, two durations compared, a speed with a lower bound or a "not slow" flag) passes on a developer's 16 cores and fails on a shared 2-CPU runner with a right build; it was the largest class of merge-queue escapes (JS-067, JS-024, JS-072, JS-071). Check the mechanism instead: how many helpers ran and whether they ran at the same moment, which worker's job made each segment, that a copy decoded no video frame, that ffmpeg was given the arguments that make it fast, that a job was claimed before the dead worker's lease ran out, that a shown speed is the one the worker recorded. A timing is still measured and logged (`t.Logf`, `console.log`) with what it is, so a regression shows in the numbers without failing a right build. A time bound may stay only where it stops a hang: a wait for an event with a timeout (`waitFor`, a context deadline, a `select` with `time.After`, a loop whose condition holds a deadline); or a measured bound of at least ten times what a right build takes at that step, where a wrong build never delivers; or one that is not before a timer or sleep the test itself set. A bound closer than ten times is a bar. **Where the timings are kept.** The timings of a run that passed are printed at the end of its output: `test/report.sh` prints every line the Go tests logged that holds a time or a multiple (the speedup of two and three workers, the copy's multiple of real time, kill to first segment, slowest wait), so in CI they are in the job log of a run that passed and of one that failed, and the e2e and roles scripts print theirs as they go. The whole of a Go tier's output is in `tests.json` (kept as an artifact only when the job failed, and in `JELLYSCALE_LOG_DIR` locally), and a whole local run is recorded under `.results/<tree>/` with the `log` directory in its record.

**Shards.** `E2E_SHARD=i/n` makes the subtitles and transcode gates run every n-th of their scenarios by call order, starting at the i-th (`test/e2e/shard.mjs`). A scenario that stops or kills the worker, or needs it gone, is marked `{ stopsWorker: true }` at its `scenario()` call and runs only on the last shard, after that shard's share, in call order. browse and play are one sequence of steps (the later ones need the login) and always run whole, so give them to one job. Every gate ends with `shard i/n: ran k of T`, T being every `scenario()` call before sharding and `E2E_ONLY` filtering; `run.sh` fails a gate with no such line (it stopped partway) or with k = 0 unless `E2E_ONLY` is set, and writes `gate i n k T` to `<logs>/shard-<gate>-<i>of<n>.txt`. `test/check-shards.sh e2e <dir> "<gates>"` reads those files and fails unless, for each gate named (CI passes `run.sh`'s default four and `differential`, so a gate that no job ran fails too), every shard is there, they agree on n and T, and their k add up to T: a scenario in no shard fails the build. A new scenario needs no list to be added to. Integration is split by `test/shard.sh`: the tests of `internal/transcode` and `internal/api` are dealt out together by time, and `INTEGRATION_SHARD=i/n` runs shard i of n of them, one `go test` run for each package (as `-run '^(A|B)$'`, so a test name in both packages runs once in each): longest first by the mean seconds in `test/shard-times.txt`, each to the shard with the least so far, a test not in the file counting as the file's median. The times are from CI's runners, not a developer machine: the file is the output of `test/shard-times.sh <run dir>...`, run on the `integration-shard-*` artifacts of at least three successful merge-queue runs (`gh run download <run> --pattern 'integration-shard-*' -D <run id>`), and its header names the runs; never edit it by hand. It only decides the split, never pass or fail. `INTEGRATION_SHARD=rest` runs every other package whole. Both are found by `go test -list`, so a new test or package lands in a shard on its own; CI deals them over four shards (`0of4` to `3of4`) and `rest`; the shard summary's 1.25 times notice is the cue to refresh the file. The `integration` job's summary has one line for each shard, `rest` included, with the seconds of the top-level tests it ran (read from that shard's own `tests.json`, by `test/shard-summary.sh`), and the line `refresh test/shard-times.txt` when the slowest dealt shard is over 1.25 times the fastest; it is a notice and fails nothing. `report.sh` expects the shard's own count (a shard that stopped partway fails) and `test/check-shards.sh integration` checks that the shards' counts add up to the tier's. The tier is split twice. `test/shard.sh` deals it to the jobs (the shards above), and then each job runs its shard as `INTEGRATION_PROCS=n` go test processes at once (the matrix's `procs`: 2 for each dealt shard, 4 for `rest`), because one process leaves most of a runner's CPUs idle. `test/shard.sh <shard> <k>/<m>` deals a shard's tests again by time, longest first, into m shares; process k runs its share, one `go test` run for each package (one run over all packages for `rest`, which refuses a test name found in two packages), against a Postgres of its own started on a Docker-assigned port under a name unique to the run (a Postgres for each process, not a database for each: some tests end backends chosen from `pg_locks`, which is cluster-wide) and with its own `TMPDIR` and `tests.json`. SeaweedFS and Garage are shared. Each process's count is checked against its share and the job's against `test/shard.sh count`, so a process that stops partway, a skip or a failure fails the job and names the test, and the other processes' results are still reported. `INTEGRATION_PROCS=1` or unset runs the shard in one process. `INTEGRATION_PROC=k` with `INTEGRATION_PROCS=n` runs only process k, which is how to run one process's share by itself. `test/alone.txt` lists tests (`<package> <test> <reason>`) that cannot share a machine with other tests, because they measure the machine or compare the whole daemon's state; they are left out of every share and run once, on their own, after the shares of their job have ended. A test that fails side by side and passes alone is fixed at its cause, or listed in `test/alone.txt` with its reason; it is never retried, skipped or given more time. A concurrency claim still needs its own real processes or real contention: running tests side by side is no proof of one. In CI, `e2e shard` and `integration shard` are matrix jobs, and the jobs named `integration` and `e2e` (the required checks, with `lint-and-unit`) fail if any shard failed or was cancelled or the totals don't add up. The media tiers run once per change, in the merge queue, which tests the exact commit that lands on `main` (on top of `main` and every pull request queued ahead). On a pull request only `lint-and-unit` runs, and `integration` and `e2e` pass at once, saying the shards run in the queue; add the label `ci:full` to run everything on the pull request first, for early feedback on a risky change. A merge group, or a `ci:full` pull request, that changes only files under `.claude/` or `tasks/`, Markdown files in the root, or `docs/*.md`, skips the media jobs and those two checks pass (`test/changes.sh`, which diffs without rename detection so code moved into `docs/` or to a `.md` name counts as code; `compat/` counts as code). That is safe because the application does not read `.claude/`, `tasks/` or Markdown at runtime. `docs/<name>.md` counts, `docs/sub/x.md` does not. A push to `main` was tested in its merge group: it runs `lint-and-unit`, and `fixture-cache`, `deb-cache` and `jars-cache` refill the e2e fixture cache, the .deb cache and the jars cache when their keys are missing, because a cache saved in a merge group is seen only there. When `lint-and-unit` fails in a run whose media jobs run, `cancel-media-jobs` cancels that run (only it), so the shards stop paying for a run that cannot merge; `integration` and `e2e` then fail. `lint-and-unit` runs on every event but a plan change: a pull request or merge group whose every file is under `tasks/`, a Markdown file in the root, or `docs/*.md`, with nothing under `.claude/` (`test/changes.sh` prints `plan`). The plan is not tested in CI (owner, 2026-11-22): `lint-and-unit` is skipped and reports as passed; the next code change runs the unit tier in CI. A change to `.claude/` still runs it, because it parses the workflow scripts. If the `changes` job fails or says nothing, `lint-and-unit` runs.

**Differential tier.** `test/differential/run.sh <workdir>` starts `jellyfin/jellyfin:12.4` and Postgres in Docker on Docker-assigned ports and `jellyscale --roles=all` as a process, over hard links to the synthetic e2e films (the same cache; never a real library), completes Jellyfin's startup wizard through its API (`compat/captures/differential-12.4.md`), adds a movie, a show and an HDR library (the Dolby Vision and HDR10+ films of `test/fixtures/dovi`, under `media/hdr`) to both, waits for both scans, signs in to both as `admin`, and leaves a film half watched on both. Then `test/differential/run/main.go` sends each request of `test/differential/requests.yaml` to both and compares the answers. It needs Docker, ffmpeg, Go, curl and python3; the output ends with `shard 0/1: ran k of T`, and `<logs>/shard-differential-0of1.txt` holds `differential 0 1 k T` for `test/check-shards.sh`, so it runs in CI as one more entry of the `e2e shard` matrix and `e2e`, the required check, expects the `differential` gate. `DIFFERENTIAL_HOLD=600` keeps both servers up for ten minutes afterwards, to poke at them; the logs (`jellyfin.log`, `jellyscale.log`) go to `$JELLYSCALE_LOG_DIR`, default `<workdir>/logs`.

**Conformance (JS-070).** One checker, `compat/conform`, holds JSON answers to `compat/schema-12.4.json`, the types and response schemas of Jellyfin 12.4.0's OpenAPI document, which `compat/gen-schema.sh` makes from the `jellyfin/jellyfin:12.4` container (it records the image and the server version). The differential tier checks every JSON answer of jellyscale as it arrives (each request, the sign-in and setup calls, the sweep below), and of Jellyfin too, so that a rule Jellyfin's own answers break shows; the e2e gates record the JSON responses their browser gets (`test/e2e/conform.mjs`, `<logs>/<gate>/responses.jsonl`) and `compat/conform/cmd/conform check` checks them when the gate ends, with the checked-in schema and no Jellyfin. A violation is a required field (listed in `required`, or non-nullable with no default; an object written inline in the document, such as `ImageBlurHashes`, requires only what it lists) absent or null at any depth and in every array element, a value of another type, enum, uuid or date-time, or no JSON body where the schema gives one; a field the schema does not list is none. A route is matched whatever the case of its path and the names of its parameters; `compat/conform.yaml` says which routes are aliases of others and which JSON routes the schema does not type (each with a reason). A violation is never filtered by `compat/differences.yaml`. Each run prints `<label>: checked N JSON responses on M routes` and fails when N is 0. The differential tier also fails when `compat/schema-12.4.json` differs from the document of the Jellyfin it started, sends every request of `compat/clients.yaml` to jellyscale (`clients: sent N requests`; a status other than 2xx fails, naming the client, the path and the route, unless Jellyfin answers the same status), decodes the answers of the requests labelled `kotlin:` in `requests.yaml` with jellyfin-sdk-kotlin 1.9.4's serializers (`test/sdkjvm/decode.sh`, needs java; `kotlin: decoded N answers`), and runs `@jellyfin/sdk`'s server discovery against jellyscale (`test/sdknode`, needs node and npm). A request with `decode_only: true` is asked of both servers and checked, but the answers are not compared. `Zeta Film (2023)`, two audio tracks, is made by `run.sh` for the second stream of a PlaybackInfo; its file is dated 2000 so that `Items/Latest` lists it last on both servers. To refresh the schema after Jellyfin changes, run `compat/gen-schema.sh`.

What makes two answers comparable is `test/differential/normalize.go`: the ids of an item (32 hex digits, dashed or not, any case, also inside URLs) become `<id:Type/Name>`, the key being the item's type and, for a film or episode, its file name, because the two servers name a film differently; the map is built up front from a recursive listing of each server, so an id in another response (a series in an episode's `SeriesId`) maps too. Tokens, ETags, session ids and server ids are masked, and so are the timestamps under the keys that change from run to run, `MaskedTimeKeys` in `normalize.go`: `DateCreated`, `DateLastMediaAdded`, `LastPlayedDate`, `LastActivityDate` and `LastLoginDate`. The key stays so that a missing field still differs. Every other timestamp (`PremiereDate`, `EndDate`, one inside free text) is compared; add a key to the list only when its value changes between runs. Each request must answer 2xx on both servers unless it says `status: 404` (or another); `rows: true` also fails an empty list from either server (an `Items` list, a top-level array, a playlist), and goes on every request that returns items on the fixtures. Arrays are sorted unless the request says `ordered: true`; set it where the route promises an order (a sorted listing, seasons, a playlist, the streams of an item). A request is sent with the same admin on both, and a JSON path in the report looks like `Items[2].UserData.Played`.

**Adding a route.** Add an entry to `test/differential/requests.yaml`: `name`, `route` (the template as in `compat/endpoints.yaml`), `method`, `path` (the request line with the query jellyfin-web sends; `{{Movie/Alpha Film (2021)}}` is the id a server gave that item, keyed by type and file name, and `{{User/admin}}` the user), `body` for a POST, `ordered`, and `rows: true` if it returns items on the fixtures. Give the request a `name` no other request has: allowlist entries refer to it. Name only films of `test/fixtures/make.sh` (and `Zeta Film (2023)`, which `run.sh` makes), and use the route as it appears in `compat/endpoints.yaml`. Run the tier: a new route usually shows differences.

A request can say `play: <name of a PlaybackInfo request>`: before it, the runner plays what that request is offered on both servers (master and main playlists, segment 0, `Sessions/Playing`), so `GET /Sessions` has a transcode to describe. `only: <Key>` keeps the differences under that key of each array element, for a document most of which other tasks own.

**Adding an allowlist entry.** Every difference is either fixed or listed in `compat/differences.yaml`, as `requests:` (a list of the `name`s in `requests.yaml` it applies to), `path` (or `paths`, a list sharing one reason), `kind` and `reason`. An entry applies only to the requests it names, never to the whole route: an entry another request needs cannot hide a difference in this one, which is how a dropped film or a wrong sort order once passed. A name that is no request fails the tier, and so does an entry with no `requests`. `kind` is `improvement` (better than Jellyfin on purpose), `non-goal` (PRODUCT.md leaves it out) or `gap` (to close; `task: JS-nnn` must be in `tasks/prd.json`). A path is the whole JSON path with `[]` for any index (`Items[].UserData.Key`), or one element (`[1]`); it never matches as a prefix. Besides the fields, the tier compares which items each array holds (by their `Id`, sorted unless the request is `ordered`, where the order counts) and reports a difference at `Items (ids)` (`(ids)` for a top-level array). Listing every field of a listing therefore cannot hide a dropped, extra or reordered item. A gap in that list needs an entry whose `path` ends in `(ids)` and whose `jellyscale:` lists the normalized Ids jellyscale answers today (`<id:Movie/Alpha Film (2021)>`); any other answer, such as a new wrong order, fails. An `(ids)` entry without `jellyscale:`, or `jellyscale:` on another path, is refused. A difference not listed fails the tier and the report names the request (`request: <name>`); an entry that no longer matches in one of its requests is printed as `note` so it can be removed, and the list shrinks as the gaps close.

**Fixtures.** The films the gates play are made by `test/fixtures/e2e.sh` (with `posix.sh` and `make.sh`) and cached under a key from `test/fixtures/key.sh`: a sha256 over the recipes (every `test/fixtures/*.sh`, so `cached.sh` and `key.sh` too, and the PGS generator with `internal/testenv`), the first line of `ffmpeg -version` and the serif font the font films attach. `run.sh` copies `<cache>/<key>/media` into the workdir; the cache is `$E2E_FIXTURE_CACHE`, default `~/.cache/jellyscale/e2e-fixtures`, and an entry is made in a temp dir and renamed, so a killed run leaves no half entry. CI caches the same directory with `actions/cache` under the same key. Hard links, the copy the failure scenario cuts short, assets, scratch and segments stay out of the cache, in the workdir. Editing any of those or changing ffmpeg or the font regenerates them; an entry for another key is removed after 14 days unused.

**CI caches.** Two caches keep the media jobs off the network, both `actions/cache`. The .deb files of each job's `test/apt.sh` install (ffmpeg, plus fontconfig and fonts-dejavu-core for the integration shards) are kept in `/home/runner/apt-debs` under a key of the runner image version and the package list: a hit installs from those files with no `apt-get update` and no download, and a miss installs from archive.ubuntu.com with three retries as before, leaves the .deb of every package it installed, dependencies included, in that directory, and the job saves it. The jars of `test/sdkjvm/jars.txt` are kept in `~/.cache/jellyscale/sdkjvm` under a key of that file's hash: a changed `jars.txt` is a miss, which fetches from Maven Central as before and saves, and a restored jar is still checked against its sha256 in `jars.txt`. A merge group sees only what `main` or itself saved, so a push to `main` saves each key when it is missing.

**ffmpeg 6.1.** CI installs Ubuntu 24.04's ffmpeg 6.1, the oldest jellyscale supports, and a newer local ffmpeg can hide what it does differently. JS-023 found two in the merge queue: Ubuntu's libx265 is built without HDR10+ and ignores `--dhdr10-info` without an error, and a global `-strict -2` let 6.1's MP4 muxer copy a Dolby Vision box into an H.264 stream that Chrome then would not start. `test/ffmpeg61.sh <command>` runs a command in an Ubuntu 24.04 container with that ffmpeg, the host's Go toolchain and module cache mounted, and `JELLYSCALE_TEST_*` passed through (it shares the host network, so a test can reach a Postgres or S3 the caller started). Run the integration tests a change to ffmpeg arguments, probing or fixtures touches under it before the merge queue does. `JELLYSCALE_TEST_CPUS=0-1` pins the container to two CPUs, as CI's runners: a core task's QA runs its checks of a race, a lock or an ordering that way, with the existing tests of the same mechanism, `-count=3`, on one database (owner, 2026-11-15, after JS-105 deadlocked 3 runs of 4 there and never on this machine). The merge queue stays the full gate; this is minutes, not a tier. `test/ffmpeg-image.sh <command>` does the same with the ffmpeg of the server image (the Dockerfile's `alpine:3.24` and its `apk add ffmpeg`, built from the Dockerfile's own lines), which is the one viewers' servers run and is neither CI's nor a developer's.

**Repeats.** `E2E_REPEAT=n` runs the chosen gates n times on one stack, to hunt a flake, and prints `passed p of n` for each scenario. Between iterations it clears the segments directory, the scratch directory and the S3 segments, truncates the transcode jobs and restarts the worker. It does not rebuild the stack, so the scan, the subtitles and fonts already extracted, and the users stay: these are warm reruns, and a scenario that depends on a film's first play can fail from the second iteration on without being flaky. `E2E_FLAKY_DEMO=1` adds a browse step that fails on odd iterations, to see the report (a repeat of 2 shows `passed 1 of 2`); CI never sets it.

**Temp files and results.** The scripts export `TMPDIR` before `go test`, ffmpeg and the browser start, and remove it on exit. Without a workdir it is a directory under `/tmp/jellyscale-test`. With one, the files live in `<workdir>/t`, so a SIGKILLed run's temp files stay with it and not in RAM-backed `/tmp`; `TMPDIR` is then a short link to it under `/tmp/jellyscale-test`, because unix sockets have a 108-byte path limit. Entries there are named `<script>.<pid>.XXXXXX`, and every script starts by removing those whose script has exited, with the `<workdir>/t` a link points to, and stale half-made entries in the fixture cache. Fixture films are made under TMPDIR and copied into the cache only when whole. `test/unit.sh`, `test/integration.sh`, `test/roles.sh` and `test/e2e/run.sh` record the outcome of a whole run (no `-run` arguments, no `E2E_ONLY`; a whole shard counts as itself) in `.results/<tree>/<name>` (gitignored; the tree is `tools/snapshot.sh`'s), as `key=value` lines with `status`, `summary` and the `log` directory, and write nothing if the tree changed during the run. `build`'s QA step reads them: it reuses a pass for an identical tree and runs the rest (`.claude/agents/qa.md`). Records older than two weeks are swept.

**Fault schedules (JS-066).** `TestFaultSchedulesHoldTheLeaseAndFailoverInvariants` in `internal/transcode` runs a fixed number of randomized schedules against real worker and stream-replica processes: kills of a worker holding a lease, restarts of Postgres, SIGSTOP of a worker, a slow database connection, and Stops of viewers, alone and overlapping, and asserts that a job has one owner, no job is lost, and no segment is stored by a dead owner, from what the database and the processes recorded, never from a measured duration. It is part of the integration tier and needs no flag. Each schedule prints its seed and steps when it starts, and a failure names the invariant, the seed and the step. Restarts of Postgres that overlap are one outage, which ends when the last of them ends, and a restart's check of a lease that ran out reports a harness error if the outage carried out was shorter than a lease. `JELLYSCALE_TEST_FAULT_SEED=<seed>` replays a seed: the same steps in the same order with the same targets and lengths; the interleaving of the processes is not replayed, so a replay can pass where the run failed. A failing seed is replayed on main the same day: if it replays, it is a blocker (a defect of the build or of the harness, fixed before the next queue run), not a backlog minor; only one that does not replay is an interleaving and goes to the backlog with its log.

```sh
JELLYSCALE_TEST_FAULT_SEED=12345 go test -tags integration ./internal/transcode -run TestFaultSchedules -count=1   # Replay seed 12345
JELLYSCALE_TEST_FAULT_SOAK=20 go test -tags integration ./internal/transcode -run TestFaultSchedules -count=1 -timeout 0   # Soak: 20 repetitions, a new seed each
```

The soak runs the same test with a new seed each time, asserts nothing the normal run does not, and prints `passed p of n` with every failing seed; it fails if p is less than n. The soak is for hunting flakes and is not a step before merging: `test/integration.sh`, CI and the build workflow never set it. Run these with the `JELLYSCALE_TEST_DATABASE_URL` and other variables `test/integration.sh` sets, or inside it.

## JS-099: recurring CI flakes

Machine for every local run below: 16 CPUs, `taskset -c 0-3` (four CPUs) on `test/e2e/run.sh`, `taskset -c 4-7` on the integration test, ffmpeg n9.0.2 (CI has Ubuntu 24.04's 6.1), another task building at the same time. There is no `TEST_CPUSET`.

## Historical test failures

A summary of the escape records kept with each task and the pending-triage notes. The detailed runs, logs and measurements are in the task sections above.

- **A test that measures the machine.** Duration and speed bars were the largest class of merge-queue escapes (JS-067, JS-024, JS-072, JS-071). They pass on a fast developer machine and fail on a shared runner with a right build. Fixed by asserting the mechanism instead (which worker made a segment, how many helpers ran, ffmpeg's arguments) and logging timings rather than failing on them.
- **A test that assumes an order the product does not owe.** An e2e seek was overwritten by the player's own start seek, and a helper waited for a job that a later seek had replaced (JS-099). Fixed by counting only real playback and by seeking to the viewer's place before choosing the track. A harness start that lost its chosen port was made to retry on a new port after run 44983050791.
- **A test that leaves state behind.** Deadlocks between a kit's reset and a snapshot read or a worker's write (runs 44855263307, 45041377896, 45049599358) came from processes and sessions outliving their test. Fixed by ending earlier environments, stopping workers around a reset, terminating a child's sessions, and failing a test that leaves a worker or a session behind (JS-158).
- **A fixture too large for the tier.** Two seek checks exceeded a 180 s bound on a two-CPU runner because each made a full film run (run 45008394219). Fixed by shortening the fixtures and bounding the work in segments (JS-171).
- **A race the test did not force.** A forgotten worker's late renewal, a job's first renewal racing its end, and an image sweep removing a track before its replacement were each seen once (JS-155). Fixed by forcing the order, or by making the kit's reset keep live workers (JS-160).
- **A product defect only the tier could show.** The upload check could store a segment cut short by an early input end (JS-159); a viewer could be refused at the moment a job was given up (JS-173); the unknown-name store could move a few rows over its bound between runs (JS-172). Each got a forced check and a fix at the cause.
- **Two reviewers sharing a log directory.** During concurrent QA and adversarial integration runs (JS-127), both runs kept `tests.json` and `failures.log` in the same place: `test/integration.sh` uses `JELLYSCALE_LOG_DIR` when it is set and otherwise `result_logdir` in `test/lib.sh` picks `.results/<tree>/integration.d` (or `<workdir>/logs`), which is one directory for both. The later writer's output then stands in for the other's, so a review cannot attribute a failure to its own run. Each concurrent reviewer sets `JELLYSCALE_LOG_DIR` to a directory of its own. This is harness evidence from those runs, not an executable check.
- **A runner image newer than its package mirror.** An exact-version Mesa dependency stopped three merge-group jobs before their tests started (run 45736550858). Fixed by dropping the optional Mesa VA packages on the mirror fallback and installing only required packages; no test was skipped, retried or given a longer bound.
- **What did not work.** Retrying, skipping or lengthening a bound never fixed an escape. A failure was reproduced with its order forced or its fixture made deterministic; when it could not be reproduced, it was recorded with what the log showed and what remained unknown, as in the JS-155 table.
