# Domains

The terms, boundaries and invariants of the system. Reviewers check changes against this file. If a change needs one of these to bend, update this file in the same change and say why.

## Vocabulary

- **Role:** what a process does, chosen by `--roles`: `api`, `stream` or `worker`. One binary, many Deployments.
- **Library:** a configured collection with a media store and an asset store. Clients see it as a `CollectionFolder`.
- **Item:** a Movie, Series, Season or Episode. Identified by a stable UUID.
- **Media source:** the playable object behind an item.
- **Store:** a POSIX or S3-compatible backend, reached only through `internal/store`.
- **Session:** a device's token, plus what it's playing.
- **Alias:** an obsolete route kept only for jellyfin-web.
- **Hint:** a NOTIFY wakeup. Lossy by design.
- **Spec hash:** identifies one transcode output: item, source and its ETag, audio track, video and audio bitrate and resolution as ffmpeg will use them, segment length, encoder family and the output settings version. A burnt-in subtitle track joins it, and so does whether the video is copied, and the transfer function of an HDR picture that is tone mapped (invariant 53). When that track is a subtitle file beside the film, the file's fingerprint joins it too (invariant 50).
- **Segment:** a 4 second piece of a transcode, stored as `segments/{spec_hash}/{n}.mp4`, with `init.mp4` beside them. In a copied stream it runs from a keyframe to the next one that makes it 4 seconds long, or to the last one that keeps it within 12 seconds, so it can be shorter than 4 seconds (invariant 47).
- **Copied stream:** a transcode that sends the source's video as it is, and the audio too when the client takes its codec (otherwise the audio is re-encoded), because the client plays the video but not the container.
- **Keyframe index:** the times of a source's keyframes, read from the file's own index at scan time and stored in `media_sources.keyframes`. A copied stream is cut on it.
- **Transcode store:** the store segments live in, configured once for every role that makes or serves segments.
- **Job:** one ffmpeg run that makes segments from N on. Workers claim jobs from a Postgres table.
- **Viewer:** one play session watching a spec. Jobs live while viewers do.
- **Seam:** where segments from two jobs meet.

## Boundaries

| Package | Owns | Must not |
|---|---|---|
| `internal/api` | HTTP, auth, DTO shaping at the edge | Touch a store except through `internal/store` |
| `internal/items` | Item queries and hydration | Know about HTTP |
| `internal/library` | Scanning, naming, probing, the keyframe index, the subtitle files and fonts beside a film, the chapter pictures | Serve requests |
| `internal/store` | Backend differences | Leak backend types or credentials |
| `internal/playback` | The decision between direct play and transcode, the spec and its hash, and the playlists | Do I/O |
| `internal/transcode` | Jobs, viewers, ffmpeg and the segment store | Know about HTTP |
| `internal/subtitles` | Extracting a text track from a file, its formats and time shift, the fonts attached to a file, and their cache in the asset store (the jobs that fill the tracks are in `internal/transcode`) | Know about HTTP |
| `internal/playstate` | Watch state: position, played, favorite, and its write rules | Know about HTTP or sessions |
| `internal/api` session persistence (`sessions`, `session_sockets`) | What each device is playing and which sockets it holds open | Keep that state in process memory |
| `internal/compat` | Client conventions | Hold domain logic |
| `internal/db` | Pool and migrations | Hold queries for other domains |

## Invariants

### Scaling

1. No process keeps state another replica needs. In-memory state must be safe to lose: connections, caches, running ffmpeg.
2. Anything a replica does at startup is safe when every replica does it at the same instant. Upserts use one conflict target, and a table must not have a second unique index that can race it.
3. Work that must happen once uses a lease or an advisory lock.
4. Routes belong to one role. Bandwidth-heavy routes go on `stream`.

### Data

5. Item IDs survive renames. A moved file keeps its item and watch state. So does a file missing from a scan: its item is hidden, with its rows, and removed only by the first scan after the grace (`missingGrace`); readers see items through `shown_items`, never `items`. A library's id survives a rename.
6. Filtering and sorting use indexed columns. Response shaping happens in memory from `items.dto`.
7. Client input reaches SQL only as bound parameters. Sort keys come from an allowlist.
8. Migrations are forward-only, and an applied migration is never edited. Dropping a column breaks replicas still running the old code, so after the first release, removals ship one release after the code stops using them.

### Messaging

9. Never call `pg_notify` inside a data transaction. Commit durably, then send the hint in a separate `synchronous_commit=off` transaction. Inline, it capped at about 189 commits/s.
10. Every hint consumer also polls, so a lost hint only adds delay.

### Storage

11. POSIX and S3 behave the same at the `Store` interface. The conformance suite runs against POSIX, SeaweedFS and Garage.
12. S3 credentials come from the environment. Store URIs are persisted and logged, so they never hold secrets: `store.Open` refuses a URI with userinfo or a parameter named like a key, secret, access, token, password, signature or credential, at startup of the process that opens it (a worker for library stores, which api and stream replicas do not read; every role for `transcodeStore`), with an error that names the problem and not the value. The parameters are searched after `;` as well as `&`, in the fragment, and inside the query of a URL-valued parameter such as `endpoint`, plain or percent-encoded. A value with no such name, such as a token in an endpoint's path, can't be told from a gateway's path prefix, so it is accepted and reaches logs like the rest of the URI.
13. ffmpeg reads S3 through the loopback input, never a presigned URL.
14. Direct play is proxied by default, and we always answer HEAD ourselves, because presigned URLs reject it.
15. `http.ServeContent` callers set `Content-Type`, or it reads the object to sniff one.

### Compatibility

16. Routing is case-insensitive and query keys are lowercased once, in middleware. Route wildcards keep their case.
17. `TranscodingUrl` stays Jellyfin-shaped and unsigned. Signing the URLs inside playlists is still to do: today each line carries the client's own token as `ApiKey`, as Jellyfin's do.
18. `PlaySessionId` can be empty in reports, so progress keys on user and item. Coalescing happens in SQL, never in process memory; see invariant 28.
19. `<video>` can't send headers, so media routes accept `ApiKey` in the query.
20. `compat/endpoints.yaml` is generated from `Routes()`, and every alias must be a real obsolete route. Tests enforce both.

### Transcoding

21. Segments are fMP4 by default. MPEG-TS seams break RFC 8216.
22. A segment's frames depend on the spec hash and segment number, not on which worker made them, where the job that made it began or how fast it ran: the same frames at the same times, starting on a keyframe. A copy's video bytes are the same too. A re-encode's are not, from run to run (x264's threads and rate control, measured: `-threads 1` repeats, every multi-threaded setting with the bitrate cap does not), so segments from different runs, a restart's or a helper's chunk (invariant 58), meet as a seam, which players cross cleanly because the times line up (`TestAKilledWorkerIsReplacedWithinSeconds`, `TestThreeWorkersEncodeOneFilmInChunksAndItsVideoEqualsOneWorkers`). x264 keeps its threads: one thread would make the bytes repeat at the cost of a job's speed, which no client needs. Its audio bytes can differ after a restart, on both paths, unless the audio is copied (invariant 52, where the packets are the same and only a Matroska source's times can move, by under 1 ms), because the encoder starts warm and does not continue (invariants 24 and 48); decoded they are the same to within the bound in invariant 48. A copied segment's length follows the layout (invariant 47), as a re-encoded one's is the fixed grid.
23. fMP4 can't splice across encoder families, so failover stays within a family. A copied stream and a re-encoded one are different families: the copy flag is in the spec hash, so their segments never mix.
24. The exact ffmpeg settings in `spikes/seam/README.md` are required, including fixed B-frames and a closed GOP. For x264 that is `bframes=2:b-adapt=0:open-gop=0:scenecut=0`; the seam test in `internal/transcode` fails if a restart drifts from a run from zero. The code leaves out `-to`: a job runs to the end of the file or until it is stopped, because a job's end is decided by who is still watching, not by a time. The cost is one padded AAC frame past the picture at the very end of a run that started late, which the seam test excludes. Frames the decoder marks interlaced go through `yadif` (one frame out per frame in, so timing is untouched) because the output is progressive; `OutputVersion` was bumped for it. A restart opens the video a quarter of a frame before the keyframe it starts on, because ffmpeg 6.1 keeps a frame up to half a frame before `-ss` where ffmpeg 9 drops it, so a cut on the keyframe itself started one frame early on 6.1; `OutputVersion` 3 marks the change.
25. Every job has a kill path, and no ffmpeg outlives its lease. The paths are: `Sessions/Playing/Stopped`, `DELETE Videos/ActiveEncodings` (sent twice, so idempotent), and no request for the spec in `transcodeIdle` (60 seconds), because closing a tab sends nothing, which ends a job paused at its lead (invariant 57) as it ends any other. A worker that loses its lease, can't renew it, or shuts down kills its ffmpeg, and the kernel does if the worker is killed outright. **Losing the liveness lock is not yet losing the lease** (invariant 38, JS-029): when the lock's connection ends, the worker takes the lock again first and only then looks for its own row. A row that is there means nobody touched its jobs, and they go on (a Postgres switchover or restart ends every connection and is not a reason to restart every transcode); meanwhile it claims no new job. A row that is gone means another replica took the worker for dead, and the worker kills every transcode ffmpeg and abandons its jobs at once, and puts its `transcode_nodes` row back only after those ffmpeg are gone and it holds the lock again. A worker that cannot take its lock again goes on the same way, retrying every 50 ms and claiming nothing, and looks for its row every quarter second and at once when a reap forgets it (a hint): it stops when another worker forgets it, inside the half second Reap leaves its jobs, and never because its own lock was lost. That is safe because a worker can never miss a mass disconnect (its own lock connection ends in it), and a live worker takes its lock again within milliseconds while a dead one never does. So a worker forgets another only when all three hold: the node's lock is gone in this look and was already gone in this worker's look at least 0.5 seconds earlier (`reapGrace`/2; a timer runs that second look at 0.5 seconds, not at the next tick); this worker holds its own lock in the same `pg_locks` snapshot (a worker that cannot see its own lock sees nobody's, and only forgets itself); and this worker's own lock has not ended within the last 10 seconds (`reapHold`). A worker that is killed during an outage is forgotten up to that much later, and its jobs end at their lease at the latest. A replica forgets nobody and deletes no row, since it holds no lock and may have missed the outage. A worker without its row claims no job, renews no lease and stores no segment (each of those checks the row), so it cannot stretch the grace Reap gave its jobs, except by a renewal already waiting on the job's row when Reap commits, which still sees the row; the worker stops all the same, and that job is taken over at its full lease. A worker's row is inserted once per lock: if it is gone, the worker was taken for dead and stops as if it had lost the lock, which it finds at its next quarter-second reap even when another reaper forgot it first. No replacement starts while its ffmpeg runs: the half second of lease Reap leaves a forgotten worker's jobs (invariant 37) covers the milliseconds the worker needs to hear of a closed connection, and a lock gone while the connection stands is found by looking at `pg_locks` every quarter second, within that half second, as long as the database answers a look within about a quarter second (a look of up to half a second can bring the stop to the end of that half second or a little past it, so two ffmpegs overlap for a moment; a slower one makes the looks time out, and the worker then stops at its next heartbeat or at the latest its 10 second lease; either way the check before every store keeps it from storing): every worker reaps that often, which is also what lets a viewer whose player has read ahead find a dead worker's job ready to be taken over when it next asks. A worker cut off from Postgres is covered by the check before every store (invariant 37): a segment finished while Postgres is away stays in scratch, nothing is stored until the check passes again, and then it is stored and the job goes on; a job that ends because Postgres was away is `cancelled`, never `failed`, so no spec is refused for it. An outage that outlasts the lease ends the job at its first heartbeat after the lease ran out. The kernel kills the extraction ffmpeg of a subtitle track if the worker is killed outright (invariant 43); a worker that only lost its lock lets a running extraction finish, since extraction leases are not reaped and have one owner throughout.

### Security

26. Tokens are random and stored per device. Passwords use bcrypt. Login failures don't reveal which usernames exist.
27. Paths built from keys can't leave the store's root.

### Play state and sessions

28. Coalescing reads `user_item_data.progress_at`, which only Progress and Stopped write. Playing, favorite and played toggles never touch it, so they can't suppress a report. The first Progress after Playing is stored, unless a Stopped or Progress landed within the last 30 seconds.
29. Runtime comparisons use `numeric`, and `ActiveWithinSeconds` is clamped to about eight years, so no client value can overflow a bigint or an interval. `PositionTicks` is clamped to `playstate.MaxTicks` so stored positions stay sane.
30. A late Stopped or Progress can't move a session: Stopped clears the row and Progress updates it only when its `item_id` matches. Playing always sets the item, so a late Playing can still move it.
31. A device can hold several sockets. Each is a `session_sockets` row, and `sessions.ws_replica` is the newest row's replica, or NULL. Connect and close update both under the session row's lock, in one transaction. Each api replica beats a row of its own in `api_replicas` every second and sweeps every five. A replica is live for 3 seconds after its beat, and `ws_replica` is the newest socket on a live replica, or NULL, so a killed replica's claim is gone seconds after it dies, whether or not the device reconnects and whatever its client's keepalive; the sweep also deletes the socket rows of a replica silent for 30 seconds. A socket's frame (jellyfin-web sends one every 30 s) refreshes its row, makes it again if it was swept while its replica could not reach Postgres, and settles the claim, so a live socket is never left unowned for longer than that. A replica stopping on SIGTERM closes its sockets and removes their rows before it exits.
32. Item DTOs carry the video, the default audio stream, the text subtitle tracks (subrip, ass, ssa, webvtt, mov_text) and the image tracks a transcode can draw (PGS, VobSub, DVB; invariant 51), so the details page offers no track that can't be delivered. A bitmap codec nothing delivers is listed nowhere. `media_sources.streams` keeps the full list. A text track in the DTO has `IsTextSubtitleStream` and `SupportsExternalStream` and no `DeliveryUrl`, because the DTO is stored and a URL carries the caller's token. PlaybackInfo lists every audio stream when transcoding is on, because a stream change can then deliver any of them, and gives each text track its delivery, as the capture shows for direct play and transcode alike: `DeliveryMethod: External` with `IsExternalUrl: false` and a relative `DeliveryUrl` of `/Videos/{item}/{source}/Subtitles/{index}/0/Stream.vtt?ApiKey=...` (`.ass` for ass and ssa tracks). The chosen track a client sends is echoed as `DefaultSubtitleStreamIndex` only where its position in `MediaStreams` equals its `Index`, because jellyfin-web reads that field as a position; where an unlisted stream (a second audio track in direct play, a track of a codec nothing delivers) shifts it, the field stays -1 and the track is still in the menu to pick by hand. When the client names none the field is -1, for the film's own tracks as before and for files beside it: choosing a track from the viewer's subtitle mode needs the user configuration routes that save the mode (`identity`, docs/status.md), and the observation of what Jellyfin does is kept in `compat/captures/subtitles-default-12.4.md`. An external track is listed before any worker has read it, so a file that turns out unreadable is listed until the first job that finds out (invariant 50): this window is the one exception to listing only what can be delivered. `MediaAttachments` (PlaybackInfo and item details) lists a film's fonts only once its fonts manifest exists, and only the fonts in it, so a font that is left out or whose job failed for good is never listed; until then the list is empty and jellyfin-web draws ASS in its fallback font, and PlaybackInfo (or the first ASS track request) starts the fonts job in the background. Menu labels (`DisplayTitle`) read like Jellyfin's, `eng - Default - SUBRIP`, so tracks in one language differ. A source scanned before the scanner recorded which tracks are text lists none until its next scan, which it does without the file changing. The track routes without a start offset are the same handler: `Stream.{format}` takes `StartPositionTicks` and `EndPositionTicks` in the query (the cues that touch the window, both ends included, as Jellyfin 12.4 does; `CopyTimestamps=true` keeps their times, `AddVttTimeMap=true` adds the `X-TIMESTAMP-MAP` line), and `subtitles.m3u8?segmentLength=N` is the VOD playlist of such windows over the film's run time, one per N seconds, with the caller's token on each (`TestSubtitlePlaylistAndWindows`). No track is listed that can't be delivered: where the reply asks for burn-in but this server can't transcode, it lists no subtitle track, and likewise when a transcode store is configured but no worker is running, since the default then plays on. And with no worker running at all (none with the worker role has reported in 10 seconds), nothing can extract a track, so a text track whose extracted object isn't in the asset store is dropped from the film's details (`GET /Items/{id}` and its alias, both `MediaStreams` lists) and from PlaybackInfo, direct play included; cached tracks stay listed, and tracks return when a worker does. This costs one worker query and one asset-store request for each text track, only for one item's details or PlaybackInfo and only while no worker runs. The check can race with a worker coming back, which only hides a track for a moment. A replica that can't open the asset store (no S3 credentials) or gets no answer from it within 5 seconds lists no text track (it can't tell which are cached) and still answers the request, rather than failing or hanging it. Lists (`/Items` queries, Continue Watching, Latest) are not filtered: they cost a store request for every track of every item, and jellyfin-web offers a track menu only for a single item (details page and player). No list view of jellyfin-web shows these tracks: its card builders read only the video stream, and the track menus and media-info dialog load the item with `getItem`, which is filtered.
33. `Content-Type` for direct play comes from the stored container, never from the URL. Matroska and WebM share a container, so only that case also reads the store key's extension.
49. `POST /UserItems/{itemId}/UserData` writes only the fields its body names, in one statement, for the caller; `?userId=` follows Jellyfin 12.4: a non-administrator naming anyone but themselves gets 403 (known user or not), an administrator naming a user writes that user's record and gets it back, an administrator naming nobody known gets 404, and a malformed id gets 400. If the body's `LastPlayedDate` is earlier than the row's `data_at` (when its played state and position were last true; separate from `last_played_at`, which is what clients show as `LastPlayedDate`), the data is older than what the viewer has watched since, so Played, position and LastPlayedDate are dropped and only `IsFavorite` (which has no time) applies; a body with no `LastPlayedDate`, or one equal or later, applies. Jellyfin has no such rule and lets an old body overwrite a newer position. The body's `LastPlayedDate` is held to the database's now (`LEAST`) before the comparison, so a fast client clock cannot outrank every later write. So that a newer change is never undone by an older-dated sync, a write with no `LastPlayedDate` that sets Played or position moves `data_at` to now, and so does marking unplayed through `/UserPlayedItems`, which leaves `last_played_at` alone; a favourite-only write moves neither. A dated write sets `data_at` to the (clamped) body date. The position is clamped like invariant 29. The body must be `application/json`, else 415 as in Jellyfin. Every route takes a valid token in every form `compat.ParseAuth` reads (`Authorization`, `X-Emby-Authorization`, the Emby scheme, `X-Emby-Token`, `X-MediaBrowser-Token`, `ApiKey`, `api_key`); a request with no valid token is 401. This is a deliberate difference from Jellyfin 12.4, which refuses some forms on `UserData`, `Download` and `ClientLog`. It neither clears the position nor counts a play, unlike `/UserPlayedItems`.

### Transcoding, continued

34. A transcode URL's query is the only input to a spec, and every request validates it again, because clients can edit it. A client value reaches ffmpeg only as a bounded integer, never as text, and segment numbers outside the playlist are refused.
35. Segments of a re-encoded stream are 4 seconds, the length the seam spike validated, not the 3 seconds Jellyfin 12.4 uses (`compat/captures/transcode-12.4.md`). Nothing else depends on Jellyfin's length: the client reads durations from the playlist, and the server reads them from the playlist's `Layout` (`playback.Layout`), never from a constant (a segment's bytes are in invariant 22): a copied stream's segments are as long as the source's keyframes make them, up to 12 seconds (invariant 47). For a re-encode the segment length is in the spec hash; a copy's follows the index, which the hash doesn't cover (invariant 47).
36. A playlist is complete VOD with `EXT-X-ENDLIST` and no discontinuity tags, computed from the duration before anything is encoded. A tail under a second joins the segment before it in a re-encoded stream, because the encoder may not cut one; a copied stream's last segment starts where the layout says (invariant 47), not always at the last keyframe, and runs to the end, however short. The duration is where the *video* ends, because the muxer cuts segments only on video and audio that runs longer would otherwise leave playlist entries nothing can produce. A re-encoded stream takes it from the probe (`DurationTicks` on the video stream, else the format duration; Matroska's tag and format duration are ends on the file's clock, so the probe takes the video's start time off them). A copied stream takes it from `media_sources.video_end`, which the scan reads from the packets (invariants 46 and 47), because those durations don't say where the video ends in every case.
37. Any `stream` replica serves segment N: from the transcode store, else by waiting on an active job that will reach it (within three segments of its progress), else by starting a job at N. That check-and-insert runs under a per-spec advisory lock, so concurrent requests start one job. A request replaces the same viewer's previous job, whether it then starts a job or joins another viewer's, unless another viewer's latest wait was on that job (`transcode_viewers.job_id`), which is left running; other viewers' jobs are left alone. The init segment's URL carries no number and any job's first segment brings the init with it, so its request joins a live job, else starts one at the segment the viewer starts at (`StartTimeTicks` is in every segment URL), never at 0 for a resume to replace. A media request for segment N starts its job at N, even below the resume point. A request that cannot be served in time fails with an error rather than hang: 500 with the reason logged if the job failed, 503 once a queued job has waited `queueTimeout` (6 seconds) without a worker taking it, whether none is running or every slot is busy (the log says which). That wait is what lets a worker that is stopping gracefully (not one that is killed) be replaced without the viewer noticing, shown with real processes by `test/roles.sh`: its job is cancelled, the next request queues a new one, and a replacement that arrives within the timeout takes it. jellyfin-web's player abandons a request after 10 seconds, so a refusal must come sooner. Time during which Postgres was away does not count as time in the queue, and a request that needs Postgres (the token, the source row, the viewer, the job) waits for it, up to the usual 90 seconds, and is answered as usual when it is back: a stream replica never answers 400 or more because the database is briefly away, since jellyfin-web ends playback on one. Postgres decides every request while it answers, so a signed-out token is refused at once. Direct play and the segments already in the transcode store go on while it is away, from a snapshot: every stream replica refreshes every 5 seconds, while Postgres answers, the tokens of the sessions seen within a window of 10 minutes (jellyfin-web reports progress every 10 seconds, paused or not, but a tab in the background may report rarely or not at all, so a film paused for up to 10 minutes is still served; a session that reported Stopped plays nothing, and one that nothing has reported on for longer than the window is outside it), each with the film it plays. A stream replica also hears of a start as it happens: the api replica that takes the Playing report sends a notification with the session's token once the session is committed, and each stream replica then reads that one session and its film from Postgres, which has accepted the token, and adds it, so a session that starts a film replaces the one it played before. While Postgres is away a replica honours a token in its last snapshot for byte ranges of that film, for the segments the store holds under the hash of the request's spec, and for a subtitle track, a PGS .sup and a font of that film that the asset store holds (answered as with Postgres up, with no subtitle or fonts job started or joined; a track or font the store lacks, one extracted from a file replaced before the last refresh, another film's, a playlist, a job, a login and every api route wait as above), whichever replica the viewer used before, so the ingress needs no stickiness. A token revoked or signed out after the last refresh stays usable until Postgres is back, which the owner accepted, and a tab closed without a Stopped stays served for the window, which is the price of serving a paused film (ten minutes of a token that no longer plays, for a viewer who left); what remains of the gap for a film just started is under 1 second, since a notification reaches a replica in milliseconds and a film started less than 1 second before the outage may still wait until Postgres is back (a notification lost while a replica's listening connection is down is made good by the next refresh), and closing it costs, per start, one NOTIFY from the api replica and, on each stream replica, one query of the session row and one of the film's sources, a few KB, instead of a refresh of every session; once it answers, every request is decided by it again and nothing is served from the snapshot. If a refresh fails, the replica keeps the last snapshot only while Postgres is away, and drops it for any other failure. A refresh reads a small row per session and per film, and a film's streams and keyframes (megabytes for a long film) only when the replica holds none or the source row changed (its row version), so a refresh reads about 250 KB for 1000 sessions, every 5 seconds on each stream replica, and with 1000 sessions in the window a replica holds about 300 KB (a token, an item id and the film's sources per session), and each film's streams and keyframes once. `GET /healthz` answers from the process alone. 504 on timeout, 410 if the viewer was stopped. The exception to a segment's failure leading to the "cannot be played" dialog before playback is a copied stream whose keyframe index was found wrong: the index is dropped and the next PlaybackInfo re-encodes, with no dialog (invariant 47).
    Before playback has begun, jellyfin-web answers a failed segment by destroying its player and asking PlaybackInfo again, with no limit and no dialog of its own, so a failing stream is a request storm, not an error unless PlaybackInfo refuses (below). After playback has begun it answers a failed segment by dropping the stream: the picture freezes, there is no dialog, and it asks for nothing more. The server can do nothing about that second case from the failed response, so a segment that fails after playback has begun freezes the picture. How long jellyfin-web waits for a segment, from the bundled hls.js 1.6.16 (`web-dist`, jellyfin-web 12.4), which sets only `manifestLoadingTimeOut` and so uses hls.js's default `fragLoadPolicy`: a request that has no first byte after `maxTimeToFirstByteMs` (10 seconds) is abandoned and asked for again at once, up to 4 more times (`timeoutRetry`), then it is fatal; a request answered with an HTTP error is retried up to 6 times by hls.js (`errorRetry`, 1 to 8 seconds apart), but jellyfin-web's own error handler destroys the player on the first error event whose response code is 400 or more, so an error answer ends playback and a silent request does not. A request that waits 10 seconds is therefore asked for again, not an error, but the buffer (30 seconds, 6 for a stream over 25 Mbps) drains while it waits. A worker killed mid-film is replaced by another that continues at the first missing segment, so the player keeps playing, with no dialog and no failed request; with the least buffer there is (killed 1.6 seconds into playback) the picture of a re-encode stood still 2.5 to 2.8 seconds in jellyfin-web and a copy's 0.3 (`test/e2e`, which fails past 7 seconds; the 4.0 to 4.3 seconds below are a Go test's, not a browser's). Every worker takes a session advisory lock on a connection of its own (invariant 25), and every live worker runs `Reap` four times a second (`lockCheck`), which finds the `transcode_nodes` rows that took a lock and no longer hold it: it deletes them, so their slots stop counting, and shortens the leases of their running jobs to half a second from now (`reapLease`), after which every reader of `lease_expires_at` (`state().Dead`, `ensure`, `LiveJob`, `Sweep`) sees the job dead, and the waiting request queues a new one for a live worker, which claims it when the hint arrives. A worker forgets a node only on the three conditions in invariant 25: the lock gone in two looks 0.5 seconds apart, its own lock held in the same snapshot, and its own lock not ended in the last 10 seconds; so a takeover after a kill comes 1.0 to 1.25 seconds after it (the reaper's first look within a quarter second, the second at 0.5 seconds, the lease cut to half a second more). Only workers reap: a replica that holds no liveness lock can miss an outage altogether (an idle pool meets the returned Postgres on a fresh connection and sees no failure) and would forget live workers that are still taking their lock again (`TestAReplicaThatMissedTheOutageForgetsNoLiveWorker`). A replica's PlaybackInfo (`Unavailable`) writes nothing: it counts a `transcode_nodes` row, for workers and slots, only if the row is not locked or its lock is held; and if that makes the answer a refusal while some slotted row is locked but lockless, it asks again every 100 ms for up to a second (`reapGrace`), in case that worker is taking its lock again, and then refuses. When the last worker is killed a new viewer's PlaybackInfo is refused 1.0 to 1.5 seconds after the kill (`TestAViewerIsRefusedWithinASecondAndAHalfOfTheLastWorkerBeingKilled`), and its row stays until a worker forgets it. Measured with real processes (`TestAKilledWorkerIsReplacedWithinSeconds`, ffmpeg at twice the film's speed): from SIGKILL to the replacement's first segment 4.0 to 4.3 seconds, of which about a second is the confirmation and the lease cut (half a second each), up to a quarter second the reaper's first look, and about 2 the first segment; a re-encode that makes a 4 second segment in 4 seconds adds the 2 more, and without the reaper the same test answered after 13 seconds. The bound is exact where the kernel closes the socket, which is any death of the worker's process. Where it does not (host power loss, kernel panic, a partition, a pooler or proxy that keeps the server's end of the connection open) the lock stays and the job is taken over when its lease runs out, up to 10 seconds from the last renewal, as before (`TestAWorkerWhoseConnectionStaysOpenIsReplacedAtLeaseExpiry`): slow, and the dead worker keeps counting as a worker for 10 seconds. Postgres's `tcp_keepalives_*`, if set, make the server drop a vanished host's backend and its lock sooner, and then a worker that is alive but cut off cannot be told from a dead one: `Reap` gives its jobs a second, while its own sockets say nothing and its ffmpeg runs until its own lease check (10 seconds after its last renewal). What keeps that from being two owners is on the store side: `Worker.upload` asks Postgres, before every put, whether the job is still this worker's, running, with an unexpired lease (a query bounded by half the lease, so a database that does not answer is a no), and stores nothing otherwise (`TestAWorkerWhoseLeaseIsGoneStoresNothing`). The same check keeps a worker that was stopped longer than its lease (SIGSTOP of the process, a frozen VM; its ffmpeg, a process of its own, goes on) from storing what it made when it goes on (`TestAWorkerStoppedPastItsLeaseOverwritesNothingWhenItGoesOn`). What remains is a second ffmpeg using CPU until the first finds out, and a put that passed the check and takes longer than the replacement needs for its first segment (seconds), which writes bytes whose video is the same and whose audio can differ (invariant 48). A lock that is gone while the connection stands because a transaction-mode pooler recycled the server's end is found by the worker itself: its own `Reap` through the pool finds its row among the dead, and that is a loss, with a log line that names the pooler (`TestAWorkerWhoseLockIsGoneWithItsConnectionOpenStopsAndLocksAgain`); `Reap` logs the workers it forgets and the jobs it cut short. A Postgres restart drops every lock at once: every worker sees its connection close, goes on, claims nothing and takes its lock again (invariant 25), and none forgets another for 10 seconds after its own lock ended, so no job is restarted. Only a closed or failed connection is a loss, never a slow round trip, so a slow or stopped (SIGSTOP) worker whose connection stands is not reaped, and a job paused at its read-ahead limit (invariant 57) holds its lock and lease. The lock key is `(27219, hashtext(node id))` in the two-int form (so it cannot meet the single-bigint locks, which are `objsubid` 1), matched in `pg_locks` on `objsubid` 2, this database's oid and the unsigned `objid`; two node ids with one hash share a lock, so a dead one is taken for live until its lease runs out. A node that holds no lock (an `api` or `stream` process, a worker of an older version, a row inserted by hand) has `locked` false and is told dead by `seen_at` and the lease alone. Subtitle and chapter-picture jobs keep their 10 second lease, as a dead worker's extraction is read again after it, not served by it. A job whose worker is gone is cancelled and restarted by the next segment request, and a replacement worker that arrives within `queueTimeout` takes the restarted job. Recovering the API replica half of the gate is Phase 4 and not built (`docs/status.md`). The fix for the first case is at PlaybackInfo: it refuses a transcode that can't start now, by answering `ErrorCode: RateLimitExceeded` with no media sources, which jellyfin-web shows as a "Playback Error" dialog saying the media can't be played at this time (`NoCompatibleStream` would blame the client). It refuses when no worker has reported in 10 seconds (`transcode_nodes`, rows with slots), when every worker slot is taken by jobs of other viewers (the asking device's own jobs don't count: jellyfin-web asks for the new stream before it deletes the old), or when the spec's last job failed within 30 seconds of its end (`transcode_jobs.ended_at`), and a segment request in that time gets the failure too rather than start the same job again. A segment failure before playback therefore ends in that dialog: the PlaybackInfo the player asks again is refused, unless the spec has a live job, which is offered (below). The exception is a copied segment that fails because the keyframe index is wrong: the index is dropped, the copy is no longer offered, and the next PlaybackInfo re-encodes with no dialog (invariant 47). A spec that already has a live job is always offered, by every replica, also one with no `transcodeStore`, since a viewer joins it, whatever failed lately and whatever the stores say; if the stores differ, the log warns and names both, and what the viewer then gets depends on the replica that serves the segments. One with no `transcodeStore` answers 503 at once, which sends jellyfin-web back to PlaybackInfo, where the live job is offered again, so before playback the viewer retries with no dialog until the job ends, which `transcodeIdle` bounds only if nobody else is watching it; after playback has begun the 503 freezes the picture as above. One with a store it can't read the segments in waits for them, keeps the job watched, and its request times out. A queued job is live for `queueTimeout` (6 seconds); whoever sees an older one cancels it and workers don't claim it, so a returning worker starts no ffmpeg for a viewer who left. With no live job on the spec, it also refuses when the live `transcode_nodes` rows differ in `transcodeStore`. Every process that takes part, whatever its roles, registers its roles, store URI and (for a worker) slots there with a heartbeat, and a process with no store registers an empty one, so a missing store and a different one are found by the same comparison; the log names both roles and both stores. The one process left out is a worker-only process with no store: it extracts subtitles and runs no transcodes, so it shares no segments with anyone. Nothing else reports a configuration fault. When the viewer's default track plays as it is, a pick of another audio track that can't be transcoded now plays the default instead of refusing, whatever codec the pick has, though the client's menu still shows the track it asked for; when the default track needs the transcode, PlaybackInfo refuses. The one case the comparison cannot see is the same URI on different volumes: a job that ends having stored a segment this replica cannot read is marked failed with that cause, and PlaybackInfo then refuses with it for 30 seconds. A stream replica with no `transcodeStore` answers a transcode request with 503.
38. A job lives while a viewer on its spec who hasn't been stopped has asked for something in the last `transcodeIdle`. Stopping a viewer marks it stopped rather than deleting it, so a request still in flight can't bring it back (`Segment` checks before it starts a job, and answers 410), and cancels at once every job no unstopped viewer is left watching (a viewer watches the job it last waited on, or any of the spec's if it has only read stored segments), so their slots are free for the stream that replaces them. A job whose ffmpeg finishes no segment in 30 seconds (`Worker.Stall`) is failed: the lease is renewed whatever ffmpeg does, and viewers would otherwise wait on it for good. A Stopped report with no `PlaySessionId` stops the device's viewers of that item (invariant 18). Two viewers on one spec share segments and jobs, and stopping one leaves the other's. A job cut short because its worker shut down or died (its lock was gone, or its lease ran out and a sweep found it, invariant 37), or lost to a seek, is `cancelled`: viewers restart it, and the spec is not refused. Only a job that ran and broke is `failed`. A worker whose lock is gone no longer counts toward `Unavailable`'s workers and slots, nor toward the "no worker" answer of a queued job, from the next `Reap` on (invariant 37); a worker only its lease vouches for counts for the 10 seconds `workerAlive` allows.
39. Segments of a spec nobody has asked for in `transcodeRetention` (24 hours) are deleted by a worker's sweep.
40. A segment the encoder flushes when its input ends is cut wherever the input stopped, and ffmpeg exits 0 either way, so the worker stores that last segment only if it is the playlist's last one and its length is within 1.5 seconds of the playlist's (the playlist's own length for it, which is the index's for a copied stream). A job whose input ended early otherwise fails with "the input ended early". `Reader` resumes a cut S3 body (invariant 42), but whether ffmpeg's own reads are exposed to the cut is unproven; this check remains for a source file that is itself cut short. It judges the last segment's length, so a source whose audio alone ends early is not caught; that stays open.
41. A re-encode never exceeds 1080 lines (`playback.MaxHeight`; the deinterlacing of interlaced video is a re-encode's too), whatever the source and the cap, because software x264 at 4K needs more CPU than a worker usually has and the player stalls. Size is in the spec hash, so segments of different sizes never mix. A copy has no such limit, since it costs almost nothing; it is the client's `CodecProfiles` (resolution, level) that decide whether the picture may be sent as it is.
42. An S3 read is one open-ended GET with the caller's context, so cancelling the caller ends the transfer. SeaweedFS can end the body of a GET early, with a clean EOF and no Content-Length error, when a neighbouring GET of the same object is dropped while it is being read, and can answer a resumed range GET with `200`, `Content-Length: 0` and no `Content-Range`; Garage never cut a body in the same tests; whether it can answer that way was not tested. ffmpeg drops a request whenever it seeks. So `S3.Open` turns a body that ends before its Content-Length into `io.ErrUnexpectedEOF`, and a GET sent with a Range that comes back without a `Content-Range` is not that range and reads as `io.ErrUnexpectedEOF` whatever its body; `store.Reader` resumes at its current offset on that error, and also when a known-size object ends cleanly short of its size. Segments are read through a `Reader` of unknown size (`math.MaxInt64`), which cannot tell a clean short end, so `readSegment` treats an empty segment (never legitimate), or one still cut once its `Reader` gives up, as not there yet, and the wait loop reads again. A `Reader` gives up after three reopens without progress. Evidence: on `chrislusf/seaweedfs:latest` (weed 4.50, image created 2026-10-25, not pinned) a probe of raw GETs held while neighbours were dropped found 67 of 200 bodies cut, at 256 KiB multiples, and 0 of 200 on Garage; that probe is not in the tree. `TestDroppedReadDoesNotCutAnother` (100 rounds) drops three neighbours during a held `Reader` read and fails on SeaweedFS with the resume removed (10 of 10 runs, `unexpected EOF`), and passes with it on SeaweedFS and Garage (10 of 10). The cases of an empty 200, a clean short body, an empty segment and a segment that stays cut have tests that fail with each fix removed. No test in the tree shows the cut harming real ffmpeg: a repro of 30 encodes per target kept every frame with the resume on and also with it off, so ffmpeg's own exposure is unproven, and an earlier loopback-input run that lost its input in 17 of 80 encodes was not reproduced. `checkLast` (invariant 40) remains for a source that is itself cut short.
43. A text subtitle track is read out of its file once, whatever the number of requests and replicas, by a worker: only workers run media tools (ARCHITECTURE rule 1), so `api` and `stream` run no ffmpeg or ffprobe, and `test/roles.sh` and `test/e2e/run.sh` run them with none on their PATH. The first request for an uncached track (`transcode.FetchSubtitle`) inserts a row in `subtitle_jobs`, keyed by the object it will become, `subtitles/{source}/{hash of the ETag}/{index}.json` in the library's asset store (a track that is a file beside the film has `-{the file's fingerprint}` after the index, invariant 50), with `ON CONFLICT` replacing only a done or failed row older than 30 seconds, so one live row exists per track however many requests, replicas and burn-in jobs ask. It is a table of its own, not rows of `transcode_jobs`, because an extraction has no spec, viewer or owner and must not count against transcode slots, `Unavailable` or the queue timeout. A worker claims it with `FOR UPDATE SKIP LOCKED` (`Worker.RunSubtitles`), runs one ffmpeg into every format (vtt, srt, ass; js is made from the vtt) through `store.Input` so S3 sources need no credentials in argv, and puts the result in the asset store as one object, so a reader never sees half of it. The requests wait on the asset store, which is the result, and on the row (every 500 ms and on the `subtitle` hint, which transcode claimers don't listen for). A worker runs at most four extractions at once on a semaphore of its own, never the transcode slots, so an extraction proceeds while every transcode slot is busy, which matters because jellyfin-web fetches a subtitle once and doesn't retry. A burn-in job asks for its track the same way and waits holding its transcode slot, as it did; the extraction itself runs on a subtitle slot, of this worker or another. The row has a lease the worker renews, and a worker killed mid-extraction (ffmpeg dies with it) loses it: after at most 10 seconds another worker claims the row again, with `attempts` incremented on each claim; a lease lost after the third claim fails the row instead. An ordinary ffmpeg failure (a file that is garbage or gone) fails the row at once, without retry, with the error text. A failed or done row is replaced only after 30 seconds (`failureMemory`), so within that window every request for a track that couldn't be read gets the 500 "the subtitle track could not be read" at once, logged with the item, source, index and the worker's error, and the file isn't read again; later the next request queues it afresh. A request waits as long as a live worker is on the job (a claimed row with a lease that is renewed), which for a big file on S3 is as long as reading it takes, up to the extraction's own limit of an hour (`subtitles.DefaultTimeout`, named in the error) and two hours in all; a worker that is stopped gracefully puts its job back in the queue. With no worker running (no `transcode_nodes` row with the worker role seen in the last 10 seconds), or a row that stays unclaimed (queued, or its lease lapsed) while no extraction is running anywhere, for six seconds (`queueTimeout`, the same wait as a segment's) the request answers 503 and the row stays queued for the worker that returns; so no request hangs. That covers a worker from before subtitle jobs, which reports in as a worker but never claims them. A row queued behind busy workers isn't refused: an extraction holding a live lease shows jobs are being claimed, so the request or burn-in job waits its turn, because jellyfin-web asks once and a refusal would lose the track. A worker cut off from the database stops its extraction on a timer that only a successful renewal puts off, one heartbeat before the lease can lapse however its renewals fail, so a partition doesn't read the file twice; the job is then taken over like a killed worker's. Waiters read the asset store only once the row says done, so a long extraction costs each a query every 500 ms and no store requests. Uncached tracks are listed whenever a worker reports in, so during an upgrade the workers must be replaced before `stream` and `api`. A cached track is read from the asset store with no job and no worker. Only a text track of the source, an index in `media_sources.streams` that the probe marked, is served; any other index is 404, as is a name that is not `Stream.*`; a format other than vtt, srt, js or ass after `Stream.` is 400, as captured. A non-zero `startPositionTicks` moves every cue earlier by that much and stops at zero, as the capture shows; ASS keeps its styles. Times are counted from the source's start time, as ffmpeg extracts them. Start and end of an extraction are logged at Info with the item, source, index, file size and duration. Extraction gives cues on the viewer's clock, which starts at zero, on ffmpeg 8.1 and 9.0; ffmpeg 6.1, which CI installs, also applies a negative start such as AAC's, so cues there can be 23 ms late, which burn-in cancels and nobody can see. ffmpeg runs with `-v error`, and any output at all, which is how it reports a file cut short while exiting 0, fails the extraction and caches nothing. jellyfin-web makes one subtitle fetch and passes no timeout to it: the bundle's `fetchWithTimeout` applies only to callers that give one, and neither the captures nor the code name a limit; Chromium held such a fetch for 200 seconds and then took the answer, so only a proxy in front bounds the first extraction in a big file, and the extraction continues for the next request to find. The only related figure is Jellyfin's server-side `SubtitleExtractionTimeoutMinutes: 30` (`compat/captures/transcode-12.4.json`). The 503 for no worker is what the `test/roles.sh` check with real processes measures, under ten seconds. After a client-rendered subtitle is picked in a transcode, switching audio leaves jellyfin-web's track disabled with no cues until re-picked; real Jellyfin 12.4 does the same, so it is a client limitation and the server does nothing about it.
44. A subtitle is burnt into the picture only when it can't be shown any other way: the client's DeviceProfile has no `SubtitleProfiles` (jellyfin-web sends none when the viewer's setting is to burn all), or the viewer has chosen to always burn in when transcoding and the film is transcoded anyway. Then PlaybackInfo marks every text track `DeliveryMethod: Encode` with no `DeliveryUrl`, a chosen text track goes in the TranscodingUrl as `SubtitleStreamIndex`, in `Params` and in the spec hash, and `SubtitleCodecNotSupported` joins the reasons; with no `SubtitleProfiles`, that reason alone forces a transcode, even at Auto bitrate. A client that shows subtitles itself is told nothing of them in the TranscodingUrl, and choosing one causes no new PlaybackInfo, no job and no playlist change. Another burnt track, or none, is another spec, replaced like an audio switch: PlaybackInfo, `DELETE ActiveEncodings`, a new master. (An image track is drawn another way: invariant 51.) The worker draws the track as ASS from a file in its job directory after the scale, with the cue times moved later by the source's start time because `-copyts` keeps frames in the source's own clock and extraction does not; a restart at any segment therefore draws the same text at the same moments (`TestBurnedSubtitleIsAtTheRightTime` restarts at segments 3, 6 and 9, a source with a 7.5 s start included, and fails without the shift). No client text reaches ffmpeg's arguments: the index is an integer (invariant 34), the file name is fixed. The job's first start for a track waits for the extraction (invariant 43), which another worker or this one makes through a subtitle job, shared with every request for the track, before ffmpeg starts, and its scratch directory is made after the read, so the sweep of idle directories can't remove it, and the worker renews the job's lease meanwhile, so a long extraction is not swept; it stops waiting, and frees its slot, if the job is lost or no viewer is watching. The extraction continues for the others. The viewer's player gives up on a segment after 10 seconds and asks again, so the first burn of a track in a big file shows a still picture until the read ends; this was not measured on a big file, only the small fixtures were. When the worker slots are all taken and the default track plays as it is, a chosen burnt-in subtitle is dropped with the audio pick (invariant 37).

50. A subtitle file beside the film (`.srt`, `.ass`, `.ssa`, `.vtt` whose name is the film's name, then dot-separated words, then the extension; same directory, either store) is a text track like any other. **The scan only lists it**: it finds the files in the listing it already makes, reads their names, fingerprints each (a hash of its key, size and ETag) and writes streams to `media_sources.streams`; it converts nothing, extracts nothing and writes nothing to the asset store, and its transaction holds rows only. A test counts the scan's tool runs and the asset store's objects. The entry has `IsExternal`, `IsTextSubtitleStream`, `Path` (the store key), `Fingerprint` (kept out of the DTO), and from the name: `Language` (ISO 639-3, or the tag as written for `pt-BR`), `IsForced` (`forced`, `foreign`), `IsDefault` (`default`), `IsHearingImpaired` (`cc`, `hi`, `sdh`), `Title` (the words that are none of these, in Jellyfin's way) and a `DisplayTitle` like Jellyfin's ("Japanese - Hearing Impaired - Default - Forced - SUBRIP - External"). **A worker converts it when asked**, through the subtitle path of invariant 43 (`transcode.FetchSubtitle`, `subtitle_jobs`, `subtitles.Fill`): one job per fingerprint, whoever asks, with the key `subtitles/{source}/{hash of the film's ETag}/{index}-{fingerprint}.json`, so an edited file has an object of its own and the old stays. The job reads the file (not the film), at most 16 MB, and converts UTF-16 itself (with or without a byte order mark: every other byte zero) because ffmpeg reads it unreliably, passes UTF-8 as it is, and for any other bytes asks chardet (`github.com/saintfish/chardet`, ICU's detector in Go) for its ranked results and converts the file to UTF-8 itself with the first that decodes the bytes (`subtitles.legacyText`), so ffmpeg sees UTF-8 and is given no `-sub_charenc`. The language in the file's name (`Language` of the stream) breaks a near-tie only: a lower ranked result that decodes too, is within `tieMargin` (10 points of chardet's 1 to 100) of the best and that chardet reports for that language wins; a clearer result is never overridden. UTF-8 with a few bad bytes (at most a tenth as many as its non-ASCII characters) or a last character cut short stays UTF-8 with those bytes dropped, and does not go to chardet (`mostlyUTF8`). Stray control bytes (NUL, VT, FF, ESC) never make a file unreadable: they are removed from the UTF-8 text before ffmpeg, which refuses a file that starts with NUL or ESC and loses the cues from a NUL on (`TestExtractFileToleratesStrayBytes` sends them through ffmpeg; `TestToUTF8IgnoresESCBeforeDesignator`: a stray ESC is always dropped, so ISO-2022 files are not supported, and docs/subtitles.md names the remedy of converting them to UTF-8); a legacy file's last character cut short is dropped. A store that stops answering while a track is read out of the film is the job's failure and not `ErrBadFile` (`TestFillStoreFailingMidReadIsNotTheFilesFault`). The file is refused only when no ranked result decodes the bytes. The detector is wrong for some files, and this is accepted and not worked around (docs/subtitles.md lists them): Windows-1250 and ISO-8859-2 text is read as Windows-1252 or 1254 (chardet's ISO-8859-2 recognisers report ISO-8859-1) and Thai as a CJK set; the remedy is for the operator to convert the file to UTF-8 (`TestLegacyText` has formal Shift_JIS, GBK and Big5 with and without a `zh` name, KOI8-R Bulgarian, Windows-1251 Russian and Icelandic Windows-1252, `TestLegacyTextToleratesStrayBytes` the control bytes and a cut Shift_JIS file, `TestLegacyTextKnownLimit` the limits). UTF-16 without a byte order mark is told by the `-->` or `Dialogue:` that every subtitle format holds, written as two bytes at an even offset. **A file that can't be read for good is remembered**: a failure that is the file's (`subtitles.ErrBadFile`: bytes none of chardet's results decodes, a file over the limit, ffmpeg exiting with an error status on the data, or exiting 0 after complaining) makes the worker log a warning that names the file and set `Unreadable` on that stream in `media_sources.streams` (`library.MarkUnreadable`, in one transaction that also rebuilds the item's DTO without the track), tied to the stream's `Fingerprint`; a rescan keeps the mark while the fingerprint is the same and drops it when the file changes, so a bad file costs exactly one job per fingerprint (a test requests, rescans, requests and rescans, then edits the file). A failure that is not the file's (the store didn't answer, a timeout, a lost lease, no ffmpeg, ffmpeg killed by a signal, a full disk) is only the job's (`TestOnlyAnErrorExitOnTheDataIsABadFile`, `TestKilledConversionKeepsTheTrack`): it is the row and `failureMemory` of invariant 43, and the track stays listed. **Listed means deliverable (invariant 32), with one exception**: the track of an unread file is listed until the first job reads it, so a bad file is offered once and the request that finds out gets the 500 of invariant 43. Without a running worker a track that has not been converted is hidden like any other. **Indices**: the film's own tracks keep their indices and the files follow from the next after the last of them; attachments do not count, since ffprobe numbers them after the tracks and a client reads `DefaultSubtitleStreamIndex` as a position in `MediaStreams`, which lists them apart (a test checks that position equals `Index` for a film with fonts), in file name order for those new at one scan. `media_sources.next_index` is a counter that survives the scan replacing the row; a file keeps the index it has while it exists (found by `Path` in the stored streams) and a new one takes the counter, which only grows, so the index of a removed file is never given again, even to a file added later (a test removes one, adds another and brings the first back; a film that comes back with more streams of its own than a file's index renumbers that file). (`TestIndicesAreNeverReused` removes the highest file and adds another; `TestRescanNoticesSubtitleFiles` does that across a replaced film.) A burn-in URL that names a file found unreadable since is read as naming no subtitle (`playback.ParseParams`), so the segments not yet made are drawn without it, from a spec of their own, instead of every one failing; segments already made keep it, and the player is not told. A viewer who holds an index never finds another file's text under it, and a removed file's index is refused (404 for a track, 400 for a burn-in URL, like a film that has been removed or changed) (except across a scan by the version before this one, during a rolling upgrade, which forgets the numbering; see the upgrade note in docs/subtitles.md). Delivery, burn-in and the decision take the track by index as for an embedded one. A burnt-in file's fingerprint joins the spec hash (`Spec.SubtitleFingerprint`), which for a track inside the film is unchanged, so segments already stored stay found, and a job whose file has changed fails like one whose film has. The scan keeps a fingerprint of the set of a film's subtitle files (`media_sources.sidecars`, on the row an older version's scan rewrites without it, so a scan by that version makes this one list the files again: `TestRescanAfterAnOlderVersionsScanListsTheFilesAgain`); when only that differs it lists the files again and rewrites the stored streams and DTO without probing the film or reading its keyframes, so a subtitle added beside a 40 GB film on S3 costs nothing from the film. A film scanned before the files were listed (`sidecars` NULL) is probed again at its next scan only if it is Matroska, the one container whose attachments matter, and its stored keyframe index and video end are kept, not read again (a film without an index, or that was never probed for its range, is probed in full as at any scan); any other film only has its files listed, as for a changed set of files. A probe is stored as soon as it ends (not after all of them), the scan logs how many films it is probing and every 100 how many are done, and a scan stopped half way keeps the films done, since each sets its `sidecars` (`TestUpgradeScanProbesMatroskaAndKeepsItsWork` stops one while a probe is held, then counts the second scan's tools).  **Fonts**: the probe's attachment streams are stored as `Type: "Attachment"` entries (`FileName`, `MimeType`) and `MediaAttachments` lists the fonts among them (the MIME types jellyfin-web hands to its ASS renderer). The first PlaybackInfo, ASS track request or burn-in of the film has `transcode.StartFonts` (no wait) or `transcode.FetchFonts` (waits, for the burn) queue one job of its own kind (`subtitle_jobs.kind = 'fonts'`, keyed by the object `attachments/{source}/{hash of the ETag}.fonts`, a JSON list of the SHA-256 of each font by attachment index) per film version, however many fonts and requests; the worker runs one ffmpeg that dumps all the fonts to its scratch disk (it maps no frames, so it reads little more than the file's header) and puts each from its file, never whole in memory, at `fonts/{sha-256 of its bytes}` (the fonts a season's episodes all carry share an object, which a new run overwrites with the same bytes, so a font cut short in the store is replaced), then the list last; a font over 64 MB is left out and logged. The attachment route (`stream` role) does not wait on that job: it serves a font in the manifest, and answers 404 for an index that is not in it or when there is no manifest yet. A font the manifest lists whose object is gone from the store is answered with an empty body and `Cache-Control: no-store` (a 404 stalls jellyfin-web's renderer, which draws the track in its fallback font with an empty font) and runs the fonts job again at once; a font body the store cuts short (an error, or a hash that does not match, since the whole font is read before headers are sent) gets the same empty 200 and a log line (`TestCutFontBodyIsAnsweredEmpty`). A font ffmpeg did not write (exit 0, no file) is left out like one over the cap. A burn-in job of an ASS or SSA track (and only those: the others name no font) waits on it holding its transcode slot, puts the fonts in a `fonts` folder of its scratch directory, and the subtitles filter has `fontsdir=fonts`, so libass draws the track in the film's fonts as jellyfin-web does (`TestBurnDrawsWithTheFontsOfTheFilm` gives fontconfig no fonts, so the text appears only if the job put the film's font in place; `TestSubRipBurnDoesNotWaitForFonts` shows a SubRip burn makes no fonts job). The segments of a burn are kept under a hash that does not name the fonts, so a burn drawn without them is what every viewer gets for 24 hours; a failure to get the fonts that may pass therefore fails the burn job, to be asked for again, and only the film's own failure burns without them. **Transient** (store error, signal, full disk, lease loss, no worker, the fonts job failed): the burn fails with `fonts of the film:` and keeps nothing (`TestAssBurnFailsWhenTheFontsJobFailedTransiently` a failed job and then, once it is forgotten, a burn with the fonts, `TestFontsThatCanNeverBeReadAreNotTriedAgain/killed_by_a_signal` a signal). A fonts job that fails is `failed` with `permanent` false, which `awaitJob` answers as `ErrJobFailed`, not `ErrUnreadable` (that is for a file that is bad for good, or a job given up after its lease was lost three times), and it is run again once `failureMemory` has passed. **Deterministic**: ffmpeg exiting with an error status on the attachments (`isBadFile`) is logged as an error and `FillFonts` stores an empty list for this version of the film (the key has its ETag, so the memory is per film version and ends when the film is replaced), the job is done, and the burn goes on without fonts (`TestFontsThatCanNeverBeReadAreNotTriedAgain/an_error_exit`). A listed font whose object is gone from the store, or whose bytes do not hash to its name (checked while copying), when a burn opens it (a bad one is deleted first) makes the burn run the fonts job again and wait for it, then burn with the restored fonts on the same request (`TestAssBurnRestoresALostFont`, `TestAssBurnRestoresACutFont`); only a failure of that job fails the burn. ffmpeg warnings with exit status 0 are not failures; the fonts that were written are kept (`.../a_warning_and_exit_0`). A font's bytes are named by their hash, but the URL names an attachment index, so a client's copy is not immutable: the route answers with `ETag: "{SHA-256 of the font}"` and `Cache-Control: no-cache`, and 304 for a matching `If-None-Match`. **Authentication departs from the capture**: Jellyfin's attachment route needs no token and its `DeliveryUrl` has none (`compat/captures/subtitles-12.4.md`); jellyscale's route is authenticated like the subtitle route, and PlaybackInfo's `DeliveryUrl` carries `?ApiKey=<the caller's token>` as a subtitle's does, which jellyfin-web follows as it follows any `DeliveryUrl`. Neither the subtitle route nor this one checks which libraries a user may see, because no route does: per-user library access is not built (docs/status.md), so there is no check to share. **Cost** (ARCHITECTURE rule 6): the scan adds no request to the media store (the files are in the listing it makes, the attachments in the probe it makes). The one scan after the upgrade reads the header of each Matroska film again and one frame for its image, and nothing of any other film. A conversion reads the file once and writes one object of about three times its text (vtt, srt and ass in one JSON), a few KB to tens of KB, once per file version and library, and the object is read from the asset store by `stream` for each request. The fonts cost one read of the start of the film per film version and a write of every font (CJK fonts reach tens of MB each; an asset store holds each distinct font once, however many films carry it, and a font is never deleted, though a sweep by hash is now possible. Each burn-in of a film copies its fonts from the asset store to the worker's scratch disk, their size in network, once per transcode start), a read of one font per request for it (jellyfin-web asks for every font of the film each time it plays an ASS track), and scratch disk on the worker of their size while the job runs. Postgres: an integer and a 64 character fingerprint on each `media_sources` row, about 400 bytes of `streams` JSON for each subtitle file and 100 for each attachment (and as many more in the item's DTO), and one `subtitle_jobs` row per converted file version and per film with fonts, swept a day after it ends. `test/roles.sh` and `test/e2e/run.sh` show this with the other roles having no ffmpeg.

51. Image subtitle tracks (PGS, VobSub, DVB) are listed, and delivered by track and by what the client says it draws; `compat/captures/image-subtitles-12.4.md` has the observation of Jellyfin 12.4 and jellyfin-web 12.4 this follows. **Listing:** the probe records them (`imageSubtitleCodecs` in `library/probe.go`, one list beside the text codecs) with `IsImageSubtitleStream` and Jellyfin's names for the codecs (`Codec` `PGSSUB`, `DVDSUB`, `DVBSUB`, ending `DisplayTitle` too), `Width` and `Height` of the track's canvas when the stream has them, and `SupportsExternalStream` for PGS alone, because only PGS is delivered as a file. Any other bitmap codec (HDMV text, XSUB) stays in `media_sources.streams` and is listed nowhere (`playableStreams`). The codec is decided at scan time, from the probe already stored, so `api` never runs ffprobe to find it. **Delivery:** a client whose profile has `pgssub` `External` (jellyfin-web sends it once its viewer turns PGS rendering on) is given a PGS track as the file: `DeliveryMethod` `External`, `DeliveryUrl` `.../Subtitles/{index}/0/Stream.pgssub?ApiKey=...` (`Stream.sup` is the same file, as in Jellyfin). A worker makes the file by a subtitle job of kind `sup` (`transcode.FetchSup`, `subtitles.FillSup`, migration 0012): `ffmpeg -map 0:N -c:s copy -f sup`, put in the asset store as a plain object `subtitles/{source}/{hash of the ETag}/{index}.sup`, not a field of `Track`, which is JSON, so a role that serves it neither decodes nor holds it. It shares the job queue, the four extraction slots, `failureMemory` and the wait of invariant 43. `stream` sends it from the store with ranges (jellyfin-web probes with `bytes=0-0` before it fetches the file, as the capture shows), from one listing of the film's directory in the asset store for the size and ETag; `api` only checks that it exists, as for text, when no worker runs. Every other case is drawn into a transcode: PGS for a client that doesn't draw it or whose setting is to burn, every VobSub and DVB track whatever the profile says (jellyfin-web would draw VobSub from a `.mks` file, which jellyscale doesn't make), and a PGS track under the viewer's "always burn in when transcoding" setting. Such a track is `DeliveryMethod: Encode` with no `DeliveryUrl`, and is listed only when this server can transcode (invariant 44). Choosing one is `SubtitleCodecNotSupported` and a transcode, and never a copy; `Source.Burnable` (text, or an image track the probe marked) is the one test the decision and `ParseParams` share, and `Request.clientShows` says whether the client draws a track itself. A format the track doesn't have (PGS as `.vtt`, a text or VobSub track as `.sup` or `.pgssub`) is 400, as in Jellyfin; an index that is no track, 404. **Burning:** `Command` takes the track from the video's own input (`-filter_complex`: the track scaled to the output's size, then `overlay=eof_action=pass:repeatlast=0`, with `-canvas_size` from the stream's size as Jellyfin passes it), so no subtitle job, file, font or wait comes first, and the worker chooses the path by the codec next to the check for `ass` (`Source.ImageSubtitle`). The spec hash has `|sub{index}` as for text. The overlay doesn't hold the video for a track with few packets: ffmpeg gives it a frame whenever the video moves, so a film that arrives slowly is drawn as it arrives, not when the track's next packet does (`TestBurnedImageSubtitleDoesNotWaitForTheNextCue`: a film served at about 12 times its speed, whose only cue is in its first 14 seconds, has more than ten of its thirty segments when half of it has been read). `-readrate` is the exception, which waits for such a track, so a transcode that draws an image track must not be run with it (the e2e harness, which throttles transcodes, throttles the audio input of those runs instead); `TestBurnedImageSubtitleIsAtTheRightTime` also has a track silent for its film's last ten seconds, and runs PGS, VobSub and DVB. **Runs mid-film:** a PGS, VobSub or DVB cue is one packet when it appears, so a run that begins at segment N > 0 would not see a cue that began before its keyframe. Where the track's packets lie comes from the Matroska Cues, which the scan already reads for the video's keyframes: `library.ReadImageCues` keeps a point (time, cluster, offset in the cluster) for each packet the Cues list for each image track inside the film, in `media_sources.image_cues` (migration 0019; a column of its own, about 30 bytes a packet, that no item read selects). The cost **per film** is one read of the film's head and its Cues, a few hundred KB of a film of any size, in the scan that stores it, and for a film an earlier release stored by the next scan alone, from the stored streams and without a probe (`TestTheNextScanOfAFilmTheLastReleaseScannedReadsNothingThatGrowsWithTheFilm`); no read of the whole film, in the scan or in a job, to learn cue times (`TestTheScanReadsNoMoreOfAFilmForItsImageTrackAndNothingThatGrowsWithTheFilm`, `TestTheFirstMidFilmRunReadsTheSameInAFilmFourTimesAsLong`). The cost **per run** (a seek, a failover, a helper's chunk): the worker reads the packet of the last point at or before the cut (`ImageTrack.PictureAt`: the cluster's header and then the block, two ranged reads of a few hundred bytes), says from it whether a picture is showing (PGS: the composition's object count; DVB: the regions of the page composition; VobSub: the block's duration) and, for a PGS or DVB packet that only adds to the picture (composition state 0), reads the packets before it back to the one that starts it (state 0x80 or 0x40; a PGS picture built by two packets is drawn whole, `TestAMidFilmRunDrawsAPGSPictureBuiltByTwoPackets`). The reads are the same whatever the film's length and however long ago the cue began, in a run that fails them (a store error, a timeout) the job fails and nothing is stored without the cue, and they end with the job (`TestAFailedReadOfTheCueTimesNeverLeavesASegmentWithoutTheCue`, `TestEveryReadOfAMidFilmRunEndsWithItsJob`). `Command` opens the film one second before the first packet of that picture, and drops the frames before the cut with a `trim` filter (not `-ss`, whose first frame differs between ffmpeg 6 and 9). **Extra reading by the cue's age:** with nothing showing, the run opens where it did and reads no more than a run without the track; inside a cue it reads, and decodes and drops, the film from the cue's first packet (and the keyframe before it) to the cut, so its cost grows with the **age** of the showing cue and no more (`TestARunInsideACueReadsOnlyTheFilmFromTheCuesFirstPacket`: a cue 8 s and 56 s old; docs/transcoding.md has the measurements). A cue that is never cleared (a last cue with no clear packet) is showing for the rest of the film, and a run long after it pays for all of that age; there is no cap, because a cap would give up a cue that is on screen. A seek, a failover and a helper's chunk therefore draw the cue showing at their first frame, with a run from zero's frames at its times (`TestASeekIntoABurntImageCueShowsItFromTheFirstFrame`, `TestAFailoverInsideABurntImageCueShowsItFromTheFirstFrame`, `TestABurntImageSubtitleGetsHelpers`, `TestAMidFilmRunDrawsTheCueAFilmFromZeroShowsAtItsCut` for PGS, VobSub, DVB and a PGS remux with compressed blocks, and for MPEG-2 with VobSub). A run from segment 0, and a track beside the film (its own input, read from its start), read nothing extra, and after a film's file is replaced the new file's points are the ones used. **What can still miss a showing cue:** a film that lists no points for the track: MPEG-TS (it has no index), a Matroska file written without Cues for the track or with Cues for the video only, and a track whose blocks are encrypted or compressed in a way other than zlib or header stripping, or whose VobSub block has no duration. A run on such a film opens `cueLookback` (10 seconds, the look-back) before its keyframe, with no read of the whole film: it reads at most the look-back more than a run without the track, draws a cue that began within it from its first frame, and misses one that began earlier until the next cue (`TestAMidFilmRunOfAFilmWithNoCueTimesDrawsACueWithinTheLookBackAndMissesAnOlderOne`, `TestAMidFilmRunOfAFilmWithNoCueTimesReadsAtMostTheLookBackMore`). That is the one remaining gap, which ARCHITECTURE lists. **Cost (ARCHITECTURE rule 6):** copying a PGS track reads the whole film from the media store once for each track of each film, because ffmpeg has to find the track's few packets in a Matroska file (a 40 GB remux is 40 GB of reads), as extracting text does; it stores the track's size in the asset store, a few MB, and one `subtitle_jobs` row. A burn costs no more network (the track's packets arrive in the video's read) and no storage; its database cost is the film's cue points (above), read with the film's other columns by a worker once per job and written by the scan; its CPU is a scale and an overlay for each frame, and the decoding of the bitmaps. **Upgrade:** a film scanned before this has no `IsImageSubtitleStream`, so a scan probes it again (not its keyframes) when it has a track that isn't text, and then lists the track; until then it is as before. A Matroska film with an image track and no stored cue points (`image_cues` NULL) has them read by the next scan, which reads its head and Cues and nothing else; until then its runs open the look-back early. Workers must be replaced before `api` and `stream`, or an old worker takes the `sup` job for a track and fails it. **Roles:** `test/roles.sh` fetches a PGS file through two `stream` replicas with no ffmpeg and burns VobSub through ffmpeg-less `api` and `stream` processes, and `test/e2e/run.sh` plays both in jellyfin-web, on POSIX and S3. **Where jellyscale differs:** a track's `DisplayTitle` has the language code, as the film's text tracks do (Jellyfin: the language's name); a DVB track's canvas is stretched to the picture (Jellyfin scales it by height and pads it); no track is chosen when the client names none (Jellyfin burns the one flagged default).


52. **Audio is copied while the video is re-encoded** when the client takes the track as it is (`Source.copyAudio`; observed in `compat/captures/audio-copy-12.4.md`). The decision is made from the URL and the source alone, as invariant 34 requires, and `Decide` (to split the cap) and `NewSpec` (the spec, rebuilt on every request) call the same function: the track's codec is in the URL's `AudioCodec` list, which `Decide` takes from the same fMP4 HLS transcoding profile that `hlsProfile("h264")` matched and `ParseParams` cuts down to AAC, MP3, AC3, E-AC3, Opus and FLAC; its channels are within `TranscodingMaxAudioChannels` (the profile's `MaxAudioChannels`, 2 if it has none; a URL value that is missing, not a number or outside 1 to 8 is 2, not a 400); the master playlist can name it (`audioCodecString`: AAC LC, HE-AAC and HE-AACv2, MP3 `mp4a.6B`, `ac-3`, `ec-3`, `Opus`, `fLaC`; AAC Main and every other codec are encoded); and it takes no more than a quarter of the cap (a deliberate choice, tested at its boundary: a copy that took more would starve the picture), which is the sum of the URL's `VideoBitrate` and `AudioBitrate`. A copied track's own bitrate is the URL's `AudioBitrate` and comes out of the picture's share (`Decide`), as in Jellyfin's URLs. A track of unknown bitrate counts as 6 Mbps, in the master playlist's `BANDWIDTH` as well as against the cap: it copies at Auto and under caps of 24 Mbps and up, and is encoded under any smaller cap. `Stream.Bitrate` is the `BitRate` the scan already stored (ffprobe's, else Matroska's `BPS` tag, read from this version on); no rescan is forced, so a film scanned before it has what it had, or nothing, and nothing in the schema changes. A CodecProfile that fails for the track (`limits("VideoAudio")`) takes its codec out of the list `Decide` writes, so a client can't ask for it back by keeping the URL: it can only edit its way to a copy of a track the source really has within the limits the URL itself states, which costs the operator the bytes of that track and nothing else. `Spec.AudioCopy` is the codec name; in the hash it is `|acopy<codec>` and only when set, and `AudioBitrate` is the track's own, so Auto and a cap that leaves the track alone share segments, and the hash and `OutputVersion` of a re-encoded track are unchanged. The master playlist's `CODECS` carry the copied codec. **A copied video copies the audio by the same test** (`Spec.Copy` with `AudioCopy`; its hash adds `|acopy<codec>` to `|copy`, and a copy that re-encodes the audio keeps its hash); a track the test refuses is encoded on the AAC grid that the fragment joiner relies on (invariant 48). **A restart splices the same packets.** (For an MP4 source the audio in each segment is byte for byte identical, times included; for Matroska the packets' data are identical and their times can differ by under 1 ms, because Matroska stores whole milliseconds. This is accepted, not a defect.) Copied packets are the source's own, so `Command` needs no grid and no warm-up: it reads the audio from two seconds before the segment and drops, with `-bsf:a noise=drop=lt(pts*tb\,T)`, what falls before the keyframe's DTS (the cut the muxer makes, as for the AAC case, from `firstFrameAt` and `reorderFrames`; no timebase is needed because the filter compares seconds; the threshold is a microsecond early, so a packet exactly at the cut stays). `TestCopiedAudioSplicesTheSamePackets` runs restarts at segments 1, 5 and 9 for AAC (48 and 44.1 kHz, MKV and MP4), AC3, E-AC3, MP3, Opus and FLAC, and a source that starts late, and finds the same packets, byte for byte (sha256 of each), in the same segments, the same init segment and no decoder warnings; the packets' times agree exactly for an MP4 and within 1 ms for Matroska, whose timestamps are whole milliseconds (ffmpeg derives later packets' times from the first's, so a restart's can be up to a millisecond from a run from zero's). The test fails with a threshold 0.1 s early or 10 ms late. `-strict -2` lets older ffmpegs write FLAC and Opus into MP4. **Cost.** Worker CPU falls (no decode, downmix or AAC encode); the source is read as before (a restart opens it twice, as in a re-encode). `stream` bandwidth, S3 reads and stored segments grow by the track's bitrate less 192 kbps: a 640 kbps AC3 track adds about 0.45 Mbps per stream (100 streams add about 45 Mbps and each stored hour of segments about 0.2 GB), FLAC's 1 to 4 Mbps ten times that; segments are kept for the usual 24 hours and the target-scale design is unchanged. Postgres: nothing but a few more characters in the hash text. The risk not measured: a client whose profile lists a codec its hardware stutters on at a high bitrate; its CodecProfile limits are honoured and its other limits are not known.
53. **An HDR picture that is re-encoded is tone mapped to SDR BT.709** (`Source.ToneMap`, `transcode.toneMap`; observed in `compat/captures/hdr-tonemap-12.4.md`). The decision is made from the source alone, so a client can't change it by editing the URL (invariant 34), and it is the spec's `ToneMap` field: the transfer function, `smpte2084` (PQ) or `arib-std-b67` (HLG), or empty. It follows the transfer function the file declares (`media_sources.streams[].ColorTransfer`, from ffprobe at scan time) and not `VideoRangeType` alone: a Dolby Vision file is mapped by its base layer, so profile 5 (`dv_bl_signal_compatibility_id` 0, a base that is neither HDR10 nor HLG, which mapped as PQ comes out green and purple) is left as it was, 8.1 maps as PQ and 8.4 as HLG, and the Dolby Vision data itself is ignored. A source scanned before the transfer was recorded has none, is not tone mapped, and is probed again by the next scan (the scan looks for the missing key). The hash gets `|tonemap<transfer>` only when it is set, so no SDR segment already stored is orphaned (`TestToneMapIsInTheSpecFromTheSource` pins an SDR hash), and a stored washed-out HDR segment is never served in place of a mapped one. The filters are `zscale` (to linear light and to BT.709) and `tonemap=hable:desat=0`, run in software at the output's size after `scale` and before burnt subtitles, so the work is on at most 1080 lines and a subtitle is not dimmed with the film: every ffmpeg build the CI and the images have has them (6.1.1 on Ubuntu 24.04, 8.1.3 on Alpine 3.24, 9.0.2), `libplacebo` is compiled into those builds too but needs a Vulkan device, which a worker without a GPU does not have, so it is not used. The input is declared BT.2020, limited range, because zscale refuses a file that leaves its primaries unsaid and HDR10 and HLG are BT.2020 by definition. `hable` and `desat=0` keep no state between frames and read nothing but the frame (the peak comes from its side data, or the transfer's default), so a restart on any worker makes the frames an earlier run did (`TestToneMappedRestartSplicesWithEarlierSegments`, no step in brightness at the seam, on 6.1.1, 8.1.3 and 9.0.2). The output is tagged BT.709 (`-colorspace`, `-color_primaries`, `-color_trc`, `-color_range`) and the master playlist already says `VIDEO-RANGE=SDR`. A copy is never tone mapped and `Decide` never offers one for an HDR source (invariant 45), in H.264 as in HEVC and AV1; a stream replica still honours a master URL's `VideoCodec=copy` for an H.264 source of any range (`Source.canServeCopy`, `TestStreamReplicaServesAnOlderAPIsH264HDRCopy`), so an older api replica's copy keeps playing during an upgrade. Cost, measured on this 16 core machine with ffmpeg 9.0.2, x264 veryfast, 20 s of synthetic 10-bit HEVC PQ to 1080p (user plus system CPU): from a 1080p source tone mapping takes 40.5 CPU seconds against 15.2 for the same re-encode with no mapping, 2.7 times (a reviewer measured 2.6), and from a 4K source 63.7 against 32.2, 2.0 times, which is about 3.2 cores to stay in real time; a job still below real time is helped by other workers (invariant 58); a worker slot counts the same for either, so a worker whose slots are all HDR jobs from 4K can fall behind real time, and there is no weighting of slots yet because it needs a decision in the scheduler that this measurement alone does not justify. Bitrate is capped as for any re-encode (the output is not smaller than the unmapped one and is bigger: 11.9 MB against 10.7 MB for 20 s of the 1080p clip, 11% more, and 6.4 MB against 5.5 MB from the 4K one, 16% more, at the same quality setting; a second measurement under an 8 Mbps cap gave 16% and 38% more), so network and storage are somewhat more than an SDR re-encode costs, and the segments of an HDR film are kept as long as any other (invariant 39). Not built: HDR direct play and copy for clients that play HDR (needs `VIDEO-RANGE=PQ`/`HLG` in the master and an SDR variant beside it), tone mapping on a GPU, and Dolby Vision's own enhancement layer.
### Video copy

45. A film's video is copied, not re-encoded, when the client plays it as it is and only the audio or the container forced the stream. "Plays it" means the video is allowed in the client's transcoding profile, so a copy is also chosen when its direct-play profile rejected the codec (an MP4 container it lists no H.264 for, say) but the transcoding profile takes H.264: the video is H.264, HEVC or AV1 (`playback.CopyCodecs`, the one list that `Decide`, the scan and `Master` read) and passes the client's `CodecProfiles` for it (profile, level, range type, interlacing, resolution; `Source.CanCopy`, `Decide`), the bitrate cap is not below the file's (with a cap and a file of unknown bitrate, the video is re-encoded; at Auto, which is no cap, a copy carries the file's whole bitrate and size, 4K included, exactly as direct play of the same file does and as Jellyfin's copy does, so a viewer on a slow link picks a cap, which re-encodes), no subtitle is burnt in, and the source has a keyframe index (invariant 46) whose keyframes can be cut into segments within `MaxCopySegment` (invariant 47). Everything else is re-encoded as before. That 4K passes at Auto follows from the code (`CanCopy` reads width and height only from a profile condition, and caps nothing at Auto) and from the captured profile, whose H.264 conditions are profile, range type, level 52 and interlacing, with no width or height (`compat/captures/transcode-12.4.json`); capture scenario 3 is a 720p film and says nothing of 4K. The reasons are the ones a re-encode gets (`AudioCodecNotSupported`, `ContainerNotSupported`, ...), as captured, and the PlaybackInfo reply has the same fields; only the URL differs, in `VideoCodec=copy` where a re-encode says `h264`. Like every query value that reaches the spec (invariant 34), `copy` is validated again on every request: `NewSpec` refuses it for a source that can't be copied, and for one that also names a burnt subtitle track, so a client that edits the URL gets 400 and not a broken stream. `Copy` is in the spec hash, so copied and re-encoded segments never mix, but a cap and the bitrate are not: a copy has the source's own size, and a bitrate estimated from its file for `BANDWIDTH`, which a cap doesn't change. The master playlist's `CODECS` names the source's own codec, profile and level (`Source.codecs`).

    **HEVC and AV1** are copied by the same rules, with four more gates, from `compat/captures/hevc-av1-12.4.md` (Jellyfin 12.4 and Chromium observed). (1) The client's transcoding profile must list the codec: `DeviceProfile.hlsMP4(codec)` finds a Video, `hls`, `mp4` profile that lists it with AAC, and `canTranscode` is the same test for h264, the re-encode fallback. A client that plays HEVC from a file but whose HLS profile lists h264 only is re-encoded with `VideoCodecNotSupported` added to the reasons, as Jellyfin reports it (capture `hevc-direct-only`). (2) The picture must be SDR, for H.264 as well as HEVC and AV1: a copy's master playlist says `VIDEO-RANGE=SDR`, so a copied HDR10 or Dolby Vision film would play washed out. An empty `VideoRangeType` (a scan from before it was recorded) counts as not SDR, for H.264 as for HEVC and AV1: an H.264 film in PQ or HLG is re-encoded and tone mapped like any other HDR film (invariant 53). HDR films otherwise behave as before: direct play where the profile allows it, else the H.264 re-encode. Jellyfin copies them with `VIDEO-RANGE=PQ` and an SDR variant beside it; that is not built, and is a known difference. (3) The master playlist must be able to name the profile: HEVC Main is `hvc1.1.6.L<level>.B0` and Main 10 `hvc1.2.4.L<level>.B0` (the level is ffprobe's number, the stream's `general_level_idc`; Jellyfin writes `1.4` for Main, which decodes the same), AV1 profile 0 is `av01.0.<level>M.<depth>` at 8 or 10 bits, as Jellyfin writes it (`BitDepth` is stored by the scan, from the pixel format). Other profiles (Rext, SCC, 12 bit, 4:4:4, AV1 Professional) and a stored source without `BitDepth` are re-encoded, with `VideoProfileNotSupported` added when the client's own `CodecProfiles` didn't say it. We do not read the SPS: the copy would need the compatibility and constraint bytes of an arbitrary stream. (4) The keyframe index must cover the file (invariant 46). A copy of HEVC in an MP4 tagged `hev1` is rewritten `hvc1` (invariant 48). Where Jellyfin and jellyscale differ otherwise: none seen on the captured files, SDR and HDR, MKV and MP4, for three profiles (`TestDecideMatchesJellyfinForHEVCAndAV1`). Cost: no new Postgres, network or worker cost. Postgres reads the same keyframe array per request (about 14 KB for a 2 hour film with a keyframe every 4 seconds); a rescan reads each file's Cues or moov once (a few megabytes at most, invariant 46); `api` and `stream` gain a pure function and run no ffmpeg; only workers do. A copy carries the file's own bitrate, and HEVC and AV1 sources of the same quality are smaller than H.264 ones, so a copy stores and reads less than an H.264 copy would. A 4K HEVC copy at Auto carries the whole file's bitrate, as H.264 does.
46. The keyframe index is read at scan time, by `library.ReadKeyframes`, from the file's own index, and stored with the media source in `media_sources.keyframes` (`bigint[]`, in ticks of the file's clock), so every replica and worker agrees and nothing is read again. For Matroska it is the Cues of the first video track, found through the SeekHead; for MP4 it is the sync sample table with the decode and composition times and one edit list. It is read for the codecs in `playback.CopyCodecs` (H.264, HEVC, AV1) in mkv and mp4, and Cues and the sync sample table are codec-agnostic, so `ReadKeyframes` needed nothing new for HEVC or AV1. The list is one: `Probe.wantsKeyframes` and the scan's rescan query (`loadSeen`, which takes the list as a SQL parameter) both read it, so a library scanned before this slice has its HEVC and AV1 films (NULL keyframes) read again at the next scan, which also records their `BitDepth`. An open-GOP film can list a CRA or a forward keyframe as a sync point: `TestIndexedKeyframesOfOpenGOPFilmsAreRandomAccessPoints` makes HEVC (x265 defaults: CRA with RASL pictures) and AV1 (SVT-AV1 forward keyframes with hidden frames) in both containers and checks that every entry is a key packet and decodes cleanly from the cut, and a bad entry is still caught by `errWrongIndex` (invariant 47). The scan does not probe random access points itself. NULL means not looked at, and a scan reads it, which is how files scanned before it get one; empty means the file has no index that can be read (Matroska without Cues, or with Cues its SeekHead doesn't point to, fragmented MP4, an edit list of more than one edit apart from an empty one before it, tables that disagree with each other), and the file is re-encoded without a scan trying again. The scan logs that at Info with the reason, so an operator can see why a film is unusable for a copy; the other reasons a film is re-encoded are in its `TranscodeReasons`. A film whose audio outlasts its video by enough to fail the 12 second check against the file's duration (the last keyframe more than 12 seconds before the end) is re-encoded: an accepted limit, because the check is against the file's duration, which is the audio's end when the audio is longer, and the scan doesn't read the video's end to learn better. Postgres cost: every request for a copied stream's master playlist, playlist or segment reads the keyframe array and `video_end` from `media_sources`, since the URL names the copy (about 1,800 bigints, 14 KB, for a 2 hour film with a keyframe every 4 seconds; the request rate has not been measured). A read that fails for another reason, including the failed read of a Cues or moov body, leaves NULL and is logged as a warning, and the next scan tries again. The tables are walked by runs, not by sample, and refused unless the sync samples ascend and lie within the file's sample count (`stsz`), so a crafted file ends quickly as a file with no index. The scan also stores `media_sources.video_end`, where the last video frame ends on the same clock, from `library.ReadVideoEnd`: a bounded `ffprobe` packet read from the last keyframe to the end of the file, for Matroska and MP4 alike and only when the last keyframe is within 12 seconds of the file's duration (a film with a longer gap can't be cut, and is stored with an empty index, logged, without the read), because the container's durations and tags don't say where the video ends (invariant 47). It opens the start of the file (a few MB; how many depends on the ffmpeg version) and asks for that last stretch twice, so it reads up to twice the distance from the last keyframe to the end, at most 12 seconds of film (120 MB at 40 Mbps); on SeaweedFS and Garage `TestVideoEndFromS3ReadsLittle` bounds the read to 12 MiB plus twice the bytes from the last keyframe to the end (the fixed part varies with the ffmpeg version; the last stretch is what carries over to a feature film). The tests bound `ReadKeyframes` to 2% of a small file from disk (`TestKeyframesReadLittle`) and 5% from SeaweedFS and Garage (`TestKeyframesFromS3ReadLittle`). The Matroska index is the Cues, one entry for each keyframe. The MP4's is the moov, which has a table entry for every frame and audio packet, so a large MP4's moov read is megabytes and grows with the length of the film, not with its bitrate. Listing the keyframes with `ffprobe` instead reads all of the file. Each read asks for the bytes it needs and closes (an open-ended S3 GET closed early may deliver a little more before it stops). `TestKeyframesMatchPackets` compares the index with `ffprobe` on every packet of the same files, with moov at the end or in front, an edit list or none, and the video as the second track.
47. A copied stream is cut on the keyframes (`playback.CopyLayout`): a segment ends at the first keyframe at least 4 seconds after the one it began at, or, if that would make it longer than `MaxCopySegment` (12 seconds), at the last keyframe before. The last ends where the video does. Times count from the first keyframe, and the video lasts from it to `video_end` (invariant 46), which is where the last frame ends, read from the packets, not guessed from the container's duration or tags: those count from the file's first stream, which may start before the video, and can be the audio's. The last entry of the playlist is within one frame of the real last segment when the video starts late, the audio starts late, everything does, or the video is shorter than the audio, in Matroska and in MP4 (`TestCopiedPlaylistEndsWhereTheVideoDoes`, `TestVideoEndIsWhereTheLastFrameEnds`). With a keyframe every 2 seconds that is 4 second segments, as a re-encode has; with a longer gap a segment is as long as the gap, so `EXTINF` is the real length (Jellyfin 12.4 writes fifteen 6.000 s entries for an MP4 whose segments are really 7, 6, 5, 8 ... s, `compat/captures/transcode-12.4.md`; for Matroska it computes them as we do), `EXT-X-TARGETDURATION` is the longest rounded up, and there is no discontinuity tag. No segment is longer than `MaxCopySegment`, so a file is re-encoded only when two keyframes, or the last keyframe and the end of the video, are more than 12 seconds apart. The longest segment can be longer than the longest gap, since two short gaps make one segment (keyframes every 3.75 seconds give 7.5 second segments). A client must download a whole segment before it shows any of it, so a long one delays every seek and start by its size at the client's bandwidth, which for 12 seconds at 40 Mbps is 60 MB. It lets through x264's and x265's default of a keyframe every 250 frames at 21 fps and up (10.4 s at 24 fps), with scene cuts between (`TestCopyLayoutKeepsSegmentsWithinTheLimit`). The playlist, `At` (the segment holding a resume position) and the worker's `checkLast` all read the same `Layout`, never a constant 4. Cues and stss are seek indexes and may not match the fragments ffmpeg cuts. When the gatherer finds a segment that doesn't start or end on a keyframe of the file (`errWrongIndex`), the job fails, the worker sets the source's keyframes to an empty array, only if the file's ETag is still the one the job started with (a file rescanned meanwhile keeps its new index), and logs an error with the item and the source, and the next PlaybackInfo re-encodes. An empty array stays until the file changes; an operator who wants the scan to read it again sets `keyframes` to NULL on that `media_sources` row. A last segment with no fragments is told apart by where ffmpeg's output stopped. Fragments are cut at every real keyframe, so with a good index none runs past the last segment's start: if the output stopped at or before it, the input was cut short, as when a faststart MP4 stops at the byte its last keyframe starts, whatever the length of the last group of frames, and the index is kept; if the output ran past it, the last entry is false and the index is dropped (`TestCopiedMP4CutAtTheLastKeyframeKeepsTheIndex`, `TestCopiedMP4CutAtAShortLastGroupKeepsTheIndex`, `TestCopiedStreamWithAFalseLastKeyframeIsDropped`); jellyfin-web asks PlaybackInfo again when a segment fails before playback. Only that error does this, never a transient failure or a cancellation (`TestCopiedStreamWithAWrongIndexFailsAndIsReEncoded`, and the early-end and stop tests, which check the index is left alone); a copy URL for that source is then refused as in invariant 45. The spec hash doesn't cover the index, so a change to the layout rules (`CopyLayout`, `MaxCopySegment`) or to the parser that gives other keyframes for the same file needs `OutputVersion` bumped, or segments stored under the old layout would be served for the new playlist. A viewer already playing a copy whose index is found wrong gets 400 on every request for the copy, stored segments included, because `NewSpec` refuses the copy (invariant 45), and jellyfin-web freezes with no dialog. That can be long before the bad point, since the job reads ahead of the viewer at 5 times the film's speed and finds it first. It is an accepted gap, listed in `docs/status.md` beside the Phase 4 mid-film freeze, until the job's read-ahead has a limit.
48. A copied job (`CopyCommand`, `gatherer`) copies the video and copies the audio too when the client takes its codec (`Spec.AudioCopy`, `Source.copyAudio`; the audio packets are then the source's own, as in invariant 52, and they come from the one input the video does, which a run for segment N seeks to the keyframe before it, so the audio starts where the video does, with no filter dropping packets, and the film is opened once; a copy whose audio is re-encoded opens it twice), else re-encodes the audio with the settings of a re-encode, writes one fragment for each keyframe of the source (`-hls_time 0.001`: the muxer cuts at the first keyframe after hls_time times the segments written, counted from its own first packet, so with irregular keyframes a run begun elsewhere would cut elsewhere, `spikes/seam/README.md`), and joins fragments into the playlist's segments as they finish. A segment's video bytes depend only on the file and the segment's number, and its audio is timed the same way, but the audio's bytes may differ after a restart, because the encoder starts warm and does not continue: the fragments are told apart by their times, read from the playlist ffmpeg writes and from the first fragment's first keyframe, the join drops each fragment's `styp` and sets its sequence number to its start time, and a segment that doesn't start and end on fragment boundaries fails the job rather than store the wrong video. The run for segment N begins at the keyframe before it, and its audio 2 seconds early on the AAC grid of a run from the start, so the audio is warm and whole at N and nothing depends on the decode time of a keyframe that Matroska doesn't store. HEVC is copied with `-tag:v hvc1`, because ffmpeg's choice of `hvc1` or `hev1` depends on its version and the input's tag, and workers on different versions would then write different init segments (`TestCopiedRestartSplicesWithEarlierSegments` fails without the pin on an `hev1` MP4 and an MKV). **A copied HEVC or AV1 stream is not a new spec family**: it is the existing copy family (`Copy` in the spec hash, invariant 23, unchanged), whose segments are the source's own bytes and so splice by construction. The codec needs nothing in the hash, since a different codec is a different file and a different ETag, and `OutputVersion` is not bumped. The test runs the same restarts on H.264, HEVC and AV1, MKV and MP4, and passes (init segment, video packets, times and decoder warnings equal to a run from the start) on ffmpeg 9.0.2, jellyfin-ffmpeg 8.1.3 and Ubuntu's 6.1.1, the last two by running the compiled test inside the Jellyfin and Ubuntu 24.04 images. Restarts at segments 1, 4, 8 and the last give the same video bytes, the same init segment and audio packets at the same times as a run from the start, on ffmpeg 9.0.2, 6.1.1 and 8.1.3 (`TestCopiedRestartSplicesWithEarlierSegments`); decoded, the audio differs from a run from the start by at most 0.31% to 0.36% of full scale (about -49 dB, depending on the ffmpeg version) on the fixture's 440 Hz tone, which the test bounds at 1%. Stopping, DELETE ActiveEncodings, a closed tab, a second viewer, an audio switch, a far seek and S3 sources use the machinery of a re-encode and are exercised on copied streams by `test/e2e` and `TestCopied*`. A job whose input ends early fails with "the input ended early", except when the cut is within 1.5 seconds of the end of the film, inside the last segment: the job then succeeds and that segment is short by that much. That is an accepted limit, because a tighter check would fail good files whose last fragment ends early (118 to 159 ms measured). A copy costs about 5% to 8% of the CPU of the re-encode of the same 1080p film at a 3 Mbps cap (1.08 against 19.89 CPU seconds of the worker's ffmpeg for 32 seconds of film in the latest run, 0.90 against 11.22 in an earlier one on the same machine, measured by `test/e2e` from the worker's children, with the AC3 decode and AAC encode included). A copy of both streams opens the file once (`TestACopyOfBothStreamsFromS3ReadsTheFilmOnce`) and ffmpeg reads it at 5 times the film's speed (`-readrate 5`, `TestCopyReadsAtFiveTimesTheFilmsSpeed`), so while the job runs it reads five times the film's bitrate, and a run to the end reads the film's bytes once. A copy whose audio is re-encoded opens the file twice, once for the video and once for the audio, so it reads ten times the film's bitrate and a run to the end twice the film's bytes; the figures that follow are for that path, and halve for a copy of both. That keeps a copy from reading, writing and uploading the whole film as fast as the disk and the store allow, and invariant 57 bounds how far ahead of the viewers it gets. For a 2 hour film at 40 Mbps (36 GB) a run to the end, which a viewer who watches it all costs, reads 72 GB from the source, which from S3 is 72 GB of egress, writes and uploads 36 GB of segments that are kept for 24 hours, and takes about 24 minutes; a viewer who leaves after a minute costs the film made up to the furthest segment asked for plus `transcodeLead` (60 seconds) and the rest of a segment, about 160 seconds of film, 1.6 GB read, instead of 6 GB (the 120 seconds of a job running at ten times the film's bitrate, 5 MB/s and 50 MB/s read, that it cost before). The byte figures here are computed from the bitrate and the length, not measured by a test. They assume the store takes uploads at 5 times the film's speed (200 Mbps for a 40 Mbps film), and ffmpeg is not paced by uploads: a slower store leaves what ffmpeg has made in the scratch directory, until the uploaded segments reach the lead, and it holds only what was made and not yet uploaded when the store keeps up. A copied seek waits for the whole segment it lands in, read at 5 times the film's speed and downloaded at the file's bitrate: up to 12 seconds of film, 60 MB at 40 Mbps. Resuming a 1080p film at 40 s of 60 s, which starts a job there as a seek past what is made does, took 2.6 s from the click to the picture moving on POSIX (2614 ms) and on SeaweedFS (2628 ms); a segment needs the film read up to its end at 5 times its speed, so the first of 4 seconds takes under a second and one of 12 seconds under 3. A copied stream's storage is the file's own bitrate, not the encoder's ceiling (`Spec.VideoBitrate` is `FileBitrate`), kept for 24 hours; the storage ceilings of a re-encode do not apply to it.
54. A film's chapters are read at scan time by the probe that lists its streams (`ffprobe -show_chapters` in the same run, never a second read of the file), as `Probe.Chapters`, and stored twice: in the item's DTO as `Chapters`, and in `media_sources.chapters` (`jsonb`), which is the marker. NULL means never read, `[]` means the file has none, so a film without chapters is not probed again. Each chapter is `{StartPositionTicks, Name, ImageDateModified}` as Jellyfin 12.4 sends it (`compat/captures/chapters-12.4.md`): the start is ffprobe's `start_time` in ticks on the file's own clock, in time order; the name is the title tag trimmed, or `Chapter N` (N the chapter's 1-based place in the file) when it has none, as Jellyfin names it; `ImageDateModified` is Jellyfin's `0001-01-01T00:00:00.0000000Z`. **There is no `ImagePath`** (absent, not null), and an `ImageTag` only where invariant 55 gives one: jellyfin-web 12.4 asks for `/Items/{id}/Images/Chapter/{n}` only for a chapter with an `ImageTag`, and lists chapters on the details page only if the first has one. The ticks are not shifted by when the streams start: a transcode keeps the file's clock (`-copyts`, invariant 48's copy as well as a re-encode), the player's timeline is that clock, and Jellyfin leaves them as they are too (a film whose streams start 2 s late, chapter at 20 s: the player seeks to 20 s in direct play and in a transcode, and the segment asked for is the one at 20 s; `test/e2e`). `Items/{id}` carries `Chapters` and a list only with `Fields=Chapters`, which `items.optional` already did. MP4 chapters in a QuickTime text track (`tref/chap`) are read by ffmpeg as chapters, and the track itself is listed by ffprobe as `data`, which the probe ignores, so it never shows as a subtitle track (`TestProbeReadsQuickTimeChapterTrack`; passes on ffmpeg 9.0.2 and Ubuntu 24.04's 6.1.1). A changed file is probed again by its ETag like any other change, which is how a rescan sees new chapters. **Upgrade cost:** every film scanned before this (`media_sources.chapters` NULL, which a scan by an older version also leaves) is probed again once by the next scan, as a film whose attachments are unread is: one ffprobe open of the file (the few MB at its start, or its moov, that the first scan's probe read, from S3 as well) and one frame extraction for its poster when it has no sidecar image, with its keyframe index and video end kept and not read again (`TestScanStoresChapters`: a sentinel index survives). That is the cost of the first scan's probe without the keyframe read, which is the dearer part for H.264, HEVC and AV1 files (up to twice the last group of pictures, 120 MB at 40 Mbps); a library of N films costs N such probes spread over the scan's four at a time, once. The item keeps its id and its watch state. Not built: reading chapters of other containers' own formats that ffprobe does not list.
55. **Chapter pictures are opt-in per library and made by a worker job, never by the scan** (`chapterImages` in the library's config, `libraries.chapter_images`, off by default as Jellyfin 12.4's `EnableChapterImageExtraction` is; `compat/captures/chapter-images-12.4.md`). It is a column and not worker-only configuration so that every role agrees: it is what stops `ImageTag`s and the route when the option goes off again. **One job per source does everything:** `library.SyncChapterImages(source)` is the only code that makes or deletes pictures, a `subtitle_jobs` row of kind `chapters`, key `chapters/{source}` (it cannot collide with the keys of tracks, `.sup` files or fonts, which start `subtitles/` or `attachments/`), claimed by `RunChapterImages`. **Chapter jobs have worker slots of their own** (`chapterSlots`, 2; `RunSubtitles` and its four slots never claim one), because a library full of them is minutes of seeking per film and a viewer's subtitle must not wait behind it past `queueTimeout`. The worker branches on the kind before looking the source up, because a removed source has no `media_sources` row. **A source is wanted** when its library's option is on, `media_sources.chapters` is not empty and the file has a video stream; this is one SQL fragment (`wantedSQL`) that the scan's enqueue and the job's own read both use. **State is `chapter_images (source_id, library_id, etag, state making|done, attempts, keys text[])`, with no foreign key to the item or the media source** (they share their id), because a scan deletes and rewrites `media_sources` for every film it probes and removes the item of a removed file, and the row must outlive both so that the next job still has the library, and so the asset store, to delete with. Only the job deletes a row, and always after the objects. **Reachability is by the prefix `chapters/{source}/` alone:** a picture is at `chapters/{source}/{md5 of the ETag}/{n}.jpg`, so a changed file's pictures never collide with the old ones; the `keys` in the row are only for serving and for resuming, written chapter by chapter as the job goes. **The scan queues, after every scan whether the option is on or off, with one call, `library.EnqueueChapterImages`,** a job for each source that is wanted and has no row, or a row of another ETag, or a row that is not done (the job, not the queue, applies the cap); for each source that is not wanted but has a row; and for each row whose source is gone (`chapter_images LEFT JOIN media_sources ... WHERE m.id IS NULL`, of the library). A source whose row is done for its ETag is not queued and not listed: it costs the scan nothing. The insert is `ON CONFLICT (key) DO UPDATE ... WHERE subtitle_jobs.state IN ('done','failed')`, so a queued or running job is left alone. **The job** reads the library, the source and the row itself, then lists `chapters/{source}/` once, deletes every object outside the current version's directory (every object when the source is not wanted, and then the row), and when the source is wanted and its row is not done for this ETag makes the pictures that are not in that one listing (so a retry resumes, with no second list or per-chapter stat). Its first statement upserts the row to `making` for the ETag with `attempts = attempts + 1` if the ETag is the same and `1` if not: **the count is taken before the asset store is touched, kept in this row because the job row is deleted by the daily sweep of `subtitle_jobs`, and the cap (3 per file version) is checked by the job itself, so a job taken over after a lapsed lease is held to it too;** a job that finds the cap reached gives up: it deletes everything under the prefix and marks the row done with no keys, so nothing stays behind; **an attempt is never given back**, not for a worker that is stopping and not for a store that is down (both count like a bad file, so an outage of three scans leaves the films without pictures, and the give-up log line says so and names the remedy: chapter images off and on again across two scans), because the criterion is at most 3 starts per file version, and deleting never touches `attempts` and has no cap, so turning the option off for at least one scan and its job, which deletes the row, and then on again resets the cap. The final write is `UPDATE chapter_images SET keys = ..., state = 'done' WHERE source_id = $1 AND etag = $2` with the ETag the job started with: if a replacement file moved the row on, the old job writes nothing and the next job's prefix sweep removes the pictures it made. Per chapter, in this order, chapter 0 like any other (jellyfin-web then lists no chapters, as it needs the first one's picture, docs/chapters.md says so): the job's context done ends the job without failing it (a stopping worker puts it back in the queue, a lost lease leaves it to the worker that took it over), its attempt still counted; each chapter's outcome (a key, or "" for a skip) is written to the row's keys as the job goes, so the next attempt resumes after it and a skip stays final; a media store error seen by `watchedStore` (ffmpeg sees it only as a failed read) fails it; the frame's own 2 minute deadline (`chapterFrameTimeout`) skips the chapter; an `ExitError` of a process that did not exit normally (a signal: the OOM killer, a kill) fails the job; any other `ExitError` (a decode error) skips it; ffmpeg not starting fails it. **A skip is final for that file version**: the chapter has `''` in `keys`, no tag, and the job is done, so a slow store can leave chapters without pictures until the file changes, costing up to 2 minutes of one slot per chapter; after a failed frame the job checks within 30 s (`readableTimeout`) that the store can still read the file, and fails if not, so a store that has stalled outright, or a POSIX file that can't be opened, fails the job rather than skipping chapters: that chapter's failure is the store's, so it is not recorded and the next attempt reads it again (the check runs in a goroutine, so a read on a hung mount that ignores its context still times out; a frame's ffmpeg is bounded by its deadline and `WaitDelay` only if SIGKILL ends it, so a mount whose reads ignore that holds the slot until it answers). Reads are at the chapter's start **on the file's clock** (`-seek_timestamp 1`, since a file whose streams start late would otherwise be read seconds too far in), scaled to at most 400 pixels wide; a start at or past the end gives no picture and no error. A picture of an HDR film (`playback.Source.ToneMap`) is tone mapped with the filter chain playback uses (`playback.ToneMapFilter`). **Serving reads only rows with `state = 'done'` and `etag = media_sources.object_etag`** (joined `c.source_id = m.id`), so while a job is making pictures the API shows no tags and the route is 404. **The tag is not in the stored DTO**: `items.Repo` adds `ImageTag` (the hash of the picture's key) to the chapters it returns when the library's option is on, the row is done for the current ETag and the number of chapters is the same, so the option going off, a changed file, or a rescan that rewrites `items.dto` can never leave a tag for a picture that is not served. `GET /Items/{id}/Images/Chapter/{n}` is on the stream role like the other item images and serves the stored JPEG as it is (`maxWidth` and `quality` are ignored, as for primary images: the role has no ffmpeg or decoder, rule 1; the picture is already at most 400 pixels wide, which is what jellyfin-web asks for); an index that is not a chapter of the item with a picture (negative, past the last, 2^31 or more, not a number), a library with the option off and a row not done for the current ETag are 404. **Storage is reclaimed** by the next scan's job after the option is turned off, the chapters vanish, the file changes or the source is removed, and a job that failed midway or lost to a replaced file leaves pictures the next job removes the same way, and a file whose attempts are used up has them deleted by the job that gives up. Renaming or dropping a library, or changing its asset store URI, leaves its old pictures (out of scope). Upgrading: roll workers first. A worker from before this release that claims a chapter job fails it (it is not a subtitle). **Cost per film:** one ffmpeg run per chapter, each opening the file and seeking to the chapter (a few ranged reads on S3, the file's header and index and the group of pictures at the seek) and decoding one frame, plus a PUT of 9 to 43 kB at 400 pixels, so a 30-chapter film is 30 seeks and up to 1.3 MB of assets, in a library of 1000 films 30,000 seeks. The size was measured (ffmpeg 9.0.2) with the job's own command (`-seek_timestamp 1`, 400 wide, `-q:v 3`, MJPEG) on three 4 s 1920x1080 25 fps H.264 `lavfi` sources, frames at 1, 2 and 3 s: `testsrc2` 9.3 to 9.8 kB, `mandelbrot` 12.3 to 15.8 kB, noise-like `life` 41.6 to 43.4 kB; no real film was measured (docs/chapters.md, Cost). Not built: other widths, the 'during the scan' and scheduled-task split Jellyfin has, `ImagePath`, a real `ImageDateModified`, chapter pictures for formats whose chapters ffprobe does not list.
56. **A scan never takes an absent library for an empty one.** `Posix.List` of a missing root is an error (a missing prefix under a root that is there lists as empty, as on S3), and a scan whose store lists no video at all, for a library that has some stored, fails without removing any (`scan.go`), so an unmounted volume, an empty mount point or an empty bucket keeps the films and their watch state. The cost: a library emptied on purpose keeps its last films until a video is back (docs/running.md, Configuration). Tests: `TestPosixListOfAMissingRootFails`, `TestAScanOfAMissingMediaRootKeepsItsItems`, `TestAScanOfAnEmptyMountPointKeepsItsItems`.
57. **A job runs at most `transcodeLead` ahead of its viewers, then waits.** The lead is film time (default 60 seconds, so 15 segments of 4 seconds, and fewer of a copy's 4 to 12 seconds), counted from the furthest segment asked for. The stream replica that serves a segment request writes the segment number to the viewer's row (`transcode_viewers.segment`, in the upsert every request makes, a request that names no segment leaves it as it was), and the worker reads it: the job's limit is the first segment that starts a lead or more after the largest `segment` among viewers of the spec that are not stopped, were seen within `transcodeIdle`, and asked for a segment from the job's start to its `next_segment` plus `catchUpSegments` (the window in which `ensure` lets a request join the job). A viewer far ahead has its own job and does not carry this one on, and one that seeked back counts by its last segment, not its greatest. With segment `limit - 1` made (in scratch, for a copy as fragments to the end of that segment) the worker stops ffmpeg with SIGSTOP, uploads what is made below the limit and nothing past it, and sends SIGCONT when the limit has moved. It looks at the viewers' rows every 500 ms while it is at its limit and not otherwise, so the cost is one indexed read of a few rows per paused job per half second, and no write beyond the ones every request already made. A paused job keeps its lease (the heartbeat goes on), its slot (so a worker's `transcodeSlots` bounds the viewers it serves at once, not only the encodes, and a copy holds its slot for the whole watch rather than the fifth of it the read takes) and its scratch directory (the heartbeat touches the directory, so another worker's `scratchIdle` sweep leaves it); the stall check (`Worker.Stall`) is held off while it is paused; and `transcodeIdle` is measured from the last request as for any job, so a paused job is killed (SIGKILL works on a stopped process) when nobody asks for 60 seconds, and a viewer who is playing keeps it. A paused job none of whose viewers is in its window any more, because they all seeked away or went, is cancelled and gives back its slot; what it stored stays, and a viewer who comes back starts a job at the first missing segment (`TestAJobLeftBehindBySeeksGivesBackItsSlot`: a viewer's own seek already replaces the job it owns, and this ends one another viewer joined). A seek beyond the window restarts as before, so the deterministic segments and splicing restarts of invariants 23 and 48 are those of a job that merely runs slowly; a stopped ffmpeg keeps its input, so a paused copy from S3 resumes where it was (`TestAPausedCopyFromS3ResumesAndMakesTheSameSegments`: 20 seconds paused on SeaweedFS and Garage, segments byte-equal to a run from the start). ffmpeg 6.1, unlike 8.1 and 9, keeps its `-readrate` budget in wall time while stopped, so after SIGCONT it reads unthrottled until it has caught up (measured with `-readrate 5 -c copy` stopped for 8 seconds at 20.4 seconds of film: 61 seconds of film 0.2 seconds after SIGCONT; 8.1.3 and 9.0.2 went on at 5 times the film). The worker pauses again once segment `limit - 1` is made, which it sees within its 100 ms poll, so on 6.1 a resume reads past the limit what ffmpeg reads at full speed in up to 100 ms, bounded by the disk or network, not by the film; nothing past the limit is stored either way. The shipped image's ffmpeg (Alpine) is not 6.1. Where SIGSTOP does not exist (not Linux, `pause_other.go`), jobs are unbounded and the log says so. Jellyfin 12.4 has `EnableThrottling` false and `ThrottleDelaySeconds` 180 in its default `encoding.xml`, so by default its transcodes run to the end of the film. A viewer of the spec that has asked for no segment (`segment` is -1: a replica from before the column writes none, and a viewer that has fetched only a playlist has not yet) frees the job, which then runs unbounded as it did before the bound, so the order replicas and workers roll in does not matter. The worker looks again every 500 ms while a job is freed, so once that viewer asks for a segment or is no longer seen the bound comes back (`TestAPlaylistOnlyViewerFreesTheJobOnlyWhileItIsSeen`). A reset of an S3 connection held unread while paused is resumed by `store.Reader` at its offset like a cut body (`TestReaderResumesAfterAReset`); a job that is paused for `transcodeIdle` holds its two S3 GETs for at most that long.
58. **A slow re-encode is shared by several workers, in chunks.** A re-encode is cut into chunks of `ChunkSegments` segments (4, 16 seconds, the same on every worker), which are where jobs meet. A job's ffmpeg begins at the segment the job wants (a helper at the first segment missing in its chunk, which is how a killed helper's replacement goes on; a viewer's job, a seek or a failover, where it was asked) and goes on across chunk starts, the same ffmpeg, until the next chunk's first segment is stored or another live job started in that chunk (`chunkFree`): then it stops, which is where a job ends when it catches up with a helper. So a job nobody helps is one ffmpeg, as before chunks, and a burnt PGS cue or the audio encoder carries across chunk starts (`TestAJobNobodyHelpsIsOneFFmpeg`). The runs of different jobs meet as a restart's segments do (invariant 22). A helper's failure is not remembered as the spec's: the viewer's job makes the chunk instead (`TestAFailedHelperDoesNotFailTheViewer`), and no helper is queued for that chunk again until the failure is older than the 30 seconds the spec's failures are remembered, so a helper that always fails costs one ffmpeg start per chunk per 30 seconds, not one per heartbeat (`TestAHelperThatAlwaysFailsIsNotRetriedOnEveryBeat`). A copy is not chunked. A burnt image subtitle is, like any re-encode: a helper's chunk draws the cue showing at its start (invariant 51; `TestABurntImageSubtitleGetsHelpers`). A job whose measured encode speed (`transcode_jobs.encode_speed`, invariant 57's pause excepted) is below `HelpBelow` (1.2), judged only once it has run `helpSpan` (2) seconds since its first output and has made some film (ffmpeg's output comes in bursts, and a speed over a job's first two seconds swung from 0.9x to 1.6x for a job that makes 1.4x, which started helpers beside failover tests that count ffmpeg on ffmpeg 9.0.2; `TestSpeedOverWaitsForTheSpanBeforeJudging`, `TestAJobThatHasMadeNothingYetAsksForNoHelp`), inserts, on its heartbeat, one **helper** job (`transcode_jobs.helper`, owner `helper`) for the first chunk ahead of it that is not stored (or is stored but for a gap, which is how a killed helper is replaced, from its first missing segment), has no live job started in it and none about to enter it, and starts below the read-ahead limit. A helper is an ordinary row, claimed like any other except that it goes to a worker with no job of its spec, or after a second to any worker with a slot (a dead helper's replacement when the others are busy), and only while a slot stays free for a viewer who has not asked yet: counting itself, the cluster must have a free slot after it, at the insert and again at the claim, and the decision to take a slot for a helper is made under one advisory lock for the cluster so that workers deciding together do not take the last one. A helper belongs to every viewer of its spec: `Stop` leaves it while any viewer of the spec is not stopped (and ends it with the last), the idle time and the lease end it like any job (invariant 25), and its limit is the lead past the furthest segment asked for by a viewer at or before its chunk (invariant 57), not past its own start; a viewer far past it has a job and helpers of its own, and the gap between is nobody's to encode (`TestHelpersDoNotFillTheGapToAFarViewer`). A seek into a helper's chunk joins it by invariant 37. The cost is an ffmpeg start, and the audio cut afresh, where a helper's chunk begins (invariants 22 and 48).

59. **A worker claims a job only if its output version is the one the worker makes.** Every `transcode_jobs` row records the `OutputVersion` of the replica that queued it (a helper, that of the job it helps; a row written with none counts as 4) and every `transcode_nodes` row that of the worker, and a worker claims only a queued job of its own version, so an older worker never stores segments made the old way under a newer spec's hash. Slot accounting (free slots, helper preemption, `Unavailable`) counts the viewer's version only. A release whose workers make any spec differently, a new spec field included, must bump `OutputVersion`, or the claim cannot tell its workers from the old ones. `docs/running.md` gives the upgrade order.
