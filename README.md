# jellyscale

A cloud-native video server that speaks the Jellyfin client API. Each role scales on its own, and each library can live on a filesystem or S3-compatible storage. Not affiliated with the Jellyfin project.

**Status: Phase 3, third slice.** Unmodified jellyfin-web logs in, browses, and plays films from POSIX and S3 libraries, with seeking, resume and Continue Watching. A film the browser can't play as it is, or that exceeds the quality menu's cap, is transcoded to HLS (H.264 in fragmented MP4, with AAC or the film's own audio copied) by a worker, which copies the video instead of re-encoding it when the client plays the video but not the audio or the container (H.264 with AC3 in MKV, say), with seek, audio track switching and the stop paths working. Text subtitles inside the file (SubRip, ASS, SSA, WebVTT, mov_text) show in jellyfin-web, as the client's own text or burnt into a transcode. Subtitle files beside a film (`.srt`, `.ass`, `.ssa`, `.vtt`) and the fonts attached to a Matroska film work the same way. PGS, VobSub and DVB tracks inside the file are listed, and drawn into a transcode (PGS by jellyfin-web itself, from the file, when its viewer has turned that setting on). Not built yet: external `.sup` and `.sub` files, hardware encoders, HDR tone mapping, and recovery when a worker dies mid-film (Phase 4; see Transcoding). Phase 0 findings are in [`spikes/README.md`](spikes/README.md).

## Scope

Video only. No music, photos, Live TV or .NET plugins. Routes Jellyfin marks obsolete aren't implemented, apart from the aliases flagged `alias` in [`compat/endpoints.yaml`](compat/endpoints.yaml), which jellyfin-web still needs.

## Roles

One binary, chosen with `--roles`:

| Role | Serves |
|---|---|
| `api` | REST API, WebSocket |
| `stream` | Images, direct-play media, file downloads, HLS playlists and segments, subtitles |
| `worker` | Library scans, transcodes, subtitle extraction |

`--roles=all` runs everything in one process. Paths under `/Videos/`, `/Items/*/Images/` and `/Items/*/Download`, and `/Playback/BitrateTest` (case-insensitive), belong on `stream`, and everything else on `api`. [`deploy/compose/Caddyfile`](deploy/compose/Caddyfile) and `test/e2e/router.mjs` do this.

## Transcoding

Add `transcodeStore` to the config, the same for every role. With none anywhere, nothing transcodes and every source plays as it is. Every process records its roles and `transcodeStore` in the database with a heartbeat, and a replica compares them: when they differ, or one process has none (a worker-only process with none is left out, since it only extracts subtitles), an `api` replica refuses the transcode at PlaybackInfo and its log names both. A spec that already has a live job is offered anyway, by any replica, and its viewer joins it; the log warns and names both stores, and if the replica that serves the segments has no `transcodeStore`, it answers 503 and jellyfin-web asks PlaybackInfo again, which offers the live job again, so before playback the viewer retries without a dialog until the job ends, and after playback has begun the picture freezes; if it has a store it can't read the segments in, the request times out. A store URI that carries credentials (a user or password, or a parameter named like a key, secret, access, token, pass, sig or credential) is refused at startup; credentials come from the environment. A process with only the `worker` role and no store starts and extracts subtitles, but runs no transcodes. Set it, to the same value, on all of them:

| Key | Meaning | Default |
|---|---|---|
| `transcodeStore` | Store URI for segments: `file:///var/lib/jellyscale/segments`, or `s3://bucket/segments?endpoint=...` with credentials from the environment | none |
| `transcodeScratch` | Where a worker's ffmpeg writes before uploading. Workers on one host may share it; each sweep removes job directories untouched for two minutes, which a crash leaves behind | `$TMPDIR/jellyscale-transcode` |
| `transcodeSlots` | Concurrent transcodes per worker, apart from up to four subtitle extractions; a negative number is refused at startup | 2 |
| `transcodeIdle` | How long without a request before a spec's ffmpeg stops. Closing a tab sends no stop | 60s |
| `transcodeRetention` | How long a spec's segments stay after its last request | 24h |

`stream` replicas and workers share the segments only through that store and Postgres, so the store must be reachable from both: a shared volume, or S3. The worker needs `ffmpeg` and `ffprobe` on its path, as the image has; `api` and `stream` need neither. Segments of a re-encode are 4 seconds, and a restart after a seek splices with the segments before it.

A viewer whose transcode can't start (no worker running, every slot busy, or the same one just failed) gets a "cannot be played at this time" dialog from jellyfin-web instead of waiting, answered within seconds; the server log says which. A segment that fails before playback has begun ends in that dialog too, because jellyfin-web asks PlaybackInfo again and is refused. There are two exceptions: a spec with a live job, which is offered again, and a copy whose keyframe index was found wrong, which is dropped so that the next PlaybackInfo re-encodes the film with no dialog. After playback has begun, a failed segment makes jellyfin-web drop the stream: the picture freezes, with no dialog. A worker that stops gracefully and is replaced within six seconds is not noticed, because a request for a segment waits that long for a worker (`test/roles.sh` does this with real processes). A worker that is killed is another matter: its job keeps its lease, which lasts 10 seconds from each renewal (7 to 10 seconds after the kill, longer if ffmpeg had only just started), before a request can restart it, and one measurement answered a waiting segment after 12.7 seconds, past the player's 10, so the picture freezes whether or not a replacement is quick. A worker that is killed, or not replaced in time, freezes the picture, and recovering from that without losing the picture or the resume position is Phase 4. A viewer on a film whose default track plays as it is, who picks another audio track while no slot is free, keeps playing the default track. In a re-encode, interlaced H.264 is deinterlaced, and the output is H.264 at no more than 1080 lines, in software with `veryfast`; a copy does neither (see Video copy). A worker that falls behind makes the player stall, and there is no lower-quality fallback yet. A job whose ffmpeg makes no segment for 30 seconds is failed, so a hung encode ends in a dialog and not a spinner when it hangs before playback begins; after playback has begun the failed segment freezes the picture as above. A source scanned before the scanner recorded level, field order and range plays directly where its conditions allow it, and is probed again at the next scan, which it does without the file changing.

Storage: segments are kept for `transcodeRetention` (24 hours) after a spec's last request, one set per spec, so a film watched in full at a quality cap of *B* bits per second takes up to *B* × 3600 / 8 bytes per hour of film: about 0.45 GB per hour for each megabit of the cap. The encoder also caps video at 6 × width × height bits per second, and the width follows the source's shape: at 1080 lines a 16:9 spec stays under about 12.63 Mbps (about 5.7 GB per hour) and a 2.39:1 one, 2578 wide, under about 16.9 Mbps (about 7.6 GB per hour); at 720 lines 16:9 stays under about 5.72 Mbps (about 2.6 GB per hour). These are ceilings for a re-encode, with the 192 kbps audio included; none of them applies to a copied stream (see Video copy); how far real film at crf 23 falls below them has not been measured. Each distinct audio track or quality is its own spec. Workers also hold a job's unuploaded segments in `transcodeScratch`, a few at a time.

### Video copy

When the video can play in the client as it is and only the audio or the container can't (H.264, HEVC or AV1 with AC3 in MKV, or in MP4), the worker copies the video and re-encodes the audio to AAC. A stream then costs almost no CPU and keeps the source's picture exactly. Nothing to configure. It happens when:

- the video is H.264, HEVC or AV1, and passes the client's `CodecProfiles` for it (profile, level, range, interlacing, resolution), and the client's HLS transcoding profile lists the codec;
- for HEVC and AV1, the picture is SDR, and the profile is one the master playlist can name: HEVC Main or Main 10, AV1 profile 0 at 8 or 10 bits. HDR films and other profiles are re-encoded to H.264 as before (HDR tone mapping is not built, so an HDR film that the client can't play as it is looks as it did);
- no bitrate cap is below the file's bitrate, and no subtitle is to be burnt in;
- the file has a keyframe index, which the scan reads from the file's own index (Matroska Cues, or the MP4 sample tables) and keeps in the database. A Matroska file written without Cues, a fragmented MP4 and any other container are re-encoded, as before;
- no gap between keyframes is longer than 12 seconds, counting the stretch from the last keyframe to the end of the film. x264 and x265 default to a keyframe every 250 frames, which is under 12 seconds at 21 fps and up. A file with longer gaps is re-encoded.

The playlist is cut on the file's keyframes: a segment ends at the first keyframe at least 4 seconds after it began, or earlier if waiting would make it longer than 12 seconds, so no segment is over 12 seconds, and the playlist says their exact lengths.

A copy is not capped, and at Auto it carries the file's whole bitrate and size, 4K included, exactly as direct play of the same file does and as Jellyfin's copy does. A viewer on a slow link picks a cap in the quality menu, which re-encodes. A copy stores and sends the picture at the file's own bitrate: a 40 Mbps remux takes about 18 GB per hour (computed) of film for each spec, kept for 24 hours, against the 5.7 GB per hour at most of a 1080p re-encode. None of the storage ceilings above applies to it.

Reading the source: a copy opens the file twice, once for the video and once for the audio, and reads each at 5 times the film's speed (`-readrate 5`), so while the job runs it reads ten times the film's bitrate, and a run to the end reads twice the film's bytes. That keeps it from reading the film as fast as the disk allows, but nothing limits how far it gets ahead of the viewer. Every request for a copied stream's playlists and segments reads the film's keyframe array (about 14 KB computed for a 2 hour film with a keyframe every 4 seconds, 8 bytes each) from Postgres; the request rate has not been measured. The job continues until the film ends or 60 seconds after the last request. For a 2 hour film at 40 Mbps (36 GB), a run to the end reads 72 GB from the source (72 GB of S3 egress), stores 36 GB of segments for 24 hours and takes about 24 minutes. A viewer who leaves after a minute still costs the minute watched and the 60 seconds of idle time, 120 seconds of the job running at ten times the film's bitrate: 6 GB at 40 Mbps. The byte figures here are computed from the bitrate and the length, not measured. They assume the store takes uploads at 5 times the film's speed (200 Mbps for a 40 Mbps film), and ffmpeg is not paced by uploads: unuploaded segments sit in `transcodeScratch` a few at a time if the store keeps up, and pile up, up to the whole film (36 GB), if it does not. A seek waits for the whole segment it lands in, up to 12 seconds of film (60 MB at 40 Mbps), read at 5 times the film's speed and downloaded at the file's bitrate.

The audio becomes stereo AAC (192 kbps by default), so only the picture is unchanged.

The scan builds the index, and a few things have to be known about it. A film scanned before this version has no index until the next scan reads it (a scan does so for every H.264, HEVC or AV1 file in MKV or MP4 that has none), so it is re-encoded until then. For a Matroska file the index is the Cues (the test bounds the read to 2% of a small test file); for an MP4 it is the moov, which has an entry for every frame and audio packet, so a large MP4's is megabytes. The scan also reads where the video ends, from the packets of the last stretch from the last keyframe to the end of the file, when that stretch is within 12 seconds of the file's duration (a film with a longer gap can't be copied and is not read): up to 12 seconds of film, read up to twice (120 MB at 40 Mbps), plus what ffmpeg reads to open the file, a few MB that vary with its version. If the index turns out not to match the file (a segment doesn't start or end on a keyframe), the job fails, the file's index is dropped and an error logged with the item and source, and the next PlaybackInfo re-encodes the film (jellyfin-web asks PlaybackInfo again when a segment fails before playback has begun; after it has begun the picture freezes until the viewer restarts). A dropped index stays empty until the file changes; to have the scan read it again, set `keyframes` to NULL on that `media_sources` row. An input cut short (a file truncated in the store) fails the job but keeps the index, unless the cut is within 1.5 seconds of the end of the film, inside the last segment: that job succeeds and its last segment is that much short. The scan logs an unusable index at Info with the reason, and a read that failed at Warn, to be tried again at the next scan; the other reasons a film is re-encoded are in the `TranscodeReasons` of the PlaybackInfo reply. A film whose audio outlasts its video enough to fail the 12 second check against the file's duration is re-encoded.

Upgrading from a version without video copy, roll in this order: workers, then `stream` replicas, then `api` replicas. The API is what offers a copy, so it goes last. A worker from before this release that claimed a copy job would not know it is a copy, and would re-encode the picture and store it under the copy's hash; once every worker is new, none can.

After the HEVC and AV1 slice, HEVC and AV1 films scanned before it have no index and no stored bit depth until the next scan reads them (it does so without the file changing), and are re-encoded until then. Chrome plays AV1 in software, so an AV1 film with AC3 audio now arrives as a copy of the file's own picture; it plays HEVC only with a hardware decoder, which jellyfin-web's profile reports, so on other machines an HEVC film is re-encoded as before. What a copy costs in Postgres, network and storage is the H.264 copy's or less (HEVC and AV1 files are smaller than H.264 of the same quality): the keyframe array per request, the Cues or moov read once per scan, no new role. Observed against Jellyfin 12.4 in [`compat/captures/hevc-av1-12.4.md`](compat/captures/hevc-av1-12.4.md).

After this release, existing H.264 films whose audio the client can't play (AC3 in MKV, say) become full-bitrate copies once a scan has read their index, where they were re-encoded. A viewer on such a film gets the source's picture, and the storage and bandwidth change with it: a copy stores and sends the file's own bitrate (see Storage above and the figures under Video copy), where a re-encode is at most 1080p.

**Audio copy.** When the video is re-encoded (a codec the client lacks, interlaced, a level or profile over its limit, a bitrate cap, a burnt subtitle) the audio is copied, not encoded to AAC, if the client's fMP4 HLS transcoding profile lists its codec (of AAC, MP3, AC3, E-AC3, Opus and FLAC), the track has no more channels than that profile's `MaxAudioChannels` and the CodecProfile limits on audio, and it takes no more than a quarter of the bitrate cap (the copy's own bitrate comes out of the cap and the picture gets the rest). Jellyfin's Chrome profile lists AAC, Opus and FLAC with two channels, so there stereo tracks of those codecs copy and AC3 and 5.1 are still encoded to stereo AAC; a client that lists AC3 and six channels gets them as they are, when the track is within a quarter of the cap. A track whose file doesn't state its bitrate (a Matroska file without a `BPS` tag, which the scan now reads) counts as 6 Mbps, so it copies at Auto and under caps of 24 Mbps and up; a film scanned before this version has the bitrates the earlier scan stored, with no rescan forced. The video-copy path still encodes its audio. Observed against Jellyfin 12.4 in [`compat/captures/audio-copy-12.4.md`](compat/captures/audio-copy-12.4.md). After a restart on another worker, a copy from an MP4 has the same audio bytes in each segment; a copy from a Matroska file has the same packets, with times that can move by under 1 ms, because Matroska stores whole milliseconds. That is inaudible, and accepted.

What it costs: a worker spends no CPU on the audio (no decode, downmix or AAC encode) and a restart reads the film the same two times as before. The network, S3 reads and stored segments grow with the track: a 640 kbps AC3 5.1 track in place of 192 kbps AAC is 0.45 Mbps more to each viewer, so 100 streams add about 45 Mbps through `stream` and from the store, and about 0.2 GB per hour of film for each stream in storage (FLAC at 1 to 4 Mbps adds up to ten times that), kept for the 24 hours of any segment. Postgres holds no more than before: a stream's `BitRate` was already in `media_sources.streams`, and the spec hash text is a few characters longer. A copied track is the file's own packets, so a restart on another worker puts the same packets in the same segments (`TestCopiedAudioSplicesTheSamePackets`), where encoded audio differs inaudibly; an MP4 source's audio in each segment is byte for byte the same, and a Matroska source's packets are identical with times that can differ by under 1 ms after a restart, because Matroska stores whole milliseconds (accepted). The risk that is not measured: a client that lists FLAC or AC3 whose decoder stutters on a high bitrate; its CodecProfile limits are honoured, nothing else is.

## Subtitles

A text track in the file is listed with the film and served on the `stream` role as `GET /Videos/{id}/{source}/Subtitles/{index}/{startPositionTicks}/Stream.{vtt,srt,js,ass}`, with the token in the query or a header, as other media. jellyfin-web fetches `js` for SubRip and `ass` for ASS, and `GET /System/Configuration/encoding` before it draws ASS. A non-zero start moves every cue earlier by that much, to zero. Picking another track makes no new PlaybackInfo, no ffmpeg job and no playlist change.

The first request for a track queues a job in Postgres (`subtitle_jobs`, one row per track) and waits for the result. A worker reads the whole file with ffmpeg and keeps the result in the library's asset store, under `subtitles/`, so later requests, other replicas and burn-in jobs read the cache. However many requests and replicas ask, one worker runs one ffmpeg. A worker runs up to four extractions at once, on slots of its own that transcodes don't take (a burn-in job does wait for its track), and renews a lease while it works; a worker killed mid-extraction loses it, and another worker takes the job after at most 10 seconds, up to three attempts in all. A changed file gets a new key and fresh text; the old object is not removed. On a big file on S3 the first request takes as long as reading the file does, and a read is given up after an hour. A track that can't be read answers 500 and is logged, and the failure is remembered for 30 seconds, so a bad track isn't read again for every request.

The `stream` and `api` roles run no ffmpeg or ffprobe, so their image can leave them out (the Dockerfile is not split yet). With no worker running, a track that is already cached still plays, one that isn't is neither listed (in the film's details and in PlaybackInfo, direct play included) nor served: a request for it is answered 503 after six seconds with no worker. The check for what is cached is a request to the asset store for each text track, made only for the details of one film and for PlaybackInfo, and only while no worker runs. A worker that returns lists the tracks again. Extracting uncached subtitles needs a worker, which needs no `transcodeStore` for it. An `api` and `stream` deployment with no worker, upgraded to this version, lists only the tracks already cached, which for a fresh library is none. A request behind busy workers waits its turn. One whose job stays unclaimed for six seconds with no extraction running anywhere, because the only workers are from before subtitle jobs, answers 503 as well.

Upgrading from a version where `stream` extracted subtitles, roll in this order: workers, then `stream` replicas, then `api` replicas. A worker from before this version reports in but never claims a subtitle job, so while only such workers are left, uncached tracks are listed and their requests answer 503 after six seconds.

### Subtitle files and fonts beside the film

A file named like the film, then dot-separated words, then `.srt`, `.ass`, `.ssa` or `.vtt` in the same folder (`Film (2024).en.forced.srt`, on POSIX or S3) is a subtitle track of that film. The words read as Jellyfin 12.4 reads them: a language (`en`, `eng`, `English`, `pt-BR`), `forced` or `foreign`, `default`, `cc`, `hi` or `sdh` (hearing impaired), and any other word is the track's title. The film's own tracks keep their numbers and the files follow in name order; a file keeps its number while it exists, a new file takes the next one, and the number of a file that was removed is never given again.

The scan only lists: it finds the files in the listing it already makes, reads their names, and takes the film's attachments from the probe it already runs. It converts nothing and writes nothing to the asset store. The first request for a track makes a worker convert the file to UTF-8 and keep it in the asset store (one job per file version, whoever asks, and `stream` and `api` run no ffmpeg), so the first request waits for the conversion, as it does for a track inside the film. The worker reads UTF-8 and UTF-16 (with or without a byte order mark) itself. For any other bytes it asks chardet (`github.com/saintfish/chardet`, a Go port of ICU's detector) which character sets they could be in, takes the first of its ranked results that decodes the bytes, and converts the file to UTF-8 itself before ffmpeg sees it. The language in the file's name (`Film.ja.srt`) breaks a near-tie: a result within 10 points (of chardet's 1 to 100) of the best, that decodes too and that chardet reports for that language, wins over it; the name never overrides a clear result. UTF-8 with a few bad bytes (a stray Latin-1 byte, a last character cut short; at most a tenth as many as non-ASCII characters) is read as UTF-8 with those bytes dropped, since chardet ranks such a file anywhere. A stray control byte (NUL, VT, FF, ESC) does not make a file unreadable: these are removed from the converted text, because ffmpeg refuses a file that starts with NUL or ESC and drops every cue from a NUL on. A subtitle track inside a film with a NUL in a cue still loses that cue and the ones after it, as ffmpeg reads it; the film is not rewritten. A legacy file cut inside its last character is read up to it. A file is refused only when none of the ranked results decodes it. **Known limits of the detector**, which this server does not work around: Windows-1250 and ISO-8859-2 text (Polish, Czech, Hungarian, Romanian, Serbian Latin) is read as Windows-1252 or Windows-1254 with wrong letters, because chardet's ISO-8859-2 recognisers report ISO-8859-1, and Thai in Windows-874 is read as a CJK set. ISO-2022 files (ISO-2022-JP, KR, CN) are not read either: they are 7-bit text whose character sets are chosen by ESC sequences, and ESC is removed like the other control bytes, so such a file shows as plain ASCII with stray characters. The remedy is for the operator to convert the file to UTF-8 (`iconv -f WINDOWS-1250 -t UTF-8 in.srt > out.srt`); a changed file is read afresh. A file that can't be read for good (bytes none of chardet's results decodes, a file ffmpeg rejects with an error status, one over 16 MB) is hidden from the film with a warning that names it, and costs one job until the file changes; a failure that isn't the file's, such as the store not answering, a full disk or ffmpeg killed by a signal, leaves it listed and is tried again at a later request. The first request for a file that turns out bad gets an error and the track disappears from the next listing of the film. A scan notices a file added, changed or removed and updates that film without reading the film again. Cost: the scan adds no request to the store; converting a file reads the file once (a few KB) and writes one object of about three times its size, once per version of the file.

The server does not choose which subtitle the viewer starts with: PlaybackInfo reports `DefaultSubtitleStreamIndex` as -1 unless the client names a track (`SubtitleStreamIndex`), for tracks inside the film and files beside it alike, and the details page does not carry the field at all, so the viewer picks one from the menu. Starting on one per the viewer's subtitle mode needs the user configuration routes that save the mode, which come with user management. What Jellyfin 12.4 does is recorded in [`compat/captures/subtitles-default-12.4.md`](compat/captures/subtitles-default-12.4.md), and where the new routes answer differently from Jellyfin in [`compat/captures/subtitles-12.4.md`](compat/captures/subtitles-12.4.md) (the playlist of a track that does not exist is 404 here, the answers for a bad attachment index are plain text, not JSON, the font route carries a token and an ETag, `cmn`, `yue` and `iw` are languages here and titles there, and `tl` is Filipino here and Tagalog there; `cht`, `chs` and other codes with no English name are titles, as Jellyfin shows them).

**Upgrading.** The migration adds a column to each film's media source (the fingerprint of its subtitle files, empty until its next scan), one to `subtitle_jobs` for what a job makes (a track or the film's fonts) and one for whether a failed job failed for good. The fingerprint is kept with the media source because a scan by the version before rewrites that row without it: while replicas of both versions run, the next scan by this version lists the film's subtitle files again, whichever replica scanned last. Such a scan by the version before also forgets the film's subtitle numbering, so this version numbers its files again from the film's own streams: a viewer who held a number from before can then get another file's text under it until they reopen the film. Upgrading every worker before the next scan avoids it. The first scan after upgrading probes again only the Matroska films, the one container whose attachments (fonts) matter: one ffprobe run reading the header of each, and one frame for the film's image, but not the keyframe index or the film's last stretch, which are kept as they were stored (an H.264 film that never had an index still gets one, as at any scan). The other films only have their subtitle files listed, with no read of the film. Each film is stored as soon as its probe is done, so a first scan of a large library shows progress and logs how many films it is probing and, every 100, how many are done; a scan that is stopped and started again carries on with the films left. For a library of tens of thousands of Matroska films on S3 that is one header read (and one frame read) each, which is egress and hours of scan time worth planning for. After that a scan probes a film only when the film changes. A subtitle file added, changed or removed later appears at the next scan of the library, not before, and the scan does not read the film again to notice it.

**Order for this release: workers first, then `stream` replicas, then `api` replicas.** A worker from before this release claims every queued subtitle job as a track, so it would take a fonts job (queued by a new `stream` replica for an attachment) for a track of index 0 and fail it. With the workers replaced first, no such worker is left when a new replica queues one. Any role that starts first applies the migration, which the old code runs beside without harm.

The fonts attached to a Matroska film are listed by the scan. The first PlaybackInfo or ASS track request, without waiting, makes a worker take all the film's fonts out in one job, reading the start of the film and writing each font to the asset store from disk (a font over 64 MB is left out and logged), and a burnt-in ASS or SSA track waits for the same job and is drawn with the fonts. PlaybackInfo and the details page list a font (`GET /Videos/{id}/{source}/Attachments/{index}`, the `DeliveryUrl` of the attachment in PlaybackInfo, which carries the caller's token where Jellyfin's does not) only once it is stored, so the first play of a film draws ASS in jellyfin-web's fallback font and later plays in the film's. A font ffmpeg did not write is left out like one over the cap, and a stored font that has gone from the store is answered with an empty font (a 404 would stop jellyfin-web drawing the track) and taken out again; a burn that finds a listed font gone runs the fonts job again, waits for it and burns with the restored fonts; a SubRip or WebVTT burn does not wait for it. The segments are kept under a hash that does not name the fonts, so a burn drawn without fonts would be what every viewer gets for 24 hours. So a fonts failure that may pass (a store that did not answer, a signal, a full disk, a lost lease, no worker) fails the burn, to be asked for again at a later request (the fonts job is not run again for 30 seconds after it failed). Only a failure that is the film's, ffmpeg exiting with an error status on its header or on an attachment, is recorded by the fonts job as the film having no fonts, for as long as this version of the film lasts (it is forgotten when the file is replaced), and the burn then goes on without them; ffmpeg warnings with exit status 0 are not failures. The route reads the whole font (at most 64 MB) before it sends a header and checks it against its hash; a body the store cuts short, with an error or silently, is answered with the same empty 200 as a lost font (and logged), so a client never keeps a cut font and jellyfin-web still draws. Font responses carry an `ETag` that is the hash of the font and `Cache-Control: no-cache`, not an immutable lifetime, because the URL names an attachment index and the same index is another font once the film is replaced; a request with the ETag in `If-None-Match` is answered 304. Cost: reading the film's header once per film version, and the fonts' size in the asset store (CJK fonts reach tens of MB each; each distinct font is kept once in the asset store by the hash of its bytes, so the episodes of a season that carry the same fonts share them); each request for a font reads it from the asset store, and each burn-in start copies the film's fonts to the worker's disk.

Limits to know:

- The first read of a track on a big file takes as long as reading the file.
- A proxy or ingress in front needs a read timeout longer than that, or the viewer gets no subtitles until re-picking the track.
- The first burn-in of a track shows no picture for that time.
- A burn-in track that can't be read fails the segments that wait for it, once; for a file beside the film the worker then hides it, and a request whose URL still names it is served as naming no subtitle: the segments not yet made are drawn without it, from a spec of their own, while those already made keep it. The player is not told, so a viewer already playing (jellyfin-web drops the stream on a failed segment, DOMAINS 37) sees the picture freeze until a seek or reload, and the recovery above serves only the requests made after that. A burn-in track inside the film that ffmpeg rejects is not hidden (only a file beside the film is): it fails again, once per 30 seconds, at each request.
- Only the worker needs ffmpeg and ffprobe.
- Without a worker, tracks not yet extracted are hidden from the film's details and PlaybackInfo, and a worker that starts again lists them once the page is loaded again. A film listed in a library page never shows its tracks.
- jellyfin-web fetches a subtitle once and sets no time limit of its own that was found in its code or the captures; Chromium held a plain fetch for 200 seconds and then took the answer, so a proxy in front is what needs a long read timeout.
- The first play of a film with attached fonts draws ASS in jellyfin-web's fallback font, which has no CJK glyphs, so Chinese, Japanese or Korean ASS text shows blank for that play when the film's own font is the one that has them; later plays draw it. A film with no CJK font attached shows none on any play. Lists of items and the sessions never list a film's fonts; the details page and PlaybackInfo do once they are stored.
- A host with no fonts draws no burnt text. Burnt-in Chinese, Japanese or Korean text needs a CJK font on the worker, and the shipped worker image has only `font-dejavu`, which has no CJK glyphs, so such text burns as empty boxes unless the film attaches a CJK font (an ASS track draws with those) or the operator adds one (`font-noto-cjk` on Alpine).
- A text track positioned after an unlisted stream (a second audio track, a bitmap codec nothing delivers), or after a gap left by a removed file, loses automatic selection, and can switch off on a quality or audio change. Attached fonts do not cause this.
- Cached subtitle objects and fonts of a replaced file or subtitle file are not deleted.
- Nothing checks which libraries a user may see for subtitle files, fonts or anything else: per-user library access is not built (PRODUCT.md).
- After a client-rendered subtitle is picked in a transcode, switching audio leaves the track disabled with no cues until it is picked again; Jellyfin 12.4 does the same (`compat/captures/transcode-12.4.md`), so it is a jellyfin-web limitation.

A viewer who sets jellyfin-web's burn subtitles to "all" gets the chosen track drawn into the picture instead: the client sends no subtitle profile, the track is marked `Encode`, and a worker re-encodes with the text. "Always burn in subtitle when transcoding" does the same for a film that is transcoded anyway. Changing the track replaces the job, as an audio switch does, and a seek or restart draws the same text at the same time. When the server can't transcode, burn-in has nothing to offer and no track is listed. Deployments need a font: the image has `font-dejavu`, which libass falls back to when a style names one that isn't there.

### Image tracks

A PGS, VobSub or DVB track in the file is listed as Jellyfin lists it (`Codec` `PGSSUB`, `DVDSUB` or `DVBSUB`, with its canvas size); any other bitmap codec is not. How it is shown depends on the client:

- jellyfin-web has a setting to draw PGS itself (off by default). With it on, the PGS track is sent as the file, `GET .../Subtitles/{index}/0/Stream.pgssub`, with ranges, and jellyfin-web draws it over the video on a direct play or a transcode. A worker copies the track out of the film once, in a subtitle job of its own kind (`sup`), and `stream` sends it from the asset store with no ffmpeg. That reads the whole film once for each PGS track, as extracting text does: 40 GB of reads for a 40 GB remux. It stores a few MB.
- Otherwise, and for VobSub and DVB always, choosing the track is a transcode that draws it into the picture. The worker's ffmpeg reads the track from the film in the pass that reads the video, so it costs no extra reads, no storage and no subtitle job, and its CPU is an overlay for each frame. `api` and `stream` run no ffmpeg or ffprobe for any of this.

A burnt-in PGS cue that began before a transcode job started is missed until the next cue. That happens on any restart mid-film: a seek more than three segments away, a pause of over a minute (the job is stopped after 60 seconds without a request), or a worker replaced mid-film. A PGS cue is a few seconds, and text burn-in is exact. A film scanned by an earlier version with an image track is read again by the next scan (its probe, not its keyframes) to list the track. Roll in workers first, as above.

## Run

```sh
docker create --name jf jellyfin/jellyfin:12.4
docker cp jf:/jellyfin/jellyfin-web web-dist && docker rm jf

MEDIA_DIR=/path/to/media JELLYSCALE_ADMIN_PASSWORD=change-me \
  docker compose -f deploy/compose/compose.yaml up --build
```

`MEDIA_DIR` needs `movies/` and `shows/` folders. Segments are kept in the `transcode` volume. Open http://127.0.0.1:8096/web/ and sign in as `admin`. The stack's Caddy ingress sends media and images to `stream` and the rest to `api`. Libraries on S3 need `JELLYSCALE_S3_ACCESS_KEY` and `JELLYSCALE_S3_SECRET_KEY` exported on the host; compose passes them to every service. Add one to `deploy/compose/config.json` such as `{"name": "Cloud", "kind": "movies", "media": "s3://bucket/movies?endpoint=https://s3.example.com", "assets": "s3://bucket/assets?endpoint=https://s3.example.com"}`. For a single process, run `--roles=all`.

## Test

```sh
go test ./...                               # Tests that need nothing outside Go
test/integration.sh                         # Every test, with disposable Postgres, SeaweedFS, Garage and real ffmpeg
test/roles.sh <workdir>                     # Each role as its own process (makes its own films and config in <workdir>)
test/e2e/run.sh <workdir> <playwright_dir>  # Real jellyfin-web, two api replicas, S3, a router, a worker
go run ./cmd/jellyscale --print-routes > compat/endpoints.yaml
```

There are two tiers of Go tests. `go test ./...` runs the tests that need nothing outside Go and passes on a machine with no ffmpeg, Postgres, S3 or fonts. Tests that need any of them live in files named `*_integration_test.go` with the build tag `//go:build integration`, and `test/integration.sh` runs them (`go test -tags integration`) with everything else. It needs Docker, curl, ffmpeg and ffprobe built with libx264, libx265, libsvtav1 and libass, and fontconfig with a font (`fonts-dejavu-core`, or `font-dejavu` on Alpine), and says which is missing when it stops. No test skips for a missing dependency: it fails, naming what it needs. A mistyped build tag would hide a test without any skip, so `TestBuildTags` requires a file's name and tag to agree. `cmd/testreport` fails a run with a skipped test, or with a different number of tests from what `go test -list` finds for the tier, which catches a run that stopped partway. Go tests run through [gotestsum](https://github.com/gotestyourself/gotestsum) (pinned in `go.mod`, run as `go tool gotestsum`), and in CI each job's summary lists passed, failed and skipped counts and each failure's reason, the last line a test located, with an annotation at that file and line. A panic or skip is named but has no line, and an e2e scenario is annotated at the quoted literal of its name, so a scenario keeps any part known only at run time after `: `; a name with no such literal is annotated at the top of the file. `test/roles.sh` and each `test/e2e` gate do the same in CI and print as before locally. A failed job uploads its logs as an artifact: for the Go tiers, `unit.json` or `tests.json` (every test's output, which holds the workers' log lines and the ffmpeg stderr in their errors) and `failures.log` (the full output of each failure, plus the server and worker log of a subtitle test that failed); for roles and e2e, the server, worker and ffmpeg logs; run locally, `JELLYSCALE_LOG_DIR` picks where the logs go. Roles and e2e default to `<workdir>/logs`; the Go tiers keep theirs only when it is set.

`test/e2e` needs `web-dist` (see Run), and a directory with `playwright-core` installed. It drives the browser at `$CHROMIUM_PATH`, `/usr/bin/chromium` if unset. Use Google Chrome (`CHROMIUM_PATH=/usr/bin/google-chrome-stable`) where Chromium is built without H.264 and AAC, which every fixture needs. `E2E_GATES="transcode"` runs one gate. `E2E_HEVC=1` says the browser plays HEVC (a machine with a hardware decoder); the transcode gate then expects HEVC to direct play and copy, where otherwise it expects the H.264 re-encode that CI's Chrome gets. The runner chooses; the test never asks the browser.
